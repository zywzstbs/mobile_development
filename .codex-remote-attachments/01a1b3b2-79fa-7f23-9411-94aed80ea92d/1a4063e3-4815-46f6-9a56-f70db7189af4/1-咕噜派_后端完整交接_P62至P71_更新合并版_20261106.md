## 4. 本人投影、状态和版本例外

`/me`及会话本人投影如实返回 `id/roles/capabilities/accountStatus/identityStatus` 和原业务必需字段。有效超管当前客户端要求显式 `accountStatus=ACTIVE`、`identityStatus=VERIFIED`。平台能力本人字段为 capabilities，管理目录DTO字段仍为 platformCapabilities，不互换名字。

停用、教师待审/驳回、撤权在登录、刷新和每次业务调用均权威核验；返回按钮不是授权。恢复仅处理确实停用且仍合法的账号，不可 `PENDING_REVIEW/REJECTED → ACTIVE` 绕审批。

恢复详情需给真实 `restorationEligible:boolean`（或双方确认的等价允许动作投影）、账号状态、核验状态和真实revision。它只能表达业务事实，不由客户端传回就授权；服务端事务重新检查。

管理资源revision/expectedRevision范围仍为真实整数1～999999999。**这不覆盖私人资料、通知偏好尚未保存时的首次0，也不覆盖附录明确的首次选票0。** 新增超管/重置请求无原版本时不编造expectedRevision，见第6节。

## 5. 管理再认证：P70当前实际格式，等待双方冻结

原 `POST /auth/reauthentications`，使用当前普通会话，不创建第二套长期管理员token。请求例：

```json
{
  "password": "<本人本次输入，不是真实口令>",
  "operationId": "op_example",
  "action": "TEACHER_APPLICATION_DECIDE",
  "targetType": "TEACHER_APPLICATION",
  "targetId": "application_example",
  "expectedRevision": 3,
  "decision": "APPROVE",
  "payloadDigest": "<按下述规范生成的Base64URL摘要>"
}
```

expectedRevision仅适用动作发送，decision仅非空发送。密码不trim；客户端这里只接受非空且最多128字符，不改变注册密码8～64的原契约。不得记录密码原文、再认证token或完整凭据正文。

### 5.1 摘要的当前实现必须精确对齐

P70 `AdminOperation.digest()` 的输入是六个字符串按固定顺序用一个LF连接：

1. action
2. targetType
3. targetId
4. expectedRevision 的十进制字符串；不适用也用 `0` 参与摘要
5. decision；不适用为空字符串
6. 已冻结并trim后的 note；请求体中对应note或reason

连接符为 `\n`（LF），不是CRLF；UTF-8编码→SHA-256→Base64URL无padding。不是JSON摘要，不是十六进制，不包含password、reauthToken、页面代次或本机sessionId。除字段本身字符外不额外加尾换行；尾字段为空时仍保留连接产生的分隔符。

这是客户端单方实现的线格式，不是已部署标准。若后端已有成熟规范，请返回明确映射/改版方案，双方一起调整，不能各自用不同JSON排序或哈希编码。冻结后给出非秘密样例向量供人工核对。

### 5.2 令牌绑定和回包

返回 `reauthToken` 和合法UTC `expiresAt`，P70会核对显著过期；若返回operationId/action/targetType/targetId/expectedRevision/decision/payloadDigest，必须逐项与原操作一致。P70目前仅校验“若回显”的字段；**缺回显不证明未绑定，也不能靠这两个字段证明已绑定。** 请后端明确真实绑定及双方采用的协议就绪证据。

服务端令牌须绑定真实操作者、真实认证会话、operationId、动作、目标、版本/前置条件和业务内容；短期、限本操作、一次性消费、安全指纹存储。账号/会话/目标不符或过期拒绝，真正写入时仍重查授权、回避、状态和版本。普通accessToken续期保持同一业务操作，不把新token当新操作。

## 6. 七类管理写入与完成回执

17项原方法/路径见附录D §6.1，本次没有私自增加操作查询路径。下表七类写入继续带Authorization、X-Request-Id与Idempotency-Key，实际操作者只来自会话。

| 动作action / targetType | 原路径 | 业务正文（均带reauthToken） | 当前正向结果 |
|---|---|---|---|
| ACCOUNT_STATUS_CHANGE / USER | POST /admin/users/{id}/status-changes | status,reason,expectedRevision | 原目标ACTIVE或DISABLED，与决定一致 |
| PASSWORD_RESET_REQUEST / USER | POST /admin/users/{id}/password-reset-requests | reason；当前不发expectedRevision | 真实重置请求已受理，不是密码已更改 |
| TEACHER_APPLICATION_DECIDE / TEACHER_APPLICATION | POST /admin/teacher-applications/{id}/decisions | decision,note,expectedRevision | APPROVED或REJECTED，与决定一致 |
| COURSE_CLAIM_DECIDE / COURSE_CLAIM | POST /admin/course-claims/{id}/decisions | decision,note,expectedRevision | APPROVED或REJECTED，不混用任课ACTIVE |
| ADMIN_GRANT_REVOKE / ADMIN_GRANT | POST /admin/admin-grants/{id}/revocations | reason,expectedRevision | 原grantId变REVOKED |
| SUPER_ADMIN_GRANT / SUPER_ADMIN | POST /admin/super-admins | targetUserId,reason；当前不发expectedRevision | 原账号的授权投影ACTIVE，待激活模型另议 |
| SUPER_ADMIN_REVOKE / SUPER_ADMIN | POST /admin/super-admins/{userId}/revocations | reason,expectedRevision | 原授权REVOKED，版本为授权版本 |

reason/note为trim后1～500字符；decision=APPROVE/REJECT，账号status=ACTIVE/DISABLED。服务端拒绝未知/只读字段和非法状态。请求里的operationId目前主要通过再认证绑定与写入Idempotency-Key关联，不要假设七类正文已包含一个额外operation字段。

### 6.1 同步回执

HTTP成功外壳仍 `code/message/data`。事务提交之后再返回，例如data：

```json
{
  "operation": {
    "id": "op_example",
    "action": "TEACHER_APPLICATION_DECIDE",
    "targetType": "TEACHER_APPLICATION",
    "targetId": "application_example",
    "status": "COMMITTED",
    "resultingRevision": 4,
    "auditId": "audit_example"
  },
  "resource": {
    "id": "application_example",
    "revision": 4,
    "status": "APPROVED"
  }
}
```

operation.id必须是原operationId；资源ID等于原targetId；resultingRevision与resource.revision一致且为精确整数。有原expectedRevision时结果严格递增；新增操作无原版本不造0版管理对象。可回显原expectedRevision/payloadDigest/decision，返回时必须一致。

操作action与审计action不是同一枚举：如请求TEACHER_APPLICATION_DECIDE，审计可为TEACHER_APPLICATION_APPROVED/REJECTED；不要把两者混填。审计结果仍用SUCCEEDED/REJECTED/FAILED，不用近义SUCCESS。

空data、错对象/目标/动作/版本、相反状态、accepted/queued或202不算已提交。若必须异步，先约查询和UI状态再开放，不能返回200空对象骗过界面。

### 6.2 重置与超管的特殊投影

- A05保留顶层 `requestId/targetUserId/expiresAt/delivery`，并补operation+resource。当前通用核对仍要求resource.id是目标账号ID；其revision必须说明真实来源，不能拿重置请求ID/伪版本冒充账号投影。若真实模型不同，双方改DTO，不能凑字段。
- A15/A16的resource是“以目标userId标识的超管授权投影”，revision为真实授权版本；不是随意用用户资料版本替代。
- A05只报请求受理，真正兑换改密后撤旧会话；不得回临时口令/重置token。delivery当前客户端要求非空2～40字符，具体值域和实际安全交付渠道由后端回告。
- P70要求重置expiresAt可解析、晚于客户端当前时间且严格早于未来30天；服务端仍权威验证。请确认真实TTL与时钟偏差策略，必要时双方调整，不能用假日期通过校验。
- P70增设期望ACTIVE，不支持待激活状态完整闭环；如真实服务采用GRANTED/PENDING_ACTIVATION等，不同时塞多个猜测状态，应先共同改协议和页面。

## 7. 幂等、未知结果与拒绝证明

### 7.1 原操作只执行一次

同一操作者、同一稳定业务操作/Idempotency-Key、同业务内容必须原子去重；不能因为换了reauthToken或accessToken就变成新业务。业务变更、幂等结果与审计原子提交。相同键不同业务内容冲突，不再次执行。

已提交后回包丢失，原编号再次核对应返回原已提交回执；读取原回执仍核验当前权限，不泄露已撤权数据。旧一次性令牌已消费不能让合法操作者永久无法核对已提交结果；未提交操作则必须有当前有效再认证。先后顺序由服务端明确。

目前未知操作状态查询端点尚未确定。请后端提出实际路径、DTO、权限和operationId查询规则再冻结；不要按本文猜一个URL部署。后台能按operationId/requestId/auditId核对，也应给出操作说明。

### 7.2 不能把所有4xx当作“第一次未执行”

历史P70曾有单方白名单。P71已经关闭此推断：REJECTION_SEMANTICS_FROZEN=false、逐项确认集合为空，任何当前未确认的4xx都不作为业务未提交证明，CONTRACT_ERROR已剔除候选集合。后端可回告400/413/422的具体前置校验码，以及403的REAUTH_REQUIRED/REAUTH_EXPIRED/REAUTH_CONTEXT_MISMATCH等实际语义，**不代表本文件已批准这些码**。

请后端逐项回告产生阶段、是否保证未提交、是否可能在业务已提交后出现。泛用CONTRACT_ERROR默认不能当未提交证明；回执构造失败、序列化失败、代理错误、后续4xx均不能抹除先前未知。

P71已经补入拒绝语义就绪前提和状态更新的第二道判定。只有已冻结规则、逐项登记的组合、首次尝试、无更早未知，才允许证明本次未提交；当前没有任何组合开放。旧P70记录中的notSubmitted来自未冻结规则，开放写入前还需重新核对其证明来源，不能因旧字段为true就追认成后端证据。

## 10. 客户端本地字段不要变成新的服务端权限

`GET /auth/registration-options`

## 3. 提交注册

`POST /auth/registrations`

匿名；客户端发送 `Idempotency-Key` UUID 和 `X-Request-Id`，不带旧账号 Authorization，不创建登录会话。

|字段|类型与校验|
|---|---|
|`loginId`|string；trim后4～32位；`[A-Za-z][A-Za-z0-9_]{3,31}`；按现有登录服务同一规则判重，必须覆盖已导入账号，不能仅依靠前端查询|
|`password`|string；8～64个UTF-16 code unit；不trim，首尾空格也是密码；确认密码仅客户端核对，不发送|
|`displayName`|string；trim后1～24个UTF-16 code unit；教师应填写可核验姓名|
|`schoolId`|string；必须来自当前允许注册的学校，不因自选学校而自动通过学校身份核验|
|`requestedRole`|`STUDENT`或`TEACHER`；表示申请类型，不能直接作为权限集合落库|
|`teacherApplication`|仅TEACHER必填；trim后5～500字核验说明，例如院系、工号、可供学校核验的信息；STUDENT请求省略|

学生请求示例（仅字段示意，不是测试账号）：

```json
{
  "loginId": "example_user",
  "password": "example-password-123",
  "displayName": "示例同学",
  "schoolId": "school_example",
  "requestedRole": "STUDENT"
}
```

教师请求在上述字段中使用 `requestedRole=TEACHER` 并增加 `teacherApplication`。客户端没有教师权限或管理员权限勾选项；拒绝 `roles`、`capabilities`、`identityStatus`、`reviewedBy` 等未知/只读字段，返回422 `FIELD_NOT_ALLOWED`。

成功HTTP200、`code=OK`，`data`固定为：

```json
{"id":"registration_example","requestedRole":"STUDENT","status":"ACTIVE"}
```

教师成功回执：

```json
{"id":"registration_teacher_example","requestedRole":"TEACHER","status":"PENDING_REVIEW"}
```

响应不包含密码、教师核验原文、accessToken或refreshToken。客户端核对回执后清空密码，提示返回登录；不调用 `/me` 或自动授予身份。注册成功不等同已加入任何课程或小组。

### 幂等、并发与存储

- 同一幂等键与同一正文返回同一注册回执，不能创建多个账号/审核记录；不同正文复用同一键返回409 `IDEMPOTENCY_KEY_REUSED`。
- 数据库对账号规范化值建立唯一约束，两个并发注册只有一个成功；重复账号返回409 `ACCOUNT_EXISTS`。账号规范化规则与登录查找一致，客户端不静默改变账号大小写。
- 不保存含password的原始JSON或明文请求日志。沿用成熟密码哈希库；幂等存储只记录服务端安全指纹和不含敏感内容的回执，不把密码塞进幂等原文表。
- 按账号/IP限制注册频率；超限返回429 `RATE_LIMITED`，可返回 `Retry-After`。服务器关闭注册时返回403 `REGISTRATION_DISABLED`。
- 网络结果不确定时允许客户端以原正文/原键重试；客户端不持久化密码和确认密码，重建后需要重新输入。

### 教师审核与登录

- 教师申请只生成待审记录；审核前不得获得TEACHER、HELP_CONTENT_WRITE、SUPPORT_HANDLE或任何班级授权。
- 服务端由有 `PLATFORM_TEACHER_REVIEW` 的有效超级管理员通过 D 部分的受保护接口核验申请人，复用原运维业务服务；审核记录审核人、时间、理由、版本与审计，拒绝申请人自审。核验说明本身不构成教师身份的可信证据。CLI 仅保留受控初始化/应急恢复等必要运维用途。
- 审核通过后原子激活账号并授予基础TEACHER身份；任课关系仍走已有教师认领和学校事实核验，不自动成为任意课程教师。
- 审核前，只有在正确校验账号密码后，登录返回403 `ACCOUNT_PENDING_REVIEW`；驳回返回403 `ACCOUNT_REJECTED`；错误口令仍按现有 `INVALID_CREDENTIALS` 处理。审核通过后按原会话接口登录。
- 注册幂等重放返回最初的提交回执，不将它作为审核状态查询或授权证据；实际能否登录由当前审核状态决定。P66 已增加超管教师审核页面与调用，接口、联合补充和未完成点见 D；未因此新增公开的匿名审核进度查询接口。

## 5. 友好的字段错误

成功包络不变。校验失败可按以下结构补充，兼容原来的 `data=null`：

```json
{
  "code": "VALIDATION_FAILED",
  "message": "请检查填写内容",
  "data": {
    "fieldErrors": [{"field":"weeklyHours","code":"OUT_OF_RANGE","message":"每周投入时间需为0至60小时"}]
  }
}
```

`fieldErrors` 最多20项，字段为 `field/code/message`，**不要返回填写值**，尤其不要回显password或教师核验材料。建议字段错误码：REQUIRED、INVALID_FORMAT、TOO_LONG、OUT_OF_RANGE、DUPLICATE。客户端主提示使用中文字段标签，不展示协议字段名和长请求编号；主动打开“问题详情”后才展示技术原因与请求编号。客户端本地校验产生的状态值标为“应用状态”，不能将其当作原始HTTP响应。继续返回 `X-Request-Id` 便于排查。

| `PLATFORM_COURSE_GOVERNANCE` | 课程治理读取、认领决定、助理授权紧急撤销 |
| `PLATFORM_ROUTING_MANAGE` | 受理路由/单事项授权管理，App 目前仍是占位 |
| `PLATFORM_AUDIT_READ` | 管理审计读取 |
| `PLATFORM_SUPER_ADMIN_MANAGE` | 超管读取、增设、撤销 |

平台能力不得放进课程 `adminGrants.capabilities`。课程能力仍限原七项：`TEAM_SUMMARY_READ`、`PERSONNEL_READ`、`PERSONNEL_HANDLE`、`ANNOUNCEMENT_WRITE`、`MATERIAL_REQUEST_HANDLE`、`COURSE_JOIN_CODE_MANAGE`、`COURSE_MEMBERSHIP_REVIEW`。

每次管理请求都校验账号可用、有效超管身份、相应能力、平台/学校/课程/事项范围、目标关系、状态、回避和版本。知道 URL、修改目标 ID、客户端显示按钮、持有近期再认证令牌均不能替代这些校验。

## 4. 会话与 `/me` 投影

超管继续原会话，不建立第二套 App 长期总密钥。正常有效超管的最小示例：

```json
{
  "id": "operator_1",
  "displayName": "平台管理者",
  "schoolId": "school_1",
  "accountStatus": "ACTIVE",
  "identityStatus": "VERIFIED",
  "roles": ["SUPER_ADMIN"],
  "capabilities": [
    "PLATFORM_ACCOUNT_READ",
    "PLATFORM_ACCOUNT_MANAGE",
    "PLATFORM_TEACHER_REVIEW",
    "PLATFORM_COURSE_GOVERNANCE",
    "PLATFORM_ROUTING_MANAGE",
    "PLATFORM_AUDIT_READ",
    "PLATFORM_SUPER_ADMIN_MANAGE"
  ],
  "skills": [],
  "revision": 1
}
```

这是 `data` 内的本人投影示意，不是真实账号。原 `/me` 其他业务必需字段继续保留。

注意本人 `/me` 使用 **`capabilities`**；下文管理账号 DTO 使用 **`platformCapabilities`**。不能把两者当作同一个字段名任意替换。

首位全功能超管建议明确配置七项平台能力。P66 增设超管请求不含“选择能力”字段，需后端确认固定超管权限配置如何派生/授予；不能接收普通用户任意 PATCH `roles/capabilities`。若以后需要细分平台管理者权限，应同步补全客户端相应入口，不能为了露出按钮一律多授权限。

`accountStatus` 与 `identityStatus` 分开：

- `accountStatus` 是账号登录/使用状态；当前管理账号 DTO 接受 `ACTIVE/DISABLED/PENDING_REVIEW/REJECTED`。
- `identityStatus` 是身份核验状态，沿用已有契约；有效身份使用既有 `VERIFIED`。
- 停用必须在登录、刷新及每次业务调用上拒绝，不能只改 `/me` 文案或等待 token 自然到期。
- 当前 P66 客户端只用 `identityStatus` 处理停用，这是已复现缺陷；客户端负责人负责修复，**请后端不要篡改两个字段含义来迁就该缺陷**。

## 5. HTTP 通用契约

下文路径均相对 `/api/v1`。

- 认证：原 `Authorization: Bearer ...`；只接受原会话中的当前账号，不信任正文传的操作者身份。
- 请求追踪：原 `X-Request-Id`；写入原 `Idempotency-Key`。令牌、口令及密钥不记录到日志。
- 成功外壳沿用 `{"code":"OK","message":"成功","data":...}`；错误沿用项目原外壳/错误码和请求编号。
- 稳定 ID：当前管理客户端接受 `[A-Za-z0-9_-]{1,120}`；不要返回带空格、斜杠的内部复合键。
- `revision` / `expectedRevision` 必须为真实整数，写入版本范围 1～999999999，不用 0、浮点或伪造递增值兜底。
- 时间由服务器产生，统一 ISO 8601 UTC，例如 `2026-11-05T12:00:00Z`。当前字符串解析上限 40 字符；不要回本地中文时间。
- 搜索 `query` 当前最多 40 字符；列表 `limit` 1～50，App 实际使用 20。
- 游标当前只接受 `[A-Za-z0-9._:-]{1,300}`，推荐不带 padding 的 URL-safe 编码，不使用带 `+/=` 的标准 Base64。
- 一般列表必须返回 `items:[]`、`hasMore:boolean`、`nextCursor:string`、`total:integer`；有更多时游标非空。`total` 是当前授权/过滤范围的真实总数，不把本页长度当总数。
- 响应不得带密码、哈希、access/refresh token、API key、临时口令等。再认证响应的 `reauthToken` 是特定用途凭证，除此之外管理目录/审计不返回凭证。

使用通用分页，每条：`id,actorId,actorName,actorRole,action,targetType,targetId,scope,reason,result,requestId,createdAt`。必填稳定 `id`、`action`、`result`、服务器 `createdAt`，其余也应如实提供；`scope` 当前是最多 200 字符的可读字符串，不是嵌套对象。

审计不可由 App 编辑/删除。旧 CLI 历史没有可证实的用户 ID 时保留真实来源/未知项，不能归到新建超管伪造历史。

当前结果文案映射为 `SUCCEEDED/REJECTED/FAILED`，分别表示成功/拒绝/失败；不要返回近义的 `SUCCESS` 让客户端显示“结果待核验”。

### 6.7 超管目录 A14

`data.items[]` 每条：`userId,displayName,status,grantedAt,grantedBy,revision`。当前 `status` 只支持 `ACTIVE/REVOKED/DISABLED`。

P66 不请求分页，也不使用服务器返回的总 activeCount，而是从全部 items 计算。因此当前必须返回完整小规模目录；不能静默只给第一页。若需要分页/激活中状态，必须同步改 App；客户端计算仅用于提示，**最后一位有效且可登录的超管保护必须在后端事务执行**。

### 6.8 当前写入请求体 A04/A05/A08/A11/A12/A15/A16

每个写入均带原幂等头；下列是 P66 当前实际字段，不代表已满足第 7 节的安全绑定和回执验收。

| 接口 | 当前 JSON 正文 |
|---|---|
| A04 账号停用/恢复 | `{status:"ACTIVE"或"DISABLED",reason,expectedRevision,reauthToken}` |
| A05 重置请求 | `{reason,reauthToken}`，当前**没有 expectedRevision** |
| A08 教师审核 | `{decision:"APPROVE"或"REJECT",note,expectedRevision,reauthToken}` |
| A11 认领决定 | 与 A08 相同，版本是认领申请版本 |
| A12 助理授权紧急撤销 | `{reason,expectedRevision,reauthToken}` |
| A15 增设超管 | `{targetUserId,reason,reauthToken}`，无任意 roles/capabilities 字段 |
| A16 撤销超管 | `{reason,expectedRevision,reauthToken}`，版本是超管授权版本 |

`reason/note` 均为 trim 后 1～500 字；同意和驳回都需要真实说明。P66 再认证令牌长度 8～200；不能由 App 自己生成可信令牌。

A05 当前校验的受理回包是：

## 7. 上线前双方必须确认的联合补充

### 7.1 再认证绑定上下文

P66 当前 A17 只发送 `{"password":...}`，期待 `{reauthToken,expiresAt}`。不能由这两个字段证明已绑定具体管理动作。

建议 A17 增加以下操作上下文，客户端冻结确认后的动作/目标/版本和内容摘要，在当前服务器和会话中提交；这组字段**尚未由 P66 完整发送**：

```json
{
  "password": "<本人本次输入，示例不含真实口令>",
  "operationId": "operation_1",
  "action": "TEACHER_APPLICATION_DECIDE",
  "targetType": "TEACHER_APPLICATION",
  "targetId": "application_1",
  "expectedRevision": 3,
  "decision": "APPROVE",
  "payloadDigest": "<双方约定的非凭据业务内容摘要>"
}
```

实际字段、摘要规范和动作枚举由双方冻结；版本不适用的新增授权应绑定明确目标、动作、内容及对应关系前置条件，不能编造 revision。再认证令牌由服务器生成并绑定操作者、会话、操作编号、动作、目标、原版本/前置条件和冻结内容，短期有效、限本操作使用，服务端保存安全指纹。

建议初期有效窗口 5 分钟，由服务器时间裁决；没有有效绑定、已到期、其他账号/会话/目标使用时拒绝。回包仍包含 `reauthToken` 和 UTC `expiresAt`，不创建 access/refresh 会话、不回显密码。

再认证不是授权：实际写入仍重查账号、角色、能力、范围、回避、状态和版本。不要仅凭“密码正确过”放行另一笔操作，也不能靠前端确认弹窗代替绑定。

### 7.2 管理操作回执

建议同步写入在事务提交后返回可核对的 `operation`，而不是 `{}` 或异步受理即报完成。例如教师审核：

```json
{
  "operation": {
    "id": "operation_1",
    "action": "TEACHER_APPLICATION_DECIDE",
    "targetType": "TEACHER_APPLICATION",
    "targetId": "application_1",
    "status": "COMMITTED",
    "resultingRevision": 4,
    "auditId": "audit_1"
  },
  "resource": {
    "id": "application_1",
    "status": "APPROVED",
    "revision": 4
  }
}
```

这是联合补充格式，当前 P66 尚未验证它。其他写入用同一结构并返回相应目标与实际结果；A05 可保留第 6.8 节顶层重置字段并补 operation，避免直接破坏当前专用解析。

客户端必须核对动作、目标、已提交状态、结果版本及业务结果，再清表单/提示完成。错目标、空对象、无结果版本、响应损坏都保持未确认状态并读回；HTTP 202 或“仅入队”不能套用同步完成提示。若必须异步执行，另约查询接口与 UI 状态后再开放。

### 7.3 幂等与结果未知

- 幂等域绑定当前操作者及稳定业务操作，业务变更和审计在同一事务内提交，不能操作成功却没有审计。
- 请求超时/断网后不能直接生成新操作再次停用/审核/重置；先按原操作编号/幂等回执或目标版本核对结果，再决定重试。
- P66 现有请求指纹包含正文中的 `reauthToken`。若重新认证取得新令牌，可能变成新指纹和新幂等键；客户端应保留稳定操作编号与确认内容，后端应明确凭据更新不改变同一业务操作的归属。
- 相同操作/幂等键、相同业务内容返回同一已提交回执；不同业务内容复用键冲突。重放仍重查当前会话与授权，不能因历史回执泄露已无权数据。
- 已提交且同一操作的回执读取不应因旧一次性再认证令牌已消费而无法核对；未提交操作则必须满足当前有效再认证。具体顺序由服务端实现统一，不能靠客户端猜成功。

## 8. 必须在后端实现的状态、事务和失效约束

### 8.1 账号与教师审核

- A04 只允许合法账号状态转移；一般恢复只处理确实被停用且仍符合资格的账号。P66 目前会给所有非 ACTIVE 状态显示“恢复”，客户端需限制，后端必须拒绝用恢复账号绕过 `PENDING_REVIEW/REJECTED` 教师审核。
- 教师通过/驳回校验当前待审版本、申请人和操作者，禁止自审；并发审核只有一笔决定生效，其余返回冲突并读取已处理结果。
- 审批与账号资格/角色更新及审计原子完成；审批不产生课程认领、HELP_CONTENT_WRITE 或 SUPPORT_HANDLE。
- 停用、撤销角色或重置后，旧会话后续请求/续期不得继续获得原授权。刷新 token 不能恢复已撤销资格。

### 8.2 任课与班级助理

- 课程保持唯一当前教师；合法学校范围、身份核验、原课程转交接受及历史关系规则保持。平台核验不冒充教师提交认领，不直接改学生成绩。
- 助理常规任命仍只由当前任课教师执行，候选来自该课有效学生；保留七项局部能力、有效期、本人/本组回避及真实受理关系。
- A12 是带理由的紧急撤销，不提供给助理自用，不等同平台可以任意扩权。撤销不删除历史公告、人员记录、成绩或任务。
- 原人员事项授权保留 case 范围与接续者本人接受；管理路由不授正文读取权。复用原服务锁顺序和事实校验，避免另建一条绕过业务的 HTTP 写法。

### 8.3 超管及最后一位保护

- 首位初始化仅受控服务器工具执行；不能公开匿名初始化 API，也不能由每个 App 首次启动各建一个超管。
- 增设禁止自授，撤销/停用禁止通过普通路径锁死管理；并发操作也要保护至少一位有效、可登录且具有必要管理恢复能力的超管，不能只数角色表行数。
- 保护覆盖撤销超管、停用账号及其他会导致最后管理者不可用的路径，不能只在 A16 做一次列表计数。
- 可用数据库事务、稳定全局管理约束锁或等效机制复用现有设计，不能只靠前端 activeCount 或先查后改。
- 首期若只允许给已完成账号激活的独立账号授予超管，请明确该前置条件；若需要待激活状态/强制改密，须同步加客户端流程，P66 当前不支持该闭环。

## 9. 错误码与客户端协同

| HTTP / 建议错误码 | 含义 |
|---|---|
| 401 / 原 `SESSION_EXPIRED` 等 | 原会话失效；按原刷新与登出机制处理 |
| 403 / `ACCOUNT_DISABLED` | 账号停用，不得通过刷新恢复 |
| 403 / `FORBIDDEN`、`SELF_REVIEW_FORBIDDEN` | 无当前能力/范围或自审被拒绝 |
| 403 / `REAUTH_REQUIRED`、`REAUTH_EXPIRED`、`REAUTH_CONTEXT_MISMATCH` | 再认证缺失、到期或绑定不符 |
| 409 / `REVISION_CONFLICT`、`INVALID_STATE_TRANSITION` | 原版本已变或状态不允许 |
| 409 / `LAST_ACTIVE_SUPER_ADMIN` | 操作会移除最后有效管理者 |
| 409 / `IDEMPOTENCY_KEY_REUSED` | 同键业务内容变化 |
| 404 / `RESOURCE_NOT_FOUND` | 单个对象不存在；与接口未部署区分 |
| 404 / `PATH_NOT_FOUND` 或 501 / `ENDPOINT_NOT_IMPLEMENTED` | 管理接口尚未提供 |
| 422 / 原字段错误码 | 非法字段、越界值、只读字段注入等 |
| 429 / 原限流码 + `Retry-After` | 密码验证、管理写入等限流 |

P66 目前将任何 404 都说成“管理服务尚未开放”，应由客户端修正错误分类。请保持服务端准确语义，不用 HTTP 200 + 空对象伪装错误，不把未知路由和资源不存在混成“业务成功”。错误/审计均不回显口令或核验敏感正文。

## 12. 建议排期与完成证据

### 第一批：打通一条可信角色链

确认角色/能力和账号状态 → 首位受控超管 → 管理读取与教师申请 DTO → 联合再认证/回执 → 教师审核事务与审计 → 有效教师按原流程任课 → 教师任命本课助理 → 撤销后旧会话被拒。

前端 F01/F02 与第 7 节修正先完成；读取可先对齐，管理写入不要在契约尚不安全时开放给真实账号。

### 第二批：完善其他日常管理

账号停用/恢复/安全重置、课程认领决定、授权紧急撤销、超管增设/撤销、审计分页及最后管理者并发保护。实际部署前仍须完成第一批已经要求的核心失效/审计规则，不把它们留成以后再补。

### 第三批：关闭剩余 CLI 操作和交互缺口

路由/单事项授权 App 闭环、助理候选与有效期、教师资格撤销及双方确认的本人改密/激活流程。逐项标记“已实现／仅接口／仅页面／未验收”，不要以占位说明算完成。

### 必交验证

- 服务端：未登录和其他三角色直调管理 API 被拒；替换 ID 跨学校/课程/事项被拒；自审、越权能力、非法状态和只读字段注入被拒。
- 并发/事务：教师重复审核只生效一次；角色/账号/审计原子；两人同时撤销/停用不能锁死最后管理者；幂等重放不重复执行。
- 会话：账号停用、资格/授权撤销、实际密码重置后，已签发的旧会话下一次无权请求拒绝，刷新不能恢复权限。
- 回执：空/错对象/错版本/仅受理的回包不能被 App 当作完成；超时后原操作核对，不新增重复审核或重置。
- 真实隔离四账号：超管审核→教师任课→助理局部授权→学生使用→撤销失效，记录 App/服务端版本、迁移号、请求和操作编号。
- 数据：原学生项目、提交、成绩、局部授权历史及 CLI 审计保留；超管没有默认聊天/成绩正文读取或代业务能力。

Mock/Preview 只能证明客户端按协议响应，不能替代以上真实后端与事务证据。生产开户、迁移、部署和发布按真实授权执行，本文本身不代表已经执行。
