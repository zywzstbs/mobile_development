# P58 后端接口适配：分步修改执行方案

编写日期：2026-11-02。

适用仓库：当前 gulupai-server 后端。目标：在现有第一版后端基础上适配 Android P58 接口契约，供执行模型逐步实施。

## 1. 审查结论与证据边界

P58 文档中 281 个正式 HTTP 方法与路径组合，在现有 Controller 中均能静态匹配。这次主要工作是既有接口的请求、响应、权限、状态和事务适配，不是重新开发 281 个接口。

路由存在不代表契约兼容。已经确认求助、帮助、正式约定、合并投票等结构差异。其余模块仍需逐字段核验，不能标记为全部兼容。

本方案依据静态代码审查制定；编写时未修改业务代码、未迁移数据库、未运行测试，也未验证 Android 真机联调。文中的“验收”均为执行要求，不是已通过记录。

## 2. 契约依据与实施边界

主契约：[咕噜派_API接口设计文档_P58_完整重编版.md](./咕噜派_API接口设计文档_P58_完整重编版.md)。

阅读顺序：

1. 第 3～7 节：通信规范、幂等、状态、公共字段、错误。
2. 第 8 节：逐接口请求、权限和动作要求。
3. 第 9 节：完整响应结构；示例不能代替字段表。
4. 第 10 节：明确保留的契约缺口。
5. 第 11 节：唯一约束、部署和验收要求。

实施约束：

- 继续使用现有 Spring Boot、JDBC、PostgreSQL、Flyway 架构，不更换框架或整体重写。
- 当前迁移到 V022；新增迁移从实施时的实际最大版本递增，不修改已执行的 V001～V022。
- 保留已修复的材料回应版本、审核记录、时间可信度和迁移证据。参考 `docs/backend/修复方案`、`修复结果`、`审查记录` 中最新记录。
- P57 主题、P58 图标、本地扫码载荷生成、摇动动画、本地附件库、本人 BYOK AI 本地能力不新增后端接口。
- 不将 Preview 的 `/app-config`、`/schools` 扩成生产服务。
- 课程入课证明 FILE、通知置顶等未闭合契约只登记缺口，不自创 purpose、caseId 或路径。
- 旧客户端兼容需求没有明确前，不给所有旧字段添加宽松别名。若需双版本兼容，先形成明确适配规则。
- 每阶段独立提交实现和验收记录，不一次性修改所有模块后才测试。

## 3. 已确认的差异与代码入口

下列路径相对仓库根目录，Java 包根为 `src/main/java/cn/gulupai/server/`。

|范围|现有实现|P58 要求|结论/入口|
|---|---|---|---|
|路由|281 项静态匹配|281 项正式接口|保留路由基础，运行时再校验|
|创建求助|读取 subject/body/attachments|title/content/attachmentFileIds，类别、范围和上下文|必须修改；support/HelpSupportService.java|
|求助回复|读取 body，返回详情|content、附件、版本；返回本次实际 reply|必须修改；同上|
|求助转交|targetUserId，只改负责人|targetRouteId、reason、expectedRevision，渠道候选及回显|必须修改；同上|
|求助状态|创建 OPEN|SUBMITTED|迁移并调整动作；同上|
|求助读取|SUPPORT_HANDLE 可能读取任意工单|当前真实指派范围|收紧；ticketDetail 等入口|
|求助业务防重|找到 clientRequestId 直接返回|相同意图复用，异意图冲突|补规范请求比对|
|求助动作|多项未读取版本及幂等键|版本、持久幂等、事务内复核|support/HelpSupportController.java|
|帮助编辑|顶层 title/body，HELP_ADMIN|expectedRevision + article；HELP_CONTENT_WRITE 或本课教师|必须修改|

## 4. 每阶段通用工作方式

1. 阅读契约和实际调用链，包括 Controller、请求类、Service、Repository、响应类、迁移和测试。
2. 先增加能复现差异的 HTTP/业务反例，记录修改前结果。
3. 实现最小完整修改，包括数据库、业务、投影、权限和幂等；不能只改字段名。
4. 执行相关测试，检查持久化结果与失败回滚。
5. 更新接口差异清单和阶段交付记录。
6. 记录未完成项、环境阻塞及契约歧义，不以空对象、虚构默认值或删除测试掩盖。

每阶段交付记录必须包含：任务编号、修改文件、接口编号、行为变化、迁移影响、测试命令与真实结果、剩余问题。

## 5. P58-00：建立契约基线

### 步骤

1. 阅读 README、测试配置及最新修复记录。
2. 记录当前提交号与工作区已有修改，避免覆盖其他工作。
3. 从主契约第 8 节提取正式接口声明，得到 281 项；不要把带示例 ID 的“请求形态”算进去。
4. 建立 `P58接口差异清单`，字段至少为：接口编号、方法、路径、Controller、请求类、Service、响应类、请求差异、响应差异、权限差异、数据库差异、测试、状态。
5. 对照 Spring 实际 RequestMappingHandlerMapping，验证方法和路径。
6. 执行现有基线测试，区分代码失败、数据库不可用、凭据缺失等原因。
7. 将本方案已确认项录入，其他标为“待核验”。
8. 现有 `src/test/java/cn/gulupai/server/it/RouteCoverageIT.java` 依赖旧索引及覆盖清单，应新增 P58 来源校验，不能只断言数量为 281。

### 验收

- 281 项都有代码定位，无重复或遗漏。
- 未核验项未冒充兼容。
- 基线失败保留，不删除旧测试制造通过。

## 6. P58-01：公共校验和契约测试

### 步骤

1. 为帮助、求助、举报的 Map 请求建立明确 DTO。Jackson 对 DTO 未知字段的限制不能自动约束任意 Map 键。
2. 按字段表添加必填、可空、长度、枚举、版本及 ID 校验。
3. 严格区分整数、布尔、字符串，禁止宽松转换掩盖错误输入。
4. 未知字段返回 HTTP422 / FIELD_NOT_ALLOWED。
5. 对照响应字典检查普通文字、集合、可空关系与空子记录的不同语义。
6. 检查时间输出，学校节次固定 HH:mm:ss，不能整分钟输出成 HH:mm。
7. 补 HTTP 层测试，确认无效输入不能写数据库。

### 验收反例

- expectedRevision 传字符串；resolved 传字符串。
- 必填字段缺失或传 null。
- 传入 assigneeId、createdBy 等只读字段。
- 新建求助仍传 subject/body。
- 超长字段、非法 ID、非法枚举。

## 7. P58-02：求助数据模型与迁移

### 步骤

1. 盘点 V018 对应工单、回复、路由、历史、附件及现有唯一约束。
2. 在新迁移中补类别、课程范围、上下文、解决确认等所需结构。
3. 明确路由类别、课程范围、当前接收者及有效性来源。
4. 为回复补附件关联，优先复用现有文件引用机制。
5. 为业务防重保存可核对的规范请求或摘要；规范化策略与幂等一致。
6. 分析 OPEN 历史数据，区分首次提交和重开后记录，根据历史转换，不能无条件一刀切。
7. 无法推导的旧字段登记迁移例外，不编造课程、负责人或用户确认事实。
8. 编写空库升级和有旧数据升级测试，核对行数、历史及关联。

### 验收

- 旧工单、回复、历史和附件不丢失。
- 新结构能持久保存完整 P58 请求。
- 迁移重复启动安全；旧 Flyway 文件未修改。

## 8. P58-03：求助创建、回复与防重

### 步骤

1. HELP-07 使用完整 DTO：clientRequestId、routeId、category、title、content、squareId、context、attachmentFileIds。
2. 校验 route 与类别、课程范围一致且存在当前真实接收渠道。
3. 新建状态为 SUBMITTED。
4. 同用户/clientRequestId 相同规范请求返回原业务记录，异请求返回冲突；不能在意图校验前直接返回旧记录。
5. HELP-10 接收 expectedRevision/content/attachmentFileIds。
6. 在事务内锁工单，验证版本、当前资格与状态。
7. 同事务插入回复、绑定文件、更新状态和版本、保存幂等结果。
8. 按 R_HELP_10 返回本次实际 reply，不能以完整工单详情代替。
9. 同键重试返回同一回复 ID，异正文同键不产生第二条。
10. 幂等回放重新检查当前访问资格。

### 验收

- 并发创建只产生一张工单。
- 同 clientRequestId 更换标题、正文、附件或范围被拒绝。
- 回复超时重试不重复写入。
- 旧版本回复无任何状态变化。
- 已转交的旧负责人不能继续回复或读取受限结果。

## 9. P58-04：受限转交和求助状态机

### 步骤

1. HELP-09 返回 transferTargets；只向非提问者的当前合法处理人展示。
2. 候选来自真实 route，routeId 唯一，最多 20 项，字段按响应字典。
3. 保持原单课程范围；null 范围仅按文档允许的类别处理。
4. HELP-15 输入 expectedRevision、targetRouteId、reason。
5. 在事务内重新查询目标 route、接收资格、原单版本，不信任旧候选。
6. 原子切换 route、负责人、状态、版本和历史。
7. 成功精确返回 transferTargetRouteId。
8. 注意现有 transfer 最后调用 ticketDetail：转交成功后旧负责人可能失去详情权，直接调用可能导致事务回滚。按契约构造本次动作允许的结果，并保证随后 GET 权限正确收紧。
9. 失败保持原负责人、route 和状态。
10. 接单、状态动作、解决确认、关闭、重开逐项补版本、幂等、当前权限和状态转换校验。
11. 只有提问者本人的明确确认才能设置 resolvedByRequester；处理者关闭不是本人解决确认。

### 验收

- 目标失效、授权到期、跨课程、提问者自转交被拒绝。
- 两个动作竞争同版本只有一个生效。
- 仅有 SUPPORT_HANDLE 不能读取所有工单。
- 转交失败原人继续负责；成功后旧人失权。
- 处理人关闭不产生虚假本人解决确认。

## 10. P58-05：求助图片完整链路

### 步骤

1. 复用 FileService 的上传、摘要、签名及短期授权机制。
2. SUPPORT_ATTACHMENT 无 ticketId 时仅本人临时私有；有 ticketId 时检查当前工单资格。
3. 仅允许 PNG/JPEG/WebP，大小最多 8MiB。
4. 完成上传核对实际大小、签名和已提供 SHA256。
5. 创建或回复引用文件时检查：最多三个、无重复、本人上传、READY、purpose 正确、范围不串单。
6. 文件引用关联与工单/回复写入同事务完成。
7. 详情和回复准确返回 attachmentFileIds。
8. 下载授权和实际下载都检查当前工单访问资格。
9. 无关联的临时图片不向他人开放；已关联文件不能误作孤立文件清理。

### 验收

- 未传真实字节、假图片、错摘要、错大小不能 READY。
- 他人文件、跨单文件、错误用途和未 READY 文件不能引用。
- 业务保存失败不残留错误关联。
- 转交后旧负责人不能获得新下载授权，旧授权使用也受当前权限约束。
- 独立字节传输不携带业务 Bearer 或幂等键。

## 11. P58-06：帮助与举报契约

### 步骤

1. HELP-05 改为 expectedRevision + article 包装，保存文档定义的结构化内容。
2. GENERAL 编辑使用 HELP_CONTENT_WRITE；COURSE 编辑检查当前本课教师资格。
3. 旧 HELP_ADMIN 授权制定明确迁移规则，不无条件扩大权限。
4. 帮助反馈按本人、条目、正文版本记录，处理 reasonCode。
5. 帮助列表和内容包真正执行声明的版本、范围及筛选参数。
6. 举报逐项核对 DTO、版本、幂等、clientRequestId 和当前指派范围。
7. 举报只提供必要证据，不因此开放完整群聊。
8. 按契约实现 cursor 分页，不继续将这类列表全部包装为 ListEnvelope.full()。

### 验收

匿名通用帮助、课程帮助越权、旧正文反馈、举报异正文防重、未指派读取、分页续页与失权均有测试。

## 12. P58-07：正式约定响应

### 步骤

1. 修改 DeliveryViews.AgreementView，将 ownerId、dueAt、units、reviewerPolicy 展开到顶层。
2. 按第 9 节补 kind 及其余必有字段，值来自真实业务。
3. 修改所有构造和返回该响应的入口。
4. 写入请求继续保留 plan/assessedPlan 包装，不将响应结构错误套到请求上。
5. 核对普通任务与正式任务创建的分支必填项。
6. 检查旧幂等结果的响应结构兼容策略。不能原样回放不兼容旧 JSON，也不能简单清空幂等记录使旧操作重做。采用经过测试的结果适配方案，并保留原操作身份与业务结果。

### 验收

约定详情、创建和确认结构一致；普通任务无需 assessedPlan；分项贡献、验收和撤回并发回归通过。

## 13. P58-08：合并投票与人员投影

### 合并步骤

1. 修改 MergeViews.SideView，输出 eligibleCount、agree、disagree、abstain、unvoted、passed、requiredYes。
2. 从真实冻结资格集合和有效选票计算，不能仅改名或填 0。
3. 严格过半 requiredYes = floor(eligibleCount / 2) + 1；两侧分别判断。
4. 盘点 WAIT_TEACHER、RETURNED 的所有写入点、动作和历史，根据真实阶段映射目标状态，不能机械替换为 WAIT_FACT。
5. 保留资格变化阻断及原作业、成绩分离。

### 人员步骤

1. 检查 Vote 实际投影，普通响应不暴露 electorate。
2. 补本人 myBallot、数量及 result；未结算为 null，结算为 PASSED/NOT_PASSED。
3. 交接响应保留真实 items、方案版本、接任状态及 LEADER 条目；nextLeaderId 是保存输入，不能替代实际条目。
4. 补资料 review 与事项 history 固定对应 responseVersion，不能套用任务验收结构。
5. GOV-19 是当前有权处理者撤回待补资料请求，不是学生删除回应历史。

### 验收

两侧人数不等、弃权、未投、资格变化和旧成绩隔离有测试；回归 GovT01T06IT、GovU01MaterialStateIT、GovU02MaterialTimeIT、W01 系列，不破坏时间证据修复。

## 14. P58-09：课程字典与匹配

### 步骤

1. 验证 COURSE-03/04 完整 Page 信封和所有必有字段。
2. 验证学校、学期、节次归属一致，稳定排序且无隐藏截断。
3. 固定日期、时间和时区格式。
4. 匹配与创建使用明确 termId，同名课跨学期不能误命中。
5. 检查学校、学期、规范课程、教师、完整时段集合的数据库唯一性及并发创建。
6. 不为旧 MergeScreen 无范围调用放宽 /squares 的学校学期鉴权。
7. 入课证明暂用 LINK，不制造 caseId 走 MATERIAL_PROOF。

### 验收

完整字典、大集合、跨学校、跨学期、并发创建、课程码只定位不入课均覆盖。已有实现符合时保留，只补测试证据。

## 15. P58-10：通知范围修订与预览绑定

现有实现已支持预览 payload 更新 assignmentId，不从零重写。当前修订路径调用 courseAudience(squareId)，必须核对它是否符合具体课程/作业范围，不能只改 assignmentId 而继续无条件使用同一接收群体。

### 步骤

1. 核对 NOTICE-03/05 字段和权限。
2. 预览绑定本人、课程、目标版本、发布身份、固定参数、范围和有效期。
3. 提交比较预览内容与实际请求，不能混用两个版本的标题正文。
4. 实质修订生成新正文版本、接收者快照及回执基线。
5. 正文、快照、回执基线、outbox 在同一事务内提交。
6. 排版修订不得改变范围或重置已读、知悉。
7. 旧正文回执不能满足新版；重试不重复生成通知和提醒。

### 验收

范围变化、过期或旧 token、正文不匹配、双身份、授权到期、事务失败、重复提交及旧回执隔离有测试。

## 16. P58-11：剩余接口全量核验

前述任务不是全量兼容证明。继续检查 AUTH、TEAM、ROLE、TASK、GRADE、REPORT、PROFILE、AI、DICE、BOARD、CHAT 等其余接口。

每项核验：

1. 请求字段、分支必填、类型及校验。
2. 响应字段、层级、可空关系及状态。
3. 声明 query 参数是否真正生效。
4. 当前权限及幂等回放权限。
5. revision、业务版本、sourceKey、contentVersion 等是否混用。
