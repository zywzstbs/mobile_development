## 3. V00：明确三类事实，避免修错语义

开始修改前，建立下面的来源说明表，填写实际表/字段和查询入口。

|事实|含义|不得替代它的事实|
|---|---|---|
|本人接受份额|本人对适用责任依据的有效接受，可按明确规则继承未变部分|signed 标志、上传、验收、贡献确认、他人接受|
|调整确认|受影响者对特定提案、特定基础版本和变更范围确认|任意历史 ACCEPT、另一提案确认|
|验收继承|目标交接约定对应安排下，允许继承的既有验收依据|任务现在的验收人、未来提交、其他约定的安排|

必须区分：

- 当前读取的是哪一版约定。
- 某分项/份额的责任依据来自哪一版。
- 某次接受或验收是针对哪个版本和来源。
- 当前访问权限与历史事实：权限每次重验，但这不等于用当前安排覆盖历史事实。

## 4. V01：局部调整的反例与根因（P2）

### 4.1 代码位置

- `delivery/DeliveryService.agreementView()`，审查时约第 1271～1287 行。
- `projectUnit()` 中 `acceptedBy.contains(share.userId())`。
- `maybeApply()`：只要求受影响者确认、生成新 ACTIVE 约定、复制无关分项份额。
- `proposeOnce()` 或对应创建提案方法：计算 affected_users。

当前 agreementView 构造一个按用户 ID 的 acceptedBy 集合，只加入本约定 agreement_ack 的 ACCEPT，以及本约定来源提案的 CONFIRMATION/ACCEPT。局部调整产生的新约定通常没有原成员的新 agreement_ack；未受影响成员也不在本次提案确认范围，因此会被投影为 false。

与此同时，maybeApply 复制未修改分项、签署新版本份额并继续保持业务责任，造成“责任仍有效，响应却表示本人未接受”的不一致。

### 4.2 必须先构造的最小反例

使用三个不同成员，避免组长必须确认掩盖问题：

1. L 为组长/统筹责任人，A 负责 U1，B 负责 U2；B 不兼任统筹责任人。
2. 创建约定 V1，相关人员完成有效接受，使 V1 生效。
3. GET V1，确认 U1/A 与 U2/B 的 accepted 均为 true。
4. 只修改 U1 的责任依据，提案受影响者包含 L、A，不包含 B。
5. 按真实流程确认提案，产生 V2。
6. GET V2：U1/A 接受来自本次确认；U2/B 的责任未变，应保留有效接受。
7. 修改前验证当前实现将 U2/B 返回 false，同时数据库中该责任仍按有效版本保留。

不要通过给 B 人为补一条本次提案确认来让测试通过，那会改变反例条件并伪造不需要发生的业务操作。

## 5. V02：按分项与份额追溯接受来源

### 5.1 目标规则

判定维度至少是目标约定 + 分项 + 用户份额，而不是全任务一个 userId 集合。

|场景|判定要求|
|---|---|
|目标约定有本人有效直接 ACCEPT|按该接受实际覆盖范围判断|
|目标版本由已生效提案产生，份额属于本次受影响范围|使用对应提案、基础版本和用户的有效确认|
|分项及份额未受本次变更影响|追溯此前仍有效的本人接受，不能因未参与此次确认而变 false|
|新增份额、换责任人、改变点数/责任或其他需重确认依据|必须使用适用的新接受，不能沿用失效来源|
|某用户同时参与多个分项|逐分项判断，一处确认不自动证明另一处改变后的责任已接受|
|目标处于待确认或被要求修改状态|不得因未来版本已接受而倒填目标版本|

“未受影响”的范围不能只通过比较 userId 或 points 得出。需要结合业务规则核对责任说明、截止、验收标准、分项内容及其他触发确认的依据，并优先使用生成该版本时保存的提案变更集合。

### 5.2 实现步骤

1. 盘点 agreement、plan JSON、agreement_ack、unit_change_proposal、proposal response 及相关快照，明确可可靠追溯的关联。
2. 以目标约定为起点，通过实际来源提案的 baseAgreementVersion 或明确前序关系追溯，不能直接取任务“最新 ACTIVE 约定”。
3. 对本次修改过的分项/份额检查对应新确认；对未修改部分继续沿前序来源寻找有效接受。
4. 不按“版本号减一”盲目找前序：中间可能有 PENDING、CHANGES_REQUESTED、SUPERSEDED 或其他未生效版本，应依据实际来源链。
5. 遇到拒绝、撤回、重新分配或需要重新确认的实质变更，停止错误继承，按真实状态判断。
6. 连续多次局部调整时，允许未变份额沿多级来源链保留接受，不只处理上一版。
7. 将来源计算集中为可测试的组件/方法，避免 agreementView 中再堆一个全用户集合。
8. 用批量查询和缓存同次请求已解析的来源节点避免 N+1 查询；检测缺失或循环来源，不能无限递归。
9. 若现有数据不能可靠表达来源，可新增明确的接受依据关联或快照，但只能保存真实来源，不能制造用户当时并未提交的 agreement_ack。
10. 投影与业务责任规则保持一致，但不得通过改写业务签署状态反过来“修正”响应。
11. 保留当前成员读取权限，来源追溯不能扩大人员材料或历史私人数据访问。

### 5.3 测试矩阵

- 单次局部调整：未受影响 B 保持 true。
- 连续 V1→V2→V3 局部调整：未变份额能够正确继承最初接受。
- 同一用户参与多个分项：修改范围与接受范围独立。
- 新增用户、换用户、变更责任/点数/截止/标准：未满足确认前不能显示 true。
- 待确认或拒绝场景不能借未来接受变 true。
- 新旧约定分别 GET，来源按各自版本解析。
- 所有 GET 前后 agreement_ack、response、unit_share、任务状态及版本无变化。
- 用户离组后 GET 和历史回放继续拒绝。

### 5.4 验收标准

每一个 true 都能追溯到本人实际接受及适用责任依据；false 不能仅因为未参与一次无关调整而产生。不能统一填 true，也不能回退为 signed。

## 6. V03：历史交接约定不能读取当前验收安排（P2）

### 6.1 代码位置与问题

`delivery/DeliveryService.reviewerAcceptanceInherited()`，审查时约第 1392 行：

```java
ArrangementRow arrangement = deliveries.arrangement(agreement.taskId()).orElse(null);
```

随后使用该当前 arrangement 的 userId/kind 匹配历史验收。但同一响应的 reviewerPolicy 来自目标 agreement.planJson。

因此，后续新约定改变任务验收安排后，再读取旧交接约定，会出现历史 reviewerPolicy 与当前安排计算的继承标志不一致。

### 6.2 先建立反例

1. V1 使用验收人 R1 和指定 kind，存在真实符合条件的验收记录。
2. 经真实交接产生 V2，V2 的安排仍为 R1，读取并记录 reviewerPolicy 和 reviewerAcceptanceInherited。
3. 再按合法流程产生后续约定，将任务当前安排改变为 R2 或另一 kind；不修改 V2 的计划。
4. 重新 GET V2，要求仍按 V2 自身安排和适用来源判断，不能因任务当前安排已变而翻转。
5. 对照新约定 GET，确认新版本使用自己的安排，不能反过来冻结整个任务在旧安排上。

如现有业务不允许某种具体后续变更，使用合法可达的替代流程；不能为了造反例绕过关键业务约束后宣称真实路径一定可达。数据层不变量测试和完整 API 流程测试分开记录。

### 6.3 修复步骤

1. 明确该字段的业务语义及目标版本：以主契约为准，不把“验收人接受安排”与“成果验收通过”未经核对地混为一类事实。
2. 使用目标约定固定的 reviewerPolicy，以及能证明属于该目标约定的安排/接受/继承来源。
3. 不再以任务当前 reviewer_arrangement 作为历史目标的唯一依据。
4. 按目标版本过滤候选验收/安排记录，核验 taskId、unitId、submissionId、agreementVersion、来源人员变更及其他适用关联。
5. 后续版本新产生的记录不得倒灌到旧约定；只比较 submission.agreementVersion 的数字大小并不自动证明完整继承资格。
6. 按实际规则检查允许继承的分项范围和验收安排，不能“任意旧分项有一条通过”就无条件把整个约定标为 true；如字段的聚合语义不明确，记录契约位置并先核对。
7. 新约定生成时若需要固定继承事实，在同一业务事务中保存可追溯依据；不能在 GET 时补写。
8. 旧记录缺少来源时，按可证明数据恢复；无法证明的情况使用明确兼容策略并登记，不拿当前安排猜测。
9. 普通约定不适用的条件字段仍按契约省略，不为统一 DTO 强行填 false。

### 6.4 测试矩阵

- 读取旧交接约定，后续更换验收人后再次读取：历史依据不串版。
- 后续改变 kind：同样不污染旧结果。
- 新增未来验收：不能倒填旧目标的继承事实。
- 没有合格旧记录：不能伪造 true。
- 来自其他任务、分项或不适用提交的验收不能参与匹配。
- 响应 reviewerPolicy 与继承计算使用同一目标版本依据。
- 旧约定 GET 不写数据库、不修改当前安排。
- 当前权限失效仍拒绝，不因属于历史记录而放行。

## 7. V04：历史数据与幂等回放兼容

前六轮已维护旧 plan 包装、第五轮顶层结构、第六轮完整结构三类回执。本轮不能为了新的来源计算把历史结果重算成当前状态。

### 步骤

1. 明确区分 GET 当前/指定约定投影与原写入结果的幂等回放。
2. 已完整保存的回执返回当次结果，在返回前复核当前访问权限。
3. 缺少新字段的旧回执按既定兼容策略处理；只有适用的历史证据可以补，不读取随后发生的新接受或新验收。
4. 若新增持久化来源字段，迁移只回填可证明的关系。不可恢复项有数量、影响和处置记录，不能批量签出 ACCEPT。
5. 不改 V001～V028；新迁移从实施时最大编号后追加。
6. 同一事务中保存新约定与来源依据，失败回滚；不出现约定已生效但来源未保存的半完成状态。
7. 回放不追加约定、确认、验收、贡献、移人或 outbox。

### 必测

- 三类历史回执不产生非预期反序列化错误。
- 原操作之后又发生局部调整/验收安排变更，旧键回放仍是原操作结果。
- 同键异正文冲突，离组后回放拒绝。
- 迁移前旧数据在升级后不会变成虚构已接受或虚构已继承。
- 新库和旧库升级均通过，已有时间证据和验收历史不被改写。
