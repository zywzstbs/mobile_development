## 5. Q01：帮助导入与响应结构一致（P1）

### 代码位置与问题

- `support/HelpCatalogImportService.java`：Article 输入、validate、classify、same、upsert，审查时 upsert 约第 147 行。
- `support/HelpSupportService.java`：articleView、published、contentPack。
- V023 引入的帮助结构化字段，V024 引入的包版本。

导入仍主要写旧 body/summary，而新接口从 steps_json、outcomes_json、failure_action、entry_json 等字段返回内容。结果可能是新导入文章步骤为空，或旧文章正文与包版本已变但客户端步骤仍旧。

### 修复步骤

1. 列出导入输入、数据库列、HELP 响应字段的映射表，明确每个字段的真实来源。
2. 选择完整的导入适配策略：升级受控导入格式为结构化内容，或为旧格式建立明确、无损且经验证的转换规则。
3. 不用截断 body 到 500 字等方式假装完成转换。旧正文无法满足新 steps 等约束时，应在 dry-run 给出具体记录和原因，要求转换输入，不生成虚假步骤或页面入口。
4. 新建与更新都同步写入客户端实际读取的结构化列；旧兼容列如仍保留，明确其派生规则，避免两套正文不一致。
5. 扩展 validate、classify、same，比较全部会影响响应的结构化内容。不能结构化正文已经改变却判为 UNCHANGED。
6. 输出内容变化时，在同一事务内推进条目 contentVersion、revision 和适用的通用包版本；不变导入和 dry-run 不推进。
7. published/audience/appVersionRange 等影响可见集合的变化继续更新包版本，保留第三轮修复。
8. 检查已通过旧导入产生的数据。对空结构或旧结构制定有依据的修复办法；不能覆盖人工通过 HELP-05 编辑出的新内容。
9. 导入和在线编辑之间使用明确的并发控制，避免无条件 upsert 覆盖较新的在线编辑。按现有导入契约制定版本冲突策略。
10. 更新受控样例、导入说明和测试夹具，不只改 SQL。

### 必测用例

- 新导入文章后，通过 HELP 详情和内容包读取，正文步骤及其他字段与导入内容一致。
- 修改一篇旧文章正文后再导入，HTTP 返回新内容，不继续返回旧 steps。
- 仅改结构化字段也应被识别为变更，条目及包版本正确推进。
- 完全相同输入重复导入：不重复推进版本。
- dry-run 不写条目、不改包版本。
- 旧格式过长或无法转换时明确拒绝，不静默截断。
- API 编辑后再导入旧文件，不无提示覆盖新的内容。
- 导入失败回滚条目及包版本，不能只提交其中一方。

### 完成标准

导入后的真实 HTTP 内容、持久化结构和包版本一致；测试不能仅断言行数或版本变化。

## 6. Q02：创建接口不能绕过请求级幂等（P2）

### 代码位置与反例

`support/HelpSupportService.java`：createTicket（约第 220 行）、report（约第 526 行）。

当前在进入 IdempotencyService 之前，查询 clientRequestId；若存在且摘要相同就直接返回。这跳过了键格式、已有键与意图绑定等检查。

确定反例：先用 K1 创建记录 A，用 K2 创建记录 B；再用 K1 提交 B 的原正文。当前可能直接返回 B，而不是拒绝 K1 被用于另一意图。缺失或非法幂等键也可能在已有 clientRequestId 分支成功。

### 修复步骤

1. 删除幂等服务之前返回成功结果的业务防重捷径。
2. 按统一规则先验证请求级 Idempotency-Key，并通过现有服务执行方法、路径、环境、用户及正文绑定检查。
3. 在幂等 action 的事务内处理 clientRequestId 业务防重：相同规范意图复用原业务记录，异意图返回业务冲突。
4. 对新幂等键命中旧业务记录的情况，保存该键与本次意图及结果的绑定，不重复创建业务记录。
5. 保留数据库唯一约束和并发冲突后的摘要检查，不能仅依赖先查再插。
6. 回放继续核验当前访问资格，返回语义与原操作一致，不将后来更高版本自动当作原操作结果。
7. 区分幂等记录保留期与业务唯一性：即使短期回执清理，clientRequestId 仍不能产生第二条业务记录。
8. 规范化遵守项目 CanonicalJson 策略，不为了通过测试随意删除字段、trim 密码/token 或忽略业务范围。

### 必测用例

- A/K1、B/K2 已存在，K1 + B 正文：IDEMPOTENCY_KEY_REUSED，不返回 B。
- 已有 clientRequestId，缺失或非法键：按统一规范拒绝。
- 原 key/body 重试：只有一条记录，返回正确结果。
- 新 key + 同 clientRequestId/同正文：复用原记录且绑定新键。
- 新 key + 同 clientRequestId/异正文：业务防重冲突。
- 两个不同 key 并发提交同 clientRequestId：只有一条记录，结果可核对。
- 两个同 key 请求竞争：依现有机制返回原结果或进行中，不重复写入。
- 回执过期后重试不重复创建。
- 求助和举报两条路径分别覆盖，不能只测试其中之一。

### 完成标准

请求幂等与业务唯一性均成立，任何成功分支都不能跳过请求键验证。

## 7. Q03：举报创建必须有本范围真实接收者（P2）

### 代码位置与问题

`support/HelpSupportService.report()`，审查时约第 537 行，使用 hasOperator 判断系统是否存在任意举报处理授权。

处理动作已使用 ContentReportAccess 按广场核权，但创建没有应用相同范围。系统只有课程 A 处理者时，课程 B 仍可能创建成功，实际上无人有权受理；停用账号的授权也可能被存在性判断计入。

### 修复步骤

1. 在 Q02 的幂等 action 内核验举报来源权限、版本和选中片段，并取得可信 squareId；不能相信请求自报范围。
2. 建立与 ContentReportAccess 一致的“是否存在当前合法接收者”查询或服务，复用能力和范围规则。
3. 接收者必须账号有效、授权当前有效且覆盖来源范围；GLOBAL 与 SQUARE 语义保持一致。
4. 延续已记录的 CONTENT_REVIEW/CONTENT_REPORT_HANDLE 兼容决定，但旧能力不能被自动提升为全局范围。
5. 来源无课程范围或历史范围不可追溯时，按现有明确规则处理，不能随意匹配某个 SQUARE 授权。
6. 无接收者返回 REPORT_ROUTE_UNAVAILABLE，事务不产生举报、处理历史或成功回执。
7. 查询与创建处于可靠事务边界；梳理接收资格变化竞争，保证创建成功时有明确依据，不将未来可能有人处理当成当前可受理。
8. 原本已成功的请求按幂等及当前读取权限恢复，不因后来暂时无人接收而重建记录或伪造失败事实。
9. 如果系统采用池式领取，不要求无依据地提前指派具体负责人，但必须存在实际可领取的合法人员。

### 必测用例

- 只有 A 范围处理者，创建 B 范围举报：REPORT_ROUTE_UNAVAILABLE，无新记录。
- 存在覆盖 B 的有效处理者：正常创建。
- 只有停用账号、撤销授权或不匹配范围授权：不能创建。
- 有效 GLOBAL 授权按规则覆盖对应来源。
- 无 squareId 来源不能被不相关 SQUARE 授权接收。
- 原请求成功后路由条件改变，原键重试不产生第二条记录。
- 失败时数据库无举报或处理历史增量。

### 完成标准

创建时的受理可用性与后续实际处理权限使用同一套事实，不产生明确无人可处理的虚假成功。

## 8. Q04：匿名帮助遵守列表分页契约（P2）

### 代码位置与问题

`support/HelpSupportService.articles()`，审查时约第 97 行。匿名分支直接 ListEnvelope.full(rows)，忽略 limit，提供 cursor 时直接报过期。

同一接口登录和匿名的分页行为不一致，匿名 limit=1 仍可能返回全量，规模增长后可能超出响应上限。

### 修复步骤

1. 对照 HELP-02 及通用分页规则，确认 limit 默认值、范围、排序、total 和游标期限。
2. 匿名仅允许 GENERAL；课程帮助继续要求当前身份和课程资格，不能因分页改造放宽。
3. 为匿名公共数据建立明确的游标主体/范围策略。匿名没有用户 ID，不能伪造 app_user 或把任意登录用户 ID 当主体。
4. 设计匿名游标不能被当作登录课程游标使用；在 scope、筛选摘要和适用身份上明确隔离。
5. 首次查询固定匹配 ID 和顺序，续页保持快照，按契约处理撤下记录和新发布记录。
6. 验证 limit 在 1～100，默认 20；非法值即使匿名也拒绝。
7. nextCursor、hasMore 和 total 反映真实快照，不把本页长度当 total，不截断后伪报无后续。
8. q、role、appVersion、范围或排序变化不得复用原游标。
9. 如果复用 CursorService 需要持久化结构改变，使用新增迁移；不能用空用户 ID 绕过数据库约束。
10. 保留请求/响应大小限制，分页不是取消字段上限或过量返回的理由。

### 必测用例

- 至少 25 条可见通用帮助，匿名默认请求返回 20 条并有续页。
- limit=1 正确分页，遍历结果无重复或遗漏，total 为完整匹配数。
- limit=0、101 或非法类型被拒绝。
- 有效匿名 cursor 可以续页；过期 cursor 返回契约错误。
- 改 q、role、appVersion 后复用游标被拒绝。
- 续页前新增文章不插入旧快照；撤下文章不泄露。
- 匿名 cursor 不能用于课程范围或冒充登录主体。
- 匿名访问 COURSE 拒绝，已授权登录用户的原分页仍正常。

### 完成标准

匿名和登录公共帮助遵守相同分页语义，同时保留匿名与课程数据的访问边界。
