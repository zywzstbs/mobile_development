## 4. T01：禁止跨课程覆盖帮助条目（P1）

### 位置与触发方式

`support/HelpSupportService.java` 的 `updateArticle()`，审查时约第 147～181 行。

现有代码锁定原条目后，只根据请求里的 `article.squareId` 检查教师资格；只禁止 GENERAL/COURSE 之间切换，没有比较原 squareId 与请求 squareId，并会更新数据库 square_id。

反例：课程 A 的教师使用课程 B 的帮助条目 ID，将请求 squareId 填成 A。当前逻辑可能允许其覆盖 B 的条目并改归属为 A。

### 修复步骤

1. 根据数据库原条目确定 scope/audience 和 squareId，不从客户端请求决定原资源权限。
2. GENERAL 原条目要求当前有效 HELP_CONTENT_WRITE；COURSE 原条目要求原课程的当前教师资格。
3. 普通编辑不承担课程迁移功能：请求 scope、squareId 必须与原资源归属一致。null 与非 null 的关系也明确校验。
4. 在同一事务内锁定原条目、核验当前权限、比较版本、更新内容和版本。
5. 无权调用者不应通过版本冲突等详细结果探测其他课程记录；按照项目统一错误策略安排核权和版本检查顺序。
6. 如发现历史 scope/audience 不一致，按真实来源修复并登记，不能依据请求悄悄重写归属。
7. 后续 T03 的幂等回放也必须根据原资源当前归属核权。

### 必测用例

- A 教师修改 B 条目，squareId 填 A：拒绝。
- A 教师修改 B 条目，squareId 填 B：拒绝。
- B 当前教师修改 B 条目、范围不变：成功且版本只增加一次。
- 请求 GENERAL/COURSE 相互切换、课程变 null 或 null 变课程：按契约拒绝。
- 教师授权解除后，原有编辑请求及回放均不能继续读取受限结果。
- 所有拒绝场景中原 title、正文、square_id、revision、content_version 不变。

### 完成标准

客户端无法借请求 squareId 改变核权对象；没有未经契约定义的帮助条目迁移入口。

## 5. T02：举报撤权后的读取控制（P1）

### 位置与触发方式

`support/HelpSupportService.java` 的 `reportDetail()`，审查时约第 596～607 行。

目前只判断 reporterId 或 assigneeId。负责人处理能力被撤销后，assigneeId 未变，仍可获取 selectedExcerpt 和 handlingNote。

### 修复步骤

1. 区分举报者读取本人记录与处理者读取指派记录，两条分支不能混淆。
2. 处理者分支检查账号当前有效、当前有效举报处理能力、适用范围以及真实指派。
3. 检查现有 CONTENT_REVIEW 与 CONTENT_REPORT_HANDLE 的兼容策略；旧能力不能自动等价为不受限制的全局授权。沿用有依据的授权映射，歧义单独记录。
4. 为举报建立一致授权入口，覆盖详情、处理动作、相关列表及回放；不要直接复用面向求助工单的资源类型或业务判断。
5. 特别检查 handleReport 的幂等资源引用：当前使用 SUPPORT_TICKET 携带举报 ID。梳理该引用的存储、清理及核权用途，再按实际举报资源修正，不能仅改字符串而忽略消费者。
6. 写入在锁定举报记录后再次验证当前能力和指派，避免只在事务外检查。
7. 任何授权不足都不返回原始片段、处理说明或其他受限材料。

### 必测用例

- A 已指派，撤销 A 的处理能力但保留 assigneeId；GET 详情拒绝。
- A 的能力范围不覆盖该举报，拒绝。
- B 有能力但未被指派，不能读取详情。
- 举报者仍可按契约读取本人允许的投影。
- 同键重放处理动作时重新核权，撤权后不返回受限缓存。
- 账号停用、授权失效等条件不能仅凭历史指派绕过。

### 完成标准

历史负责人字段不再单独证明访问权，所有相关入口核权一致，拒绝动作无状态或历史增量。

## 6. T03：帮助编辑和反馈接入持久幂等（P2）

### 位置与问题

`support/HelpSupportController.java` 的 HELP-04/HELP-05，审查时约第 54～68 行；对应 Service.feedback/updateArticle。

两个入口没有读取并使用 Idempotency-Key，直接修改数据库。编辑成功响应丢失后，原请求重试会因旧 expectedRevision 冲突，无法恢复原结果；反馈同键改正文也未按幂等契约拒绝。

### 修复步骤

1. Controller 按项目惯例接收 Idempotency-Key 和规范请求路径。
2. Service 使用现有 IdempotencyService，绑定用户、环境、PUT 方法、规范路径和完整正文。
3. 当前资源核权、业务更新、版本递增与回执提交保持可靠事务边界。
4. 成功回放前重新执行 T01 的当前权限判断；正常回放不重新应用 expectedRevision 更新。
5. 相同键与相同正文恢复原操作结果；同键不同正文返回幂等冲突。
6. HELP-04 保留按本人/条目/正文版本的业务唯一性；业务 upsert 不能替代请求幂等。
7. 首次有效请求仍验证反馈正文版本。先前成功请求的回放不能因为当前正文后来更新就被错误地当作一次新提交执行。
8. 不为历史未记录幂等的写入伪造回执；记录升级边界及可能无法恢复的旧请求。

### 必测用例

- 编辑成功后模拟响应丢失，原 body/key 重试返回原结果，revision 和 contentVersion 不再增加。
- 同键修改标题、正文、版本、scope 或 squareId：冲突且无写入。
- 反馈同键同正文不产生新业务动作；同键 helpful/reasonCode 改变：冲突。
- 不同键的合法新反馈按业务约束更新，不被错误锁死。
- 授权撤销后回放被拒绝；跨课程无权调用不能取得历史结果。
- 缺失或非法幂等键按统一规范拒绝。

### 完成标准

请求级幂等和业务唯一性都成立，失败恢复不重复修改业务，也不暴露失权结果。

## 7. T04：修复帮助内容包版本漏更新（P2）

### 位置与反例

`support/HelpSupportService.java` 的 `contentPack()`，审查时约第 74～81 行。

当前 version = 所有匹配条目的 max(contentVersion)。若 A 版本 10、B 版本 1，B 更新为 2 后 max 仍是 10。客户端发送 knownVersion=10 时拿到空 articles，无法发现 B 更新。新增低版本条目、撤下非最高版本条目也可能不改变包版本。

### 修复步骤

1. 盘点所有影响通用帮助包内容的写入路径：API 编辑、受控导入、发布/撤下、删除或维护操作、适用版本和角色等过滤字段变化。
2. 采用持久化的包版本机制，确保发布集合或其输出内容改变时版本可区分；不再取单条版本最大值，也不使用不稳定的当前时间或有碰撞风险的随意整数散列。
3. 保持主契约规定的 version 类型，不自行改成字符串摘要或新增客户端必填参数。
4. 明确 appVersion 等筛选维度与 knownVersion 的使用边界。可以采用全局单调版本使相关修改统一失效，但请求参数变化后客户端需按契约重新取全量，不能混用不同筛选缓存。
5. 内容更新和包版本推进在同一事务内完成。包版本与本次 articles 读取保持一致快照，不能返回“新版本+旧内容”，使客户端长期不再更新。
6. 并发编辑不丢版本推进；幂等回放不再次推进包版本。
7. 所有受控导入/维护入口同步推进版本，避免只修 API 编辑。
8. updatedAt 对应真实包变更，不取按 ID 排序的第一篇文章时间，也不在空集合时用当前时间假造变更。
9. 设计旧库初始化方案。新包版本不能与旧客户端缓存的 max(contentVersion) 意外相等而误判未变；根据历史可取得的版本范围或明确的缓存失效策略处理，记录依据。
10. 如需新表或列，通过新增迁移实现，并验证空库及已有数据升级。

### 必测用例

- A=10、B=1，B 改为 2：knownVersion=旧值请求能获取变化。
- 新增低版本文章、撤下一篇非最高版本文章：能获取变化。
- 改适用版本导致文章进入/退出集合：刷新正确。
- 无变化同参数请求：按契约返回未变化结果。
- 两个编辑并发完成后，版本可反映最终内容；无丢更新。
- 编辑回放不重复推进版本。
- 写入失败时包版本不单独提交。
- 包读取与编辑并发时，版本和内容一致。
- 空集合以及旧缓存升级不会错误地永久维持陈旧内容。

### 完成标准

所有可见内容变化都能通过版本机制被客户端发现；包版本、内容与更新时间一致且可追溯。

## 8. T05：限制举报状态转换（P2）

### 位置与反例

`support/HelpSupportService.java` 的 `handleReport()`，审查时约第 625～646 行。

目前直接把 ACCEPT 映射为 IN_PROGRESS、RECORD_RESULT 映射为 HANDLED、CLOSE 映射为 CLOSED，没有验证原状态。已关闭记录的负责人可以提交新的 ACCEPT 或 RECORD_RESULT，使其回到处理中或已处理。

### 修复步骤

1. 从 REPORTING-04 及主契约状态规则列出“原状态—动作—目标状态—身份”矩阵。
2. 契约未明确的边界动作不要自行扩展，尤其不能借普通处理动作创建重开能力。
3. 在行锁和当前版本验证下检查允许转换，再更新负责人、状态、版本、处理记录。
4. CLOSED 不允许通过普通动作离开终态；HANDLED 是否允许补充结果等细节以契约为准。
5. 同键成功回放恢复原结果而不再次执行状态转换；新键的重复或非法动作按契约处理。
6. ACCEPT 的认领检查、当前能力和指派范围使用 T02 规则。
7. 失败时不得新增 report_handling、递增 revision 或更换 assignee。

### 必测用例

- CLOSED + ACCEPT、CLOSED + RECORD_RESULT：拒绝，状态保持 CLOSED。
- 未指派、未接受的记录尝试直接写结果，按明确矩阵验证。
- 正常受理、记录结果、关闭链路符合矩阵。
- 同键关闭重试不新增历史；新键非法关闭不伪造额外处理事实。
- 两个操作竞争同 revision，只有一个成功。
- 撤权处理人尝试转换状态，拒绝且数据不变。

### 完成标准

所有状态转换都有原状态条件，终态不被普通动作重开，并发与重试不产生矛盾历史。
