## 4. R01：撤权后的工单与文件访问控制（P1）

### 问题与定位

- `support/HelpSupportService.java`：`canRead()`，审查时约第 953 行。
- `requireParticipant()`、`requireReadable()`、回复与其他处理动作。
- `file/FileRepository.java`：`supportTicketVisible()`。
- `file/FileService.java`：SUPPORT_ATTACHMENT 上传资格、元数据、下载授权及实际下载路径。

当前主要根据 requesterId 或 assigneeId 判断访问。处理人的 SUPPORT_HANDLE 被撤销后，只要 assigneeId 未改变，仍可能读取工单、回复或图片。受理资格必须是当前事实，不能由历史指派字段单独证明。

### 修复步骤

1. 梳理提问者与处理者两条授权分支，不能让提问者读取本人工单也必须拥有 SUPPORT_HANDLE。
2. 建立统一的当前工单权限判定组件，避免 support 与 file 各自维护不同规则。
3. 处理者分支同时检查：当前有效身份、有效能力、实际指派、适用范围；课程或助理权限按主契约核对期限和回避规则。
4. 接入详情、回复列表、处理动作、候选转交、工作台、附件上传、文件元数据、下载授权、实际字节下载及幂等回放。
5. 写入在事务内再次核验；不要只在进入事务之前检查一次。
6. 文件字节端点不能只凭短期 token 放行，应从授权记录中的用户重新检查当前资格；已失效身份同样不能继续下载。
7. 对历史指派存在、当前授权不存在的记录拒绝访问，不为恢复访问自动授予能力。

### 必测反例

- A 是工单处理人，撤销 A 的 SUPPORT_HANDLE，保留工单 assigneeId。
- A 读取详情、回复、元数据、申请下载、使用撤权前下载 URL、提交回复或处理动作，均应按契约拒绝。
- 提问者仍可按契约访问本人工单，不能被处理者撤权误伤。
- B 有 SUPPORT_HANDLE 但未指派到该单，不能读取。
- 课程授权过期或范围不匹配不能继续访问。
- 转交后旧处理人失权，新处理人在当前资格有效时可访问。

### 验收标准

所有入口使用一致授权事实；权限拒绝后无回复、历史、版本、附件引用或 outbox 增量。

## 5. R02：禁止转交后的失权幂等回放（P1）

### 问题与定位

`support/HelpSupportService.java` 的 `mutate()`，审查时第 667～668 行：缓存包含 transferTargetRouteId 且调用者已不能读取时，直接返回 cached。

这正好绕过了失权检查。转交后的旧处理人能够用原键取回旧工单内容。

### 修复步骤

1. 删除“已失权所以返回缓存”的特殊放行分支。
2. 所有历史成功回放都执行 R01 的当前权限检查，不能只检查账号仍有效。
3. 保留首次成功转交的动作响应：该响应在有效授权的动作事务中构造，允许返回契约定义的本次结果。
4. 首次转交成功后，不要再调用要求旧处理人仍有详情资格的 GET 投影方法，否则可能错误回滚转交。
5. 后续重试是新的回放请求，已失权时应拒绝，不以“解决未知结果”为理由暴露缓存正文。
6. 拒绝回放不得删除回执、撤销转交或重复生成历史。

### 必测反例

1. A 转交给 B，保存原 body/key。
2. A 随后 GET 工单被拒绝。
3. A 使用原 body/key 重试转交，同样不能获取工单正文或缓存结果。
4. 数据库仍只有一次转交，负责人为 B，版本和历史不重复增长。
5. 模拟首个响应丢失后 A 重试，结果遵守当前权限；不能假造第二次成功。
6. 新负责人仍有权限时，正常查询不受影响。

### 验收标准

首次动作响应与后续回放权限明确区分；不存在失权缓存特例。

## 6. R03：约定历史幂等结果兼容及回放核权（P1）

### 问题与定位

- `delivery/DeliveryService.java`：`writeAgreement()`，审查时第 1485～1494 行。
- `common/idempotency/IdempotencyService.java`：先 deserialize，再调用 replayProjector。
- `common/config/JacksonConfig.java`：开启 FAIL_ON_UNKNOWN_PROPERTIES。
- `delivery/DeliveryViews.java`：AgreementView 已从 plan 包装改为顶层字段。

旧缓存带 plan，新 DTO 不接受该字段。当前代码需要先反序列化为新 DTO 才进入兼容回调，因此可能在兼容逻辑之前失败。

另外，`findAgreement(cached.id()).orElse(cached)` 在找不到约定记录时只检查学生身份，交接续约返回其他业务 ID 的分支可能绕过项目核权。

### 修复步骤

1. 从旧版结构构造真实历史回执测试样例，保留原 plan、ID、状态、版本及时间，不用新结构伪装旧缓存。
2. 设计显式、受限的历史回执读取方式，例如按回执类型/版本解析为历史 DTO 或 JsonNode 后适配；不要全局关闭未知请求字段拒绝。
3. 在解析后先提取可信资源绑定，再检查当前项目/任务资格。
4. 普通约定、交接续约、资源已不存在等分支均显式处理，不使用无核权的 orElse(cached)。
5. 适配应保留原操作的结果身份、版本和快照语义。当前约定可能已被后续操作改变，不能直接把最新状态当成原操作结果。
6. 可以基于持久化历史快照补新协议字段，但必须有真实依据。不能补全的情况给出明确兼容处理，不能编造数据或重新执行业务。
7. 保留原幂等绑定与有效期，不通过清空回执解决。
8. 回归共用 IdempotencyService 的其他模块，避免公共改动影响聊天、防重和失权回放。

### 必测反例

- 升级前旧结构回执 → 升级后原请求重试，不出现反序列化 500、不重复写入。
- 原约定后续已更新，再重试旧操作，不能冒充返回后续操作的结果。
- 用户离组后重放普通约定动作被拒绝。
- 用户离组后重放交接续约分支也被拒绝。
- 同键不同正文仍冲突。
- 历史资源缺失不能未经核权返回旧内容。

### 验收标准

历史结果可按明确策略恢复；所有分支核权；操作身份不变；无重复成员、责任、版本或历史写入。

## 7. R04：通知预览的来源版本与范围绑定（P1）

### 问题与定位

`notice/application/NoticeService.java`：预览创建、`consumePreview()`（审查时约第 453 行）、实质修订。

当前预览未使用请求 expectedRevision，消费仅检查课程、本人、期限及已使用状态。旧预览可能与后来读取的新版本组合提交；同课程、同用户不能证明 token 对应本次来源与动作。

### 修复步骤

1. 先核对 NOTICE-03/05，明确各 expectedRevision 对应哪类资源，不能自行混用课程版本与通知版本。
2. 梳理现有请求是否足以识别修订目标；若契约不能表达目标绑定，明确记录最小契约缺口，不擅自添加必填字段或另造接口。
3. 在服务端预览记录中保存契约可确定的资源范围、来源版本、发布身份、固定参数和到期时间。
4. 提交时检查来源仍有效、请求与预览一致，不能用新的 expectedRevision 替换预览时的旧基准。
5. 核对标题、正文、assignmentId、类别、重要性、知悉要求、期限、引用及发布身份等全部适用参数，不能只比较文字。
6. 校验失败后不得执行正式动作；客户端需要重新预览，服务器不能自动生成新 token 并提交。
7. token 消费、通知正文版本、接收者快照、回执基线和 outbox 在可靠事务中完成；消费更新应防并发重复使用。
8. 保留排版修订与实质修订的区别，不能用 FORMAT_ONLY 修改范围或绕过预览。

### 必测反例

- 生成预览后来源发生变化，再以新版本号配旧 token 提交，被拒绝。
- 不同用户、课程或不匹配动作范围使用 token，被拒绝。
- 过期、已消费 token 被拒绝。
- 标题正文相同，但范围、身份或其他固定参数变化，被拒绝。
- 两个请求竞争同一 token，只有一次有效消费。
- 失败无新正文、快照、回执或 outbox；旧回执不能满足新正文。

### 验收标准

预览固定的是可核对的操作依据，不是仅校验文本的一次性通行证。

## 8. R05：解决合并计票字段的文档矛盾

此项是契约核对，不直接判当前代码错误。

P58 主文档第 9 节的合并响应使用 agreeCount/requiredCount，第 10.3 节描述 agree/requiredYes。第一轮方案沿用了后一种描述，不能据此要求执行模型机械改回。

### 步骤

1. 精确列出第 9 节、第 10.3 节、当前 MergeViews 和客户端读取位置的字段对照。
2. 若客户端源码可用，读取真实解析代码及规则测试；本仓库不可用时将其列为待确认事实，不假称已核对。
3. 根据确认的兼容契约统一维护源、生成文档、响应 DTO 和测试；维护源不在仓库时记录缺失，避免只修改生成文件造成下次覆盖。
4. 兼容双字段必须有明确决定，不能随意永久并存。
5. 无论字段名最终如何，验证有效选民数、同意/反对/弃权/未投、严格过半阈值和两侧独立判定。
6. 同步复核 RETURNED 等历史状态与 P58 状态集合的映射；保留真实退回事实，但不能未经说明把额外状态宣称为客户端已支持。

### 验收

字段和状态均有明确证据与统一结论；未确认项保留阻塞标记，不计为接口兼容通过。
