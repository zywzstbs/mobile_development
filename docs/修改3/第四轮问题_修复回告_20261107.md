## 2. T4-1 实现

### 2.1 日志先打开，失败不留进程

`Invoke-BoundedProcess` 与 `Start-ResidentProcess` 的执行顺序改为：

1. 打开 stdout 日志流；
2. 打开 stderr 日志流；
3. 启动进程；
4. 初始化两个异步复制任务；
5. 等待/返回。

第 2 步失败时，第 1 步打开的流由 `finally` 释放，进程根本没有启动，因此不会出现“子进程已启动、打开日志抛错、没人清理”的窗口。日志路径不可写、被独占或实际为目录时，都在启动前失败。

### 2.2 完整资源生命周期与自身进程树清理

两个函数把“打开日志 → 启动 → 复制初始化 → 等待 → 返回”整体放在 `try/finally` 中：

- 用 `$processStarted` 记录是否已 `Start()`，用 `$handedOff` 记录是否已把结果/句柄交给调用方；
- 短命令只有在确认进程已退出（正常退出或超时后已结束）时才标记交接完成；否则 `finally` 会再清理一次；
- 异常路径调用新增的 `Stop-OwnedProcessTree`，只对**本函数持有的那个 Process 对象**执行 `Kill($true)`，并有界等待 15 秒；不按进程名、端口或命令行筛选，不会误杀其它 PostgreSQL 实例或调用者的进程；
- 清理中的每一步（结束进程、等待复制任务、释放流、释放 Process）都单独 `try/catch`，因此清理失败不会覆盖日志打开失败、启动失败等原始异常。

### 2.3 常驻进程：成功返回后才转移所有权

`Start-ResidentProcess` 先完整构造返回对象（进程、PID、两个日志路径、两个日志流、两个复制任务），设置 `$handedOff = $true` 后才返回。失败路径（任一日志打开失败、启动失败、复制初始化失败）在 `finally` 中先结束自己启动的进程树，再有界等待复制任务、释放两个流和进程句柄；调用方拿不到半成品，也不会遗留日志句柄。

`Close-ResidentProcess` 相应增加一次有界的复制任务等待（2 秒），然后照常释放流与进程句柄；子进程继承句柄时仍不会被无限等待。

### 2.4 复制任务列表显式数组化

按审查要求改为：

```powershell
$pending = @(@($stdoutCopy, $stderrCopy) | Where-Object { $null -ne $_ })
if ($pending.Count -gt 0) { ... }
```

两个任务都为空时 `$pending` 是空数组而不是 `$null`，StrictMode 下访问 `Count` 不再抛 `PropertyNotFoundException`，不会再遮住原始日志错误、跳过释放逻辑。该写法同时用于短命令 `finally`、常驻失败清理和 `Close-ResidentProcess`。

### 2.5 确定性覆盖“启动后复制初始化失败”

新增内部函数 `New-ProcessOutputCopyTasks`（生产路径就是创建两个 `CopyToAsync` 任务，无测试专用参数）。自检脚本在局部匿名作用域覆盖该函数：先从传入的 `Process` 对象记录已启动的子进程 PID，再抛 `InvalidOperationException`，从而在真实进程已启动的情况下验证（不依赖子进程自身写文件的时序）：

- 原始注入异常原样抛出，未被清理异常替换；
- 子进程被结束；
- 两个日志流均被释放（用 `FileShare.None` 重新打开验证）。

短命令与常驻进程各有一条这样的用例。`Invoke-BoundedProcess` 原有“缺失 exe 抛错”断言也加强为：断言最内层异常仍是 `Win32Exception`、消息含缺失路径、两个日志文件已打开且句柄已释放。
