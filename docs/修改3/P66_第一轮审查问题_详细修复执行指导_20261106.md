## 4. 第1批：R1/R4 统一管理事务和恢复能力

### 4.1 要达到的事务性质

业务提交必须对应当前有效操作者授权。平台撤权/停用与管理写入必须有清楚的先后顺序：

- 若撤权先完成，后续取得执行资格的写入必须拒绝。
- 若业务写入先取得用于保护授权的锁并保持到提交，撤权可以等其提交后再执行。这是合法串行顺序，不要求将已经先行的事务追溯取消。
- 不允许撤权已经提交，仍利用之前抓取的 Access 继续新增权限。

当前仅在 A04/A16 使用 `platform_admin_lock`，A15 等路径不参加，形成缺口。审核回调还有“重新 require，但使用原 access 检查 school”的模式，须一起消除。

### 4.2 推荐方案：首期复用单行管理锁，统一串行化

当前管理写入规模有限，推荐所有实际管理写入共同使用已有 `platform_admin_lock` 单行排他锁，保持到事务提交。比在多类操作者/目标上临时拼凑锁更容易验证。

参加路径至少包括：

| 路径 | 必须处理 |
|---|---|
| A04、A08、A11、A12、A15、A16 | 在同一真实事务内取得管理锁后读取授权，再进行业务写入 |
| init-super-admin、未来受控授权修复 | 相同管理锁，再锁目标账号和授权 |
| AdminImportService | 在可能修改管理员账号/角色之前进入同一协议，整批原子 |
| 其他会修改平台角色、grant、capability、scope、账号可用性的受控工具 | 全仓搜索，记录并纳入；不得留绕行入口 |

不要把全部普通课程/聊天写入都挂到该锁上；只有能改变上述授权事实或相关受保护管理操作的路径需要参加。

建议统一顺序（实施时必须结合实际调用图确认）：

1. IdempotencyService 获取该 HTTP 请求的幂等锁。
2. 获取平台管理约束锁。
3. 新执行分支获取 actor+operationId 锁并查询已提交操作。
4. 未提交才锁定并校验本次再认证记录。
5. 按已有领域顺序锁业务资源，例如广场→认领/助理授权，注册申请→目标账号。
6. 更新业务、版本、审计、令牌消费和操作回执，原子提交。

CLI 没有幂等锁时从第2步进入。严禁“先锁用户/广场，再去拿管理锁”的反向路径。`IdempotencyService` 的新执行和回放都运行在事务里，可在管理调用专用 authorizationCheck 中取得管理锁并核权；不要把平台锁放入全局通用幂等服务，影响所有业务。

**以上是推荐最终顺序，不是对当前代码顺序的描述。** 当前在 verifyUnused 后才有条件拿管理锁，应整体统一；同步修改类注释。

其他方案如共享/排他 advisory lock 或精细授权行锁也可采用，但必须说明锁图、保护范围和两种竞争顺序，并通过相同数据库并发验收；只增加一次普通查询不合格。

### 4.3 授权读取与事务边界

- 锁外 require 仅可快速拒绝，不能作为提交依据。
- 锁内重新查数据库账号状态、SUPER_ADMIN 角色、有效 grant、能力、scope；`principal.roles` 是过滤器在请求开始时的快照，不能代替锁内事实。
- 取得新 Access 后，后续 school 检查必须用这个 Access；不要丢弃 require 返回值而继续使用旧对象。
- 检查当前会话属于操作者、未撤销且未过期。CurrentUserPolicy 当前只检查 principal 标记与账号，不是完整会话重读。需要补服务/仓储读取时保持作用域清晰。
- 正式写入需在资源锁后验证版本、状态、自审回避和目标范围；全局锁保护管理授权变化，不能替代领域资源锁和 CAS。
- 重新取得业务锁后再检查令牌期限，防止漫长等待跨过有效期仍执行；失败时不得消费令牌或留下部分操作。
- 事务方法必须经 Spring 代理生效或使用 TransactionTemplate；不要依赖同类自调用上的 @Transactional。锁不能在一个已返回的短事务中释放后再执行业务。
- 任何会话锁的新增都须核对 AuthService/SessionRepository 现有刷新、退出、撤销的锁顺序。不要为了修复平台竞争引入跨模块死锁。
- `lockAdminConstraint` 若没有读到单行，应明确失败，不能在锁行丢失时静默无锁运行；不要每次请求擅自重建锁行。

### 4.4 R4：统一“可恢复管理员”定义

建议提取平台恢复保护服务或统一仓储谓词，由 HTTP 与 CLI 共用。不能再让 isRecoveryAdmin 和 countRecoveryExcluding 各自维护不完整版本。

最低有效条件：

- 目标账号存在，account_status=ACTIVE 且 disabled=false。
- 当前有 SUPER_ADMIN 角色、ACTIVE 平台 grant。
- 有符合现有登录机制的密码凭据；不依赖是否此刻已经登录。
- 具备 ACCOUNT_MANAGE 和 SUPER_ADMIN_MANAGE 两项必要能力。
- 具备覆盖所需恢复范围的有效 scope。
- 资格条件与本系统有效管理员规则一致；例如现有授予要求 VERIFIED 和明确 eligibility，应明确哪些资格变化会使管理员不可用，不把残缺/已失效状态当作兜底。

首期推荐安全规则：**已有可用全平台恢复管理员时，任何减少可用性的操作都不能把其数量从正数变成0。** 多个学校管理员的并集也不能替代全平台管理员，因为当前 A15 没有把学校授权升级为 PLATFORM 的路径。

在已有全平台管理员保护下，单学校管理员可被撤销，其学校仍由全平台管理员覆盖。历史状态若已经没有可用全平台管理员，不自动补造：返回明确的需受控恢复状态，或只允许不恶化恢复能力的动作，并在契约/运维说明写清实际规则。空库首次初始化要有明确例外，不能被“至少已有一人”条件锁死。

校验必须位于管理锁内并针对操作后的有效集合：HTTP 单目标可排除目标计算，导入多目标必须评估整批最终状态。禁止逐项在锁外用旧总数做判断。

### 4.5 并发验收与旧探针的调整

原 R1 探针的顺序是“业务已等待目标锁 → 撤权提交 → 释放目标锁”。统一全局锁后，撤权会等待前一业务事务；原探针若仍等撤权返回才释放目标锁，会人为制造测试等待循环。

必须将其改为两组明确时序：

1. **业务先保护授权**：确认业务已持有管理锁且等待目标；发起撤权并确认它在等待；释放目标；业务先提交，撤权后提交。撤权后的新写入拒绝。
2. **撤权先提交**：让业务在保护授权之前等待，先完成撤权，再放行业务；业务返回无权限/会话失效，目标授权和审计不增加。

使用两条以上真实数据库连接、屏障/锁状态检测和有限超时；finally 释放屏障并终止线程。不要只靠 Thread.sleep 判断顺序。

补 A04/A16 混合竞争、两个管理员互停用/互撤销、不同幂等键同操作、撤权与审核/助理撤销等代表路径。每组验证最终角色、grant、账号、审计、操作行数及有效恢复管理员，不只验证状态码。

## 5. 第2批：R2 使 CLI 与平台授权一致

### 5.1 用户导入的职责边界

`AdminImportService` 当前删除用户全部角色，再从文件重建；parseRoles 又禁止 SUPER_ADMIN。修复时继续禁止文件声明 SUPER_ADMIN，但只重建普通业务角色，平台角色由平台授权服务管理。

建议做法：

1. 语法校验和密码编码等耗时工作可在事务外做，但账号/grant/恢复能力等状态必须在管理锁内重新确认。
2. 整批使用一个事务，先管理锁，再按稳定顺序锁受影响用户，之后再执行更新。
3. 平台资格正常时保留 SUPER_ADMIN；没有有效授权的孤立角色不能当正常权限保留并计数，明确报异常或交给受控修复。
4. 不能只保留角色却任意覆盖账号可用性。对已有管理员的 disabled、身份资格、凭据变化执行恢复保护；普通批量导入不得成为隐式提权或绕过管理员停用的入口。
5. 首期可明确拒绝普通导入修改现有管理员的敏感资格/凭据，要求使用受控工具；无敏感变化的重复导入应成功且保留平台资格。选择该策略时记录具体拒绝条件和错误，不静默忽略输入。
6. 若保留导入修改这些字段的能力，就必须共用最后管理者保护、资格状态转换和会话失效规则。不要将待审/驳回/管理员停用账号无条件改成 ACTIVE。
7. 输入密码相同但 bcrypt 等编码结果不同，不代表换密。若需区分，使用现有 PasswordEncoder.matches 对当前哈希核对，不比较新旧哈希文本，不输出密码。
8. 实际发生密码/敏感资格变更且该动作被允许时，撤销旧会话；恢复账号不能让旧会话复活。
9. 后置验证整批恢复能力与角色/grant 一致性，失败回滚全部学校/用户/角色/批次审计。

不要因为修复本问题就扩展成新公开管理员接口。测试所用 SQL 构造异常状态仅限隔离夹具，不是生产恢复方案。

### 5.2 初始化和恢复应明确区分

当前 `grantInitial` 找到 ACTIVE grant 就返回 already-active，应改成检查真实完整状态后才能这样返回。

| 数据状态 | 推荐行为 |
|---|---|
| 没有 grant，目标符合首次授予资格 | 原子创建授权、能力、scope、角色及审计 |
| grant/角色/能力/范围/账号都符合本命令承诺 | 幂等返回 already-active，不新增授权历史 |
| ACTIVE grant 存在但缺角色/能力、scope 不符合或账号不可用 | 显式冲突，不能报已正常初始化 |
| 只有 SUPER_ADMIN 角色却没有有效 grant | 不当作有效管理员，进入明确的异常处理 |
| dry-run | 只报告真实预期结果，不修复、不写审计或用户数据 |

本轮最低要求是显式冲突并给出恢复说明。若实现受控修复命令，单独定义允许修复的状态、可信 CLI 操作者、理由、事务与审计；不得把所有残缺 grant 自动补成七能力全平台，也不能将学校授权借初始化静默升级。

已有一致的 grant 重试保持同一授权 ID；修复历史保留可追溯记录。不要在应用启动时自动修复/提权。

### 5.3 CLI 必测

- 同一夹具重复导入，现有唯一超管仍可登录访问管理端，普通角色按原合同更新。
- 文件写 SUPER_ADMIN 明确拒绝。
- 最后全平台管理员被导入停用或降为不满足资格时，整批拒绝/回滚。
- 一个批次包含全部恢复管理员，不能因逐行看到另一旧管理员而把所有人停用。
- 有另一个有效全平台管理员时，允许或拒绝敏感变更符合明确策略；若允许，旧会话下一次请求/刷新不得复活资格。
- 角色/grant 不一致不计作有效恢复管理员，初始化不再假报 already-active。
- dry-run 不产生写入，真实失败不残留 import_batch 或部分用户更新。

## 6. 第3批：R3/R6 管理读取与隐私

### 6.1 R3：建立专用管理审计投影

当前 auditIds/auditsByIds/auditFrom 从整个 audit_event 读取，PLATFORM 范围仅用 TRUE；auditItem 原样输出 reason。修改目标是控制读出内容，**不是删除、截断或改写旧审计存储**。

建议由明确事件分类定义：允许公开的 action+resourceType、映射、真实目标范围解析、可返回的字段/理由策略。未知组合默认不进入管理列表；不能只判断 action 前缀或字符串包含某个词。

首批分类建议：

| 事件来源 | 管理投影处理 |
|---|---|
| 本轮账号状态、教师申请、认领、助理撤销、超管授撤 | 显式列入管理事件；逐项定义字段及理由可见条件 |
| 历史 REGISTRATION_APPROVE/REJECT、TEACHER_CLAIM_APPROVE/REJECT、CLASS_GRANT_REVOKE | 只有已知资源类型/目标关系匹配才映射；保留真实 CLI actor |
| SUPPORT_* / SUPPORT_TICKET | 默认不纳入本轮管理审计；不能因为有 AUDIT_READ 就返回工单理由 |
| PERSONNEL_CASE 等事项事件 | 默认不返回事项理由/正文；未来如需最小元数据另定权限 |
| CHAT/任务/成绩/文件等普通业务事件 | 不自动纳入平台管理审计 |
| 未知/无法确定真实范围的事件 | 学校范围拒绝展示；全平台也不能直接回原文，按明确分类处理 |

`PLATFORM_AUDIT_READ` 不等于 `PLATFORM_TEACHER_REVIEW` 或事项资格。即使是已允许的管理事件，教师审核 note、含核验材料的 reason 等仍需字段级处理。默认不回未经批准的原文；可返回空字符串或真实的脱敏摘要并在契约写清含义，不能用猜测文本冒充当事人的原始理由。不要用关键词替换正则当作可靠脱敏。

### 6.2 范围解析、分页和缓存必须一致

- 按 USER→用户学校、REGISTRATION→申请学校、TEACHER_CLAIM→广场学校、CLASS_GRANT→广场学校等真实关系计算。
- 平台授权事件同时考虑该 grant 的实际 scope，不能只因目标用户属于某学校，就将全平台授权事件当成该学校事件开放。
- 删除 `actor.school_id` 作为目标范围的兜底。跨校操作者和 CLI 并不能证明目标所属学校。
- 列表 ID 查询、total、hasMore、游标快照、按 ID 加载、总览 recentOperations 都使用一致分类与授权。只在 DTO 组装后过滤会泄露总数并破坏分页。
- 修复上线前已生成的游标可能保存全表 ID。为管理审计游标更换明确版本的 scope/query 标识，使旧游标失效；或对旧快照重新严格校验，不允许按 ID 加载绕过新规则。
- 不从异常中返回敏感 SQL 参数/理由原文。请求编号可以保留。
- `AdminAuditMapping.result` 当前只用包含 REJECT 来推断，其余都是 SUCCEEDED。对纳入的新白名单事件使用明确映射；不能把未知失败事件标成功。审核驳回动作与“请求执行被拒绝”的语义在契约中区分，避免随手改变前端枚举。

### 6.3 R6：总览必须按字段检查能力

原 A01 入口 ACCOUNT_READ 保留为基础资格，但不能据此获得所有计数/审计。

| 字段 | 最低所需能力/范围 |
|---|---|
| exceptionsPending | ACCOUNT_READ，当前账号管理范围 |
| teacherApplicationsPending | TEACHER_REVIEW，当前申请范围 |
| courseClaimsPending | COURSE_GOVERNANCE，当前课程范围 |
| recentOperations | AUDIT_READ，且使用6.1～6.2的安全审计集合 |

当前前端要求三个计数都是整数，尚无“无权/未提供”的字段级协议。推荐在现有协议下采用明确的保守策略：

- 缺少任一必填计数的读取能力，A01 返回 403 FORBIDDEN，message 明确说明总览统计权限不足；账号列表等已授权接口仍正常使用。
- 计数能力齐全、但无 AUDIT_READ 时，recentOperations 返回空数组，含义为“当前可见操作集合为空”，不声称全平台没有事件。
- 具备全部能力时返回真实计数和安全的最近操作。

这会使部分有限能力管理员无法打开完整总览，应同步记录为后端本轮策略和客户端兼容项；原交接已允许统计无权限时明确报错。不得偷偷把无权计数置0、缺字段或改 null。

若双方以后确认可选计数/availability 等新结构，可另行升级；本轮不虚构“前端已经支持”。修复模型无需等待该未来协议才能关闭当前泄露。

### 6.4 管理读取验收

1. 仅 ACCOUNT_READ 的账号：账号目录正常；A13拒绝；A01按上述策略拒绝，不泄露计数/targetId。
2. 有三种计数能力但无 AUDIT_READ：真实计数，空 recentOperations。
3. 有 AUDIT_READ、没有工单/事项权限：标记原文不会出现在 A13、A01或错误响应。
4. 同校操作者处理跨校资源：学校审计以真实目标范围拒绝，不按 actor 学校放行。
5. 平台/学校、CLI/HTTP、未知 action、合法空列表、多页混合敏感事件全部测试。
6. total/游标只反映可见集合，旧游标失效，按 ID 读快照不能绕过过滤。
7. 已允许的管理审计仍能追溯真实动作、目标、操作者和 UTC 时间；原表敏感历史未被删除。

## 7. 第4批：R5 两层回执按当前目标核权

### 7.1 区分三类校验

建议在 PlatformAuthorizationService 内或专用服务中拆分：

- 操作者当前资格：账号、会话、角色、有效 grant、动作能力。
- 当前目标可见范围：能否读取这个操作目标的最小回执。
- 新执行的业务前置条件：原 revision、PENDING/ACTIVE、禁止自授/自审、NO_ACTIVE_GRANT 等。

**回放只做前两类，不重新执行第三类。** 否则合法撤销后找不到 active grant、合法审核后不再 PENDING、新增授权后不再 NO_ACTIVE_GRANT，会让已经提交的操作永远无法核对。

当前 prepare 混合了目标与前置条件，不能直接放进回放回调。

### 7.2 两个回放入口都要覆盖

| 入口 | 当前位置 | 必须新增的行为 |
|---|---|---|
| 同 Idempotency-Key | IdempotencyService.execute 的 authorizationCheck | 按 command 目标检查当前作用域，再返回缓存回执 |
| 换键但同 actor+operationId | PlatformWriteService.commit 的 existing 分支 | 摘要一致后检查当前目标作用域，再返回 admin_operation 回执 |

若管理 authorizationCheck 同时取得第4章的管理锁，两层核权应复用一致逻辑。不要改全局幂等行为，保持其他业务原语义。

### 7.3 目标关系解析

| 动作 | 回执范围事实 |
|---|---|
| ACCOUNT_STATUS_CHANGE | 当前用户所属学校；允许目标现已 DISABLED |
| TEACHER_APPLICATION_DECIDE | 申请的真实学校和申请人关系；允许已决定 |
| COURSE_CLAIM_DECIDE | 认领对应广场学校；允许已决定 |
| ADMIN_GRANT_REVOKE | 已撤销授权仍保留的广场关系；不要求 ACTIVE |
| SUPER_ADMIN_GRANT/REVOKE | 用户范围，加实际被操作授权的 scope；不要求旧 grant 仍 ACTIVE |

超管授权可撤销后重新授予。不得简单 findActiveGrant(userId) 将旧操作套到新的授权。需要追溯原 grant 时，可从该操作的 auditId 对应的真实 PLATFORM_ADMIN_GRANT 资源确定，或保存明确内部资源引用；发现没有足够事实时明确拒绝，不能猜测。内部字段不足才追加迁移，不为修复随意改变前端回执形状。

沿用该动作所需平台能力并检查当前范围作为最小回执读取权限，不无理由额外要求另一项读能力，避免破坏原写能力合同。若决定要求独立读能力，必须在联合契约和测试中明确记录兼容变化。

目标不存在/已无权时不返回缓存内容。已提交操作仍需会话有效；操作者已被停用/撤权不能借旧回执绕过当前授权。

### 7.4 保持原幂等保证

- 相同业务、相同 operationId，无论原键或换键，只提交一次。
- 新旧 reauthToken 不改变业务摘要；成功回放不要求旧令牌未消费。
- 原目标版本后来变化，不导致仍有权的原回执读取失败；返回的是原操作结果，而不是伪造当前版本。
- 相同键/操作编号但业务摘要变化返回 IDEMPOTENCY_KEY_REUSED。
- 不因回放再次写审计、发通知、递增资源版本或消费另一令牌。
- 回放拒绝不改动已经提交的历史操作。

### 7.5 验收

覆盖原键和换键两条路径：操作者范围收缩、目标范围变化、撤权/停用、仍有权但版本变化、已撤销 grant、重新授予后读原撤销回执、令牌过期/已消费、换会话、内容冲突。

范围变化可以在隔离夹具中通过事务构造，须声明不是已有在线 scope 编辑 API。若模拟并发修改，应通过与产品相同的锁协议，不能用任意 SQL 绕过全部约束后声称事务方案无效。

| 组 | 必须验证的结果 |

复现文件中的5项要转化成安全断言：

- CLI：改为资格保留，或明确拒绝敏感输入且整批无变化。

- 回放：越权重试403，仍有权的重试成功。
- 最后全平台：危险操作409 LAST_ACTIVE_SUPER_ADMIN，状态不变。
- 竞争：按4.5改写屏障顺序，不能只把原200断言改403。

不要在正式 src 测试目录残留仍断言“漏洞成功”的临时探针。docs 中原探针保留为历史证据；新安全测试独立命名并说明覆盖哪个 R 编号。
