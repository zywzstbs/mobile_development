## 1. T3-1 / P1：Windows凭据文件没有落实私有访问权限

位置：`src/main/java/cn/gulupai/server/identity/cli/DemoSeedService.java:264–266`，调用点`:222–223`、`:255`。

本轮为解决Windows不支持POSIX权限而新增restrictToOwner，但在PosixFileAttributeView不存在时直接返回。这样虽然避免了UnsupportedOperationException，却跳过了“只有当前用户可读写”的保护。

writePrivate写出的是演示账号的明文登录口令，其中包含教师和运营账号。输出位置由`--app.cli.credentials-file`指定，不一定是用户私有临时目录。输出到继承了Users/Authenticated Users读权限的项目或共享目录时，其他本机用户仍可读取口令；对已有宽权限文件覆盖也一样。注释所说的“沿用系统临时目录默认ACL”不能保证调用者指定位置安全。

**本轮复现**：在`.tools/probe`下创建只含假数据的文件，显式给BUILTIN\Users READ_DATA权限，反射调用实际DemoSeedService.restrictToOwner后检查ACL：

```text
POSIX supported=false
BUILTIN Users read survives=true
```

未读取、输出或改变真实凭据。探针保存为[审查复现/P66ThirdAclProbe.java](审查复现/P66ThirdAclProbe.java)，须在已构建项目的运行时classpath下运行，参数使用可丢弃的假数据文件路径。该探针验证缺陷，不是安全验收。

DemoSeedIT本轮也只在支持POSIX时检查权限，Windows分支完全不检查ACL，因此全量通过没有覆盖此风险。

修复要求：

1. Windows使用AclFileAttributeView建立明确的私有ACL，处理继承和已有宽权限文件；非POSIX也无可用ACL时明确拒绝生成凭据，不能静默成功。
2. 在写入秘密之前建立权限。优先在私有目录中创建受保护临时文件再安全替换；不能先写明文再收紧，也不要在失败时遗留宽权限明文副本。
3. 确保凭据文件与包含原始口令的中间JSON都受保护；不修改整个项目目录的权限。
4. 保留Linux权限行为，并明确Windows允许保留哪些系统管理主体；不能因存在OWNER条目就忽略其他主体的ALLOW规则。

验收：Windows上分别覆盖新文件继承宽权限、已有宽权限文件、权限设置失败；普通Users/Authenticated Users不能读取口令，失败不遗留明文。Linux继续验证0600。测试使用假口令。

## 2. T3-2 / P2：正常pg_ctl启动路径仍会停滞，无法端到端运行脚本

位置：`scripts/run-pg-tests.ps1:372–373`及其后的就绪等待。触发条件：pg_ctl能正常启动，不进入“继承套接字错误”的直接启动回退。

本轮使用现有脚本、现有`.tools/pg17`和`-KeepData -MavenArgs @('verify')`复跑。沙箱内pg_ctl初始化失败，获准在沙箱外调用后工具版本正常、数据库启动成功，但脚本迟迟不进入Maven。

可核对时序：

- 19:49:20：脚本记录本次专用运行目录。
- 19:49:37：postgres.log记录`database system is ready to accept connections`；pg_ctl-start.log记录`done / server started`。
- 手工pg_isready确认127.0.0.1:55441可连接。本轮在同一专用实例另建review_third数据库，直接Maven验证全部通过。
- 在直接verify结束之前，原脚本仍未输出“测试实例已就绪”，也未调用Maven，超过配置的60秒。
- 按本次postmaster.pid核对目录并手工停止该专用实例后，原脚本最终以“数据库在60秒内未就绪”、exit 2结束。

**确定事实是正常启动成功路径没有正常推进，且当前超时不能限制整条启动流程。** 表现与原生进程/输出管道或子进程句柄等待相符；不能仅凭日志武断认定某个Windows句柄为根因，需进一步定位。上一轮日志走的是直接启动回退，它的成功不能覆盖本轮正常pg_ctl分支。

修复要求：

1. 分开验证正常pg_ctl启动和回退启动，不把其中一种路径的成功当作两者均可用。
2. 管理原生进程的生命周期及stdout/stderr，避免长期运行的postgres继承管道使父脚本等待；启动与pg_isready子进程都要有外层可执行的超时控制，不能仅给内部循环一个deadline。
3. 超时后仅收尾本次实例，保留诊断，并恢复环境及工作目录。停止测试实例必须核对所属目录，不能停止系统已有PostgreSQL服务。
4. 使用标准PostgreSQL安装、非管理员运行账号再次验证；本机修改过的postgres.exe不能代替标准发行版兼容证据。
5. 回退分支Start-Process的ArgumentList还需核对空格路径的实际参数边界；从含空格的“调用者当前目录”运行，并不能证明包含空格的“仓库/数据目录”能正确传给postgres。

验收：正常启动和回退分别完成一次最小真实IT；超时/启动失败返回非0且无遗留自建实例；根目录、子目录及含空格的实际仓库路径可运行；最后脚本自身完成verify并正确退出，不再需要手工接管数据库。
