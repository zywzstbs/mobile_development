## 3. 锁顺序与并发证据

最终顺序（HTTP 从第 1 步进，CLI 从第 2 步进）：

1. HTTP 幂等 advisory 锁；
2. `platform_admin_lock` 管理约束锁；
3. `actor + operationId` advisory 锁；
4. 再认证记录；
5. 领域资源行锁；
6. 业务、审计、回执同一事务提交。

参与入口：A04、A05、A08、A11、A12、A15、A16，`init-super-admin`，`import-users`。普通课程、聊天、作业写入没有挂到这把锁上。事务范围是 `IdempotencyService.execute` 的 `@Transactional`，`commit` 在其中执行，回执插入与外层业务同事务。

两种合法串行顺序的用例：

- “撤权先提交”：`revocationCommittedFirstMakesTheAlreadyIssuedGrantFail`——先撤权再用旧令牌发起 A15，期望 `403 FORBIDDEN`，且没有新授权、没有 `admin_operation` 行。
- “业务先取保护锁”：`inFlightGrantKeepsTheConstraintLockSoRevocationCannotOvertakeIt`——用原始 JDBC 连接持有目标 `app_user` 行锁，A15 阻塞在 `app_user` 上；此时再发 A16，它在 `platform_admin_lock` 上等待，order 不被反转；释放后两者都成功，被撤权者的 dashboard 立即 403。等待证据取自 `pg_stat_activity` 的 `wait_event_type='Lock'`，不是 `Thread.sleep`。

这两条用例本轮**未执行**，所以“锁顺序正确”目前只有代码与用例设计作为依据。

## 4. 恢复管理员与导入边界

有效恢复管理员（HTTP 与 CLI 共用同一段 SQL）：账号 `ACTIVE` 且 `disabled=false`、持有 `SUPER_ADMIN` 角色、有 `ACTIVE` 平台授权、该授权具备 `PLATFORM_ACCOUNT_MANAGE` 与 `PLATFORM_SUPER_ADMIN_MANAGE`、范围覆盖 `PLATFORM`、有密码凭据。

规则：已有可用全平台管理员时，减少可用性的操作不能让数量从正数变 0，否则 `409 LAST_ACTIVE_SUPER_ADMIN`。只挂学校授权的管理员不计入，多个学校并集也不能替代全平台。历史数据里已经没有全平台管理员时，不自动补造，只允许不恶化的动作；空库首次初始化是例外。

CLI 导入的敏感字段策略（首期）：普通导入只更新学校、班级学号、显示名、技能与普通角色；对已具备平台授权的账号，停用状态、身份核验状态、口令一律拒绝并给出受控操作指引，不静默忽略。整批进入管理锁、按账号 ID 顺序加锁，前后比较可恢复管理员数量，恶化就整批回滚。文件仍然禁止声明 `SUPER_ADMIN`。

残缺授权：`grantInitial` 遇到 `ACTIVE` 授权但缺角色、缺能力或范围不符时，显式失败并打印人工受控修复说明，不自动补齐，也不把学校授权升级成全平台。只有 `SUPER_ADMIN` 角色、没有有效授权时不计入恢复数量；由可信 CLI 显式指定该用户时按“无授权”路径补齐并写审计。

## 5. Windows 可信身份

来源：Windows 下取进程令牌的 `NTSystem.getUserSID()`；Linux 下取 `/proc/self/status` 的 euid，要求与 `UnixSystem.getUid()` 一致且用户名非空。两者同时尝试，恰好命中一个才返回，命中零个或两个都失败即报“无法确认当前操作系统用户”。

匹配格式：Windows 身份规范化为 `sid:<小写 SID>`，与映射表里的 `os-user` 比较时大小写不敏感；Linux 保持用户名原样（区分大小写）。两个命名空间天然互斥——Linux 用户名不可能以 `sid:` 开头——所以即使 `os.name` 被篡改，也伪造不出他人的有效身份。完全不读 `user.name`、`USER`、`USERNAME`、`USERDOMAIN`。

失败路径：Windows 上 `UnixSystem` 抛 `UnsatisfiedLinkError`、`/proc` 不存在，两者都被捕获后按“无该平台身份”处理。

生产映射边界：`src/main/resources/cli-operators.yml` 仍只有 `os-user: app`。本地 Windows 账号的 SID 不可能等于 `app`，所以不会因为这次改动获得审核权。测试资源用 `__TRUSTED_OS_USER__` 占位，解析为当前可信身份。

## 7. 审计与总览

允许集合：15 个 `action + resourceType` 组合（第二轮补入 4 个 HTTP 审核动作），见联合契约 2.9。`SUPPORT_*`、`PERSONNEL_CASE_*`、`AUTH_*` 与普通业务事件不在集合内；未登记组合默认不出现，即使持有 `AUDIT_READ`。

理由策略：账号状态、超管授撤保留原文；教师申请、课程认领、助理授权撤销一律返回空字符串，原文仍留在 `audit_event` 表里，不删除、不截断、不改写。

范围来源：用户事件取目标用户学校，教师申请取申请学校，课程认领取广场学校，已撤销授权取原本的广场，平台授权取该授权自身的 `PLATFORM`/学校范围。删除了操作者学校兜底。学校管理员看不到范围不匹配的事件，平台管理员也看不到范围解析为空的事件。

游标：版本从 `p66:audit:<grantId>` 改为 `audit-v2`，旧游标全部失效；total 与 hasMore 只统计可见集合；用别处的游标读审计会被拒绝。

总览无权限时：缺任一计数能力返回 `403 FORBIDDEN`，响应不含 `counts`，不返回 0 冒充统计；三项齐全但无 `AUDIT_READ` 时 `recentOperations` 是空数组，不是 `null`。

## 8. 回执与回放

回执写入与外层业务同事务，同一 `actor + operationId` 由 advisory 锁串行化，同一幂等键的重复请求返回同一 `receipt_json`，不重复写审计。

回放授权：先按当前库重查操作者资格（会话、账号、角色、授权、能力），再按当前目标关系核范围——账号事件用目标用户当前学校（允许已停用）、教师申请用申请学校、课程认领用广场学校、助理授权撤销用原本的广场。超管授撤不查目标用户当前授权，而是用该操作的 `auditId` 找到审计里的 `PLATFORM_ADMIN_GRANT` 资源，再读这条授权自身的范围；事实不足直接 `403`，不回退到猜测。

合法重试：目标被重新授权、目标版本变化都不影响旧回执可读；操作者被撤权、停用或失去目标范围时回放 `403`，不回执。正文不一致按 `IDEMPOTENCY_KEY_REUSED` 拒绝。
