日期：2026-11-06。检查对象：HEAD `66b856b` 加当前未提交实现及《P66与Windows迁移_修复回告_20261106.md》。本轮独立复核，没有修复产品代码，没有连接生产或执行数据库迁移。

**结论：暂不通过。77项单元测试独立重跑通过，但发现1项P1和4项P2。首次增设/撤销超管存在确定性404回归，Windows数据库脚本还存在启动后必然失败的问题。真实PostgreSQL用例仍未运行。**

## 1. 必须修复的问题

### S1 / P1：首次增设和撤销超管被回放检查直接拒绝

位置：`src/main/java/cn/gulupai/server/platform/application/PlatformWriteService.java:169`、`:216`；对照`common/idempotency/IdempotencyService.java`的新执行分支。

`requireCurrentReplayScope`被作为通用authorizationCheck传入IdempotencyService。该回调不仅在命中回执时执行，也在首次执行、action.get之前执行。SUPER_ADMIN_GRANT/REVOKE分支无条件调用requireOriginalGrantScope，后者要求findOperation(actor,operationId)已存在。

首次请求天然还没有admin_operation，因此抛RESOURCE_NOT_FOUND（HTTP404），根本不会到commit，也不会取得管理锁或校验再认证。这会阻断所有新的A15/A16 HTTP操作，不只是某个历史数据边界。

本轮在隔离源码副本中使用真实IdempotencyService和PlatformWriteService、模拟仓储及授权运行两个探针：首次grant和首次revoke均抛RESOURCE_NOT_FOUND；管理锁和verifyUnused都没有被调用。未冒称HTTP/真实数据库复现。

修复要求：明确区分首次执行和已提交回放。新请求允许在管理锁内按新执行规则处理；只有确认原操作存在后才追溯原grant。相同幂等键回放和换键同operationId回放都要保留当前目标授权，不可通过删除范围检查修复。检查摘要冲突的优先级，避免把不存在的原回执当新执行或把不匹配操作当同一目标。

验收：空操作记录下首次A15/A16成功执行；原键及换键回放不重复提交；越权回放拒绝；先运行既有PlatformP66IT及新PlatformAdminTransactionIT/PlatformReplayScopeP66IT。现有77项单元测试不包含这些数据库场景。

### S2 / P2：审计白名单漏掉HTTP教师审核和课程认领事件

位置：`src/main/java/cn/gulupai/server/platform/domain/ManagementAuditEvent.java:45`；写入端`PlatformWriteService.java:100`、`:120`。

新白名单只登记旧CLI动作REGISTRATION_APPROVE/REJECT和TEACHER_CLAIM_APPROVE/REJECT。HTTP A08实际写TEACHER_APPLICATION_APPROVED/REJECTED，A11实际写COURSE_CLAIM_APPROVED/REJECTED，并由reviewAs原样传给AuditService。

上述四种组合不在允许集合中，成功的App审核会被auditIds/auditsByIds的SQL直接过滤，不出现在A13和首页近期事件。新的隐私测试手工插入的是旧REGISTRATION_APPROVE，无法覆盖真实HTTP写入动作。

本轮探针确认四种实际HTTP动作的ManagementAuditEvent.find均返回null。这是白名单遗漏，不应放宽为全audit_event可读。

修复要求：精确补齐四个action+resourceType组合，继续保留敏感reason隐藏规则、范围解析和旧CLI映射。新增真实HTTP审核→读取A13/A01的完整测试，断言auditId、动作、结果、目标可见且理由不泄露。

### S3 / P2：Windows脚本的数据库连接串插值在严格模式下必然报错

位置：`scripts/run-pg-tests.ps1:304`、`:306`。

双引号字符串中的`$databaseName?currentSchema`被PowerShell视为一个变量名，不会拆成databaseName加URL查询部分。脚本启用了StrictMode，因此起库及createdb成功后，在“测试实例已就绪”的输出行就抛异常，Maven还没开始运行；下一行TEST_DB_URL也有同样问题。

本轮直接在PowerShell StrictMode下运行相同插值，得到：`The variable '$databaseName?currentSchema' cannot be retrieved because it has not been set.`。不需要PostgreSQL即可确认。

修复要求：两处均使用`${databaseName}?currentSchema=...`或格式化字符串；最好只构建一次URL，再用于日志和环境变量。增加不依赖数据库的连接串断言；随后真实起库验证Maven确实被执行。

### S4 / P2：脚本没有让Maven使用仓库根目录

位置：`scripts/run-pg-tests.ps1:325–327`。

脚本计算了repoRoot，但最终调用`& $mvnExe @argumentList`之前没有切换目录，也没有传-f。Maven Wrapper定位的是Maven分发，不会自动把调用者工作目录变成项目根。用户从src等子目录按文档调用时，即使修复S3并成功起库，Maven仍会在子目录找pom而失败。

修复要求：在try/finally中Push-Location repoRoot并保证Pop-Location，或传绝对`-f <repoRoot>/pom.xml`并验证测试夹具相对路径。选择一种一致方式，保留调用者原目录。不能只用“从子目录能检测到缺PG”证明完整子目录运行有效。

验收：从根目录、src目录、含空格路径分别执行真实最小测试；确认pom、admin夹具及docs接口清单都按项目目录加载，调用返回后工作目录恢复。

### S5 / P2：等待业务锁跨过再认证有效期后仍可提交

位置：`src/main/java/cn/gulupai/server/platform/application/PlatformWriteService.java:251–255`；`AdminReauthenticationService.java:106`、`:123`；`PlatformRepository.java:250`。

verifyUnused在取得目标用户/广场等领域锁之前检查expiresAt。之后business.apply可能长时间阻塞；取得业务锁后没有再次检查令牌期限，consumeReauth的UPDATE只要求consumed_at IS NULL，也不检查expires_at。

例如A04在令牌有效时进入verifyUnused，然后等待目标app_user锁直到5分钟期限过去，释放锁后仍会停用账号并消费过期令牌。管理约束锁解决撤权串行化，不能阻止时钟前进。统一指导和原详细指导均明确要求等待资源锁后检查期限；该项仍未落实。本轮为静态调用链确认，尚未在真实数据库重放时序。

修复要求：在领域锁取得后、业务提交前验证有效期，或在同事务消费时增加原子expires_at条件，失败时将业务、审计、操作记录全部回滚并返回准确错误。已提交回放仍不应重新要求原令牌未消费/未过期。

验收：真实连接锁住目标，发A04并确认其等待，推进MutableClock越过TTL后释放；应拒绝且无业务/审计/回执变化。补未过期正常提交和已提交回放。

## 2. 脚本仍需一并处理的生命周期问题

这些问题不替代上面5项主问题，应在修复W2时一起核对：

- JAVA_HOME在156行已修改，258行之后才保存previousEnvironment，所以finally恢复的是新值；MAVEN_USER_HOME被修改但没有保存/恢复。预检失败路径也在外层finally之前退出。
- pg_ctl start失败/超时时serverStarted仍为false；如果子进程已启动但尚未就绪，finally不会尝试确认并停止这个本次实例。需要基于本次数据目录的PID/status安全核对，不能停止其他实例。
- pg_ctl stop失败只警告，后面仍尝试删除数据目录，Maven成功时还可能打印“测试通过”。应保留诊断，不删除仍使用中的目录，并区分测试结果和清理失败。
- 调度专用NoticeOutboxSchedulingIT只awaitIdle，未取消后续轮询就清理；瞬时idle不是“不会再开始”。普通测试已关闭调度是改进，但专用测试的生命周期仍需实跑确认。
