## 6. 第 3 批：再认证、幂等与审计事务

### 6.1 再认证

复用现有密码编码器、Clock、RateLimitService；A17 验证当前操作者本人密码，不创建新会话。密码不 trim，不记录正文。限流覆盖用户和来源 IP，并返回真实 Retry-After（如支持）。

冻结后的合同必须绑定 actor/session/operation/action/target/原版本或前置条件/非凭据业务内容。服务端重新计算摘要，不能信任客户端自报摘要。建议五分钟有效期，随机不可预测令牌，仅存安全指纹，原始令牌只在返回时出现。

摘要规范应给出跨 Java/Android 相同的测试向量：键排序、字符串编码、整数、缺省/null、reason/note trim 规则；排除 password/reauthToken，但包含所有能改变业务结果的字段、目标与操作类型。一个令牌只能对应一笔被冻结的业务。

### 6.2 管理事务执行顺序

1. 校验会话和当前能力/范围，构造不含凭据的业务指纹。
2. 进入统一事务，取得稳定操作/幂等锁。不同幂等键但同 actor+operationId 不能二次执行。
3. 已提交同操作：比对内容后重查当前读取权限，返回原已提交回执，不要求旧令牌仍未消费；不同业务内容返回 IDEMPOTENCY_KEY_REUSED。
4. 未提交：核验令牌绑定、期限和未消费；按统一锁顺序锁管理约束、业务资源，再在锁内重查授权、状态、版本、回避与真实前置条件。
5. 原子完成业务更新、版本递增、令牌消费、审计、operation 与幂等回执。异常全部回滚，不得成功业务无审计。
6. 事务提交后才对外返回 COMMITTED。重试不得再次通知、重置或增加授权。

现有 IdempotencyService 可复用事务和加密回执，但其 authorizationCheck 同时作用于新执行/回放，所以“一次性令牌未消费检查”应放新执行分支，不能放共同回调。向它传入专用业务指纹 DTO；不要全局忽略某些 JSON 字段，破坏旧业务幂等。

锁顺序需结合现有服务确认并写在实现注释中；不同路径必须一致。已有请求先读出来的权限/版本，在拿到锁后必须重新查，防止撤权与写入竞态。

### 6.3 审计与回执

AuditService 当前返回 void，可增加返回审计 ID 的方法，保留旧调用兼容。新管理审计用真实当前 actor，明确 action/result/scope；历史事件采用可说明的映射，缺失信息不编造。拒绝/失败审计如需保留，应在业务回滚后走独立审计流程，不能为了存失败记录提交半笔业务。

成功回执按联合 D §7.2：operation 包含 id/action/targetType/targetId/status=COMMITTED/resultingRevision/auditId，resource 为真实结果。A05 保留顶层 requestId/targetUserId/expiresAt/delivery 并追加 operation；这里只代表重置请求创建，不代表密码已更改。

验收：原键重试、换令牌原操作重试、换键原操作、错摘要、跨用户/会话/目标、过期、并发消费、提交后断网、审计失败回滚。不能仅测试 HTTP 200。

## 7. 第 4 批：各写操作的具体业务改造

### 7.1 教师申请 A08

将 RegistrationReviewService 中业务规则抽成接受可信操作者上下文的内部事务服务：CLI 由 CliOperatorDirectory 提供身份，HTTP 由 PlatformAuthorizationService 提供身份。不能把 HTTP 用户传进 CLI 身份环境，也不能允许正文指定 reviewedBy。

保留申请锁、expectedRevision CAS、禁止自审、账号角色更新原子性。新增账号状态/修订一致性检查，防止审核将已被停用的账号意外恢复。管理投影 ACTIVE→APPROVED；公开注册回执不变。通过只授 TEACHER，不授受理/帮助/任课权限。返回结构化结果而非 CLI 文本；CLI 再格式化为原输出。

### 7.2 课程认领 A11

TeacherClaimReviewService 当前不接收 expectedRevision，审计写 cli，不能直接加 Controller 完事。抽公共业务服务，接受可信 actor、原申请版本、真实说明；HTTP 和 CLI 分别授权。

锁定广场后重读申请并做状态+revision CAS，保持唯一当前教师、真实学校/核验关系及已有转交流程；检查申请人当前账号与教师资格，禁止自审。拒绝和通过都要求 1～500 字说明。建立任课、申请决定、广场版本/epoch、审计原子完成。

### 7.3 助理紧急撤销 A12

复用 TeacherService 撤销底层逻辑（授权版本、ClassGrantRepository.revoke、广场 revision/epoch、审计），但单独核验平台能力/范围。不要放宽原教师端 requireTeacher，不伪造教师 principal。锁内重读 grant，使用 grant revision；撤销后下次局部权限调用立即拒绝，历史公告/成绩/人员记录保留。

### 7.4 停用/恢复 A04

仅 ACTIVE→DISABLED、DISABLED→符合原资格的 ACTIVE；PENDING_REVIEW/REJECTED 不能靠恢复绕过审核。账号 CAS、disabled/account_status 同步、会话撤销、管理审计原子化；恢复后旧会话不复活。恢复资格来源不明确时明确冲突，不能猜为已审核。

### 7.5 超管 A15/A16 与最后管理者

首期推荐只给已激活的独立有效账号授权，禁止自授。新授权/撤销同步角色和能力关系，保留授权历史；A16 版本来自授权而非用户。

所有会减少有效管理者的操作（包括 A04、A16 和应急 CLI）在同一全局管理约束锁下检查操作后的可用集合。至少保留一个账号可登录、授权有效且具有必要管理恢复能力的管理员。不能只数 user_role 行，也不能只在 A16 检查。

并发测试使用两个真实数据库事务和同步屏障：两个管理员同时撤销/停用对方，至多一笔导致人数减少，另一笔冲突；最终仍有恢复管理能力。附交叉场景 A04 对 A16，而非只测两个相同接口。

### 7.6 密码重置 A05

复用密码编码及会话撤销基础，但先实现真实安全交付和一次性兑换闭环。请求受理不立刻改密码，不通过 API 回新密码/重置秘密；实际兑换成功才更新哈希并撤销旧会话。兑换过期、并发二次使用、目标变化均有测试。未具备渠道时明确 ENDPOINT_NOT_IMPLEMENTED/未开放，保持前端相同状态，不伪造成功。
