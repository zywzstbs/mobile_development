# P62～P66 第一轮实现审查

日期：2026-11-06。检查对象：基线 `66b856b` 上当前未提交的全部实现，包括新增 platform 包、V031 和旧服务改动。需求依据为同目录 P62～P66 合并交接文档及详细执行指导；实施记录和联合契约作为实现方声明核对。

**结论：暂不通过交付验收。主体接口已经实现，但存在 4 项 P1、3 项 P2 问题。既有 P66 的 8 项测试通过，不能覆盖下面已复现的缺陷。** 本轮只审查和编写证据，没有修复产品代码，没有连接生产、开户、迁移生产库或部署。

## 1. 必须修复的问题

### R1 / P1：操作者撤权后，等待业务锁的增设请求仍可成功

位置：`src/main/java/cn/gulupai/server/platform/application/PlatformWriteService.java:187`、`:265–279`。

`commit` 在取得目标用户锁之前取得 Access；A15 不取得管理约束锁，`grantSuperAdminLocked` 等到目标锁后仍使用先前 Access，也没有重新查询操作者的有效授权。另一个管理员可在等待期间完成 A16 撤销操作者，但原请求仍建立新的全平台超管。

已用真实 PostgreSQL 事务复现：锁住目标学生行 → A 发出 A15 并确认在数据库等待锁 → B 经 HTTP 成功撤销 A → 释放目标锁 → A 的 A15 返回 COMMITTED。不是仅靠线程同时启动推测竞争。

修复要求：对操作者授权的验证和业务提交建立与撤权/停用一致的串行化机制，明确统一锁顺序；取得等待的业务锁后不能沿用旧 Access。只补一次普通 SELECT 仍须论证检查到提交之间的竞态。审核、助理撤销等其他写路径也按同样原则审计。

验收：上述固定时序下，撤权已提交的 A 不能继续增设；补停用与授权范围变化场景，验证不死锁。

### R2 / P1：普通 CLI 重导入可移除最后超管，且初始化命令不能修复

位置：`src/main/java/cn/gulupai/server/identity/cli/AdminImportService.java:77–87`、`:249–261`；`platform/application/PlatformSuperAdminService.java:30–34`。

导入先删除目标全部 `user_role`，而本次新增的解析规则又禁止导入 SUPER_ADMIN，所以重导入现有超管必然丢失该角色。平台 grant 仍 ACTIVE，没有同步撤销，也没有最后管理者约束锁/检查。

已复现：初始化唯一超管 → 重导入同一演示夹具 → SUPER_ADMIN 角色数量为 0，登录后的管理请求 403；`countRecoveryExcluding/isRecoveryAdmin` 所依据的 grant/能力仍把该用户视为恢复管理员。再次执行 `grantInitial` 只返回 already-active，不补角色，App 管理入口仍无法恢复。

修复要求：普通用户导入不能隐式覆盖平台授权；受控身份变化、停用与平台授权必须保持一致，覆盖最后管理者保护。已有 grant 但缺角色的状态须显式报错或通过受控修复路径处理，不能假报已正常初始化。也检查导入 disabled=true 和批量导入多个管理员。

验收：重导入不丢平台资格；禁止通过导入停用/移除最后有效管理员；角色/grant 不一致不再被计作有效恢复管理员。

### R3 / P1：A13 将全业务审计及业务理由原文直接暴露给平台管理员

位置：`src/main/java/cn/gulupai/server/platform/persistence/PlatformRepository.java:627–647`、`platform/application/PlatformReadService.java:258–269`。

查询直接读取整个 `audit_event`，全平台 scope 的条件为 TRUE，没有管理事件白名单或敏感字段投影；`reason` 原样返回。原 `support/HelpSupportService.java:1137` 会将工单处理理由写入这里，`governance/PersonnelCaseGrantAdminService.java:101,131` 也会写事项授权理由。因此只具平台审计资格、没有工单/案情资格的人可从新管理接口读取这些原文。

隔离探针按现有业务审计格式插入 SUPPORT_CLOSE / SUPPORT_TICKET 和标记理由后，A13 响应确实包含理由原文。该探针验证读取泄露，不冒称跑过真实人员事项全链路。

修复要求：明确允许公开的管理事件与字段；业务事件若需出现在平台审计中，只返回经批准的最小元数据，敏感理由须脱敏或按原资源权限检查。学校范围不要用操作者学校兜底猜测事项所属范围。旧 CLI 审计可保留，但“保留历史”不等于把全表原文开放。

验收：无 SUPPORT_HANDLE/事项资格的超管不能从 A13 获得工单理由、事项敏感说明；学校范围按真实目标确定；管理审计仍可正常查看。

### R4 / P1：最后管理者计数忽略授权范围，可移除最后全平台管理员

位置：`src/main/java/cn/gulupai/server/platform/persistence/PlatformRepository.java:66–103`；`platform/application/PlatformWriteService.java:300–301`。

恢复管理员判断只看账号 ACTIVE 和两项 capability，不看 scope，也不检查有效 SUPER_ADMIN 角色。存在一个全平台管理员和一个单学校管理员时，允许前者撤销自己，之后平台范围有效授权为 0。根据当前 A15 实现，学校管理员只能继续授予学校范围，不能在 App 中恢复全平台管理，也无法处理其范围外学校。

已复现：唯一全平台管理员自撤销返回 COMMITTED，剩余 recoveryCount=1，但有效 PLATFORM scope 数量为 0。学校范围通过实现已有的授权模型构造，并非假设不存在的能力。

修复要求：把“具有必要管理恢复能力”落实到真实可用角色、账号和范围，保证相关管理范围仍可恢复；若首期不准备支持学校管理，须一致关闭该模型，不能只在文字里声称支持。A04、A16、CLI 共用规则。

验收：全平台+单学校、多学校及角色/grant 不一致的组合均不能造成管理范围不可恢复；补 A04/A16 混合并发。

### R5 / P2：幂等回放只重查能力，不重查目标当前范围

位置：`src/main/java/cn/gulupai/server/platform/application/PlatformWriteService.java:162–181`。

原幂等键回放的 authorizationCheck 和换键原 operationId 回放，都只调用 require(capability)，没有检查目标学校/当前读取范围。管理员 scope 缩小后，直接读取目标已 403，但两种重放都仍返回该目标的操作、结果版本和 auditId。

已复现：先成功停用目标 → 在隔离库将操作者 scope 改为其他学校以构造权限收缩 → 目标详情 403 → 原键、换键同操作均返回 COMMITTED。这里模拟的是权限变化后的状态，没有声称已有在线编辑 scope 的 API。

修复要求：为回放单独实现当前目标读取授权，并用于两层回执路径；不能直接复用会要求原 revision 仍匹配的 prepare，也不能重新要求已消费令牌未消费。合法重放仍应返回原回执且不重复执行。

验收：原键/换键在当前目标越权时都拒绝；有权情况下旧版本已改变、令牌已消费的原操作仍可安全核对。

### R6 / P2：总览绕过审计能力，返回其他能力范围内的信息

位置：`src/main/java/cn/gulupai/server/platform/application/PlatformReadService.java:46–57`。

A01 只检查 ACCOUNT_READ，却无条件查询全部近期审计及教师申请/课程认领计数。独立平台能力未落实到首页投影。

已复现：只授 ACCOUNT_READ 的超管访问 A13 返回 403，却可从 A01 读到同一工单审计的 targetId/action。修复 R3 的业务审计过滤后，也仍须防止只读账号管理员绕过其他管理能力看到受限事件。

修复要求：按当前能力过滤首页近期事件和各计数。计数必填与无权限表达的冲突需双方明确，不能填假 0；指导文档第 5 节已要求按其他能力过滤内容。

验收：单项能力账号不能借总览读取本来无权的事件/目标，完整权限账号保持真实统计。

### R7 / P2：新增清库依赖未同步测试，标准 verify 已失败

位置：`src/test/java/cn/gulupai/server/it/TestSchemaCleaner.java:33–38`；`TestSchemaCleanerTest.java:28–34`。

新增平台子表依赖是必要的，但原测试仍用 containsExactly 断言只删除 registration_application/app_user/school。本次标准 `bash scripts/run-pg-tests.sh verify` 确定在该断言失败，无法正常进入集成测试阶段。

修复要求：按 V031 的实际依赖更新测试，检查子表先于父表且不误扩展无关清理；不能删掉新增依赖或长期使用 failure.ignore 冒充通过。

验收：不加忽略失败参数的完整 verify 通过。

## 3. 复现材料与使用方式

`审查复现/PlatformP66ReviewIT.java` 是本轮探针源文件，放在 docs 下，不自动加入正式测试。它复用原 PlatformP66IT 的隔离初始化/请求辅助逻辑，包含 5 个探针，分别覆盖 R1、R2、R3+R6、R4、R5。

需要重新复现时，将它临时复制到 `src/test/java/cn/gulupai/server/platform/PlatformP66ReviewIT.java`，运行：

```bash
bash scripts/run-pg-tests.sh -Dtest=AdminPayloadDigestTest -Dit.test=PlatformP66ReviewIT verify
```

运行后移除临时副本。修复后应把断言改为期望安全行为，再纳入正式回归；不能把当前“漏洞应当成功”的断言长期当作产品验收标准。本轮已移除 src 下的临时探针和对应临时编译类，保留 docs 中证据。
