## 4. 第一步：先补能失败的权限测试

### 4.1 复现当前行为

历史证据在[ACL探针](审查复现/P66ThirdAclProbe.java)。它证明调用restrictToOwner后普通Users仍能读取；不能原样当作“安全通过”的测试。

正式测试应反转结果：给可丢弃的文件或父目录配置普通用户可读ACL，调用新的私有写入接口，要求最终不再存在普通Users/Authenticated Users/Everyone的有效读取授权，且当前可信用户仍能读写。

不要在JUnit输出中打印文件正文、哈希对应的真实口令或真实账号。测试只用`dummy-password-for-test`一类无意义字符串。

### 4.2 至少先写这四个用例

1. **新文件继承宽权限**：父目录有普通用户继承读权限，生成凭据后只允许规定的可信主体读取。
2. **已有文件权限过宽**：预先创建含假口令的文件，授予普通Users读权限；重复写入后权限被收紧，或在无法安全处理时明确失败，不静默成功。
3. **权限建立失败**：用可控失败注入模拟ACL设置/校验失败，断言新秘密没有被写入目标文件或残留临时文件。
4. **无可用权限视图**：文件系统既无POSIX也无ACL能力时明确失败，不能把“不支持”当成功。

后两项可以通过小型权限操作接口注入失败，避免依赖开发者恰好不是管理员。但前两项必须在真实Windows NTFS上操作真实ACL，不能全部mock。

## 5. 第二步：实现受保护的凭据文件组件

### 5.1 先确定权限策略

最低要求：当前可信操作系统用户可读写；普通Users、Authenticated Users、Everyone没有读取、写入或改变ACL的授权。如保留SYSTEM等系统维护主体，明确列出，测试按同一策略判断。不要笼统声称“只有owner”而实际上保留任意组的ALLOW规则。

Linux保持私有目录0700、私有文件0600。Windows用`AclFileAttributeView`读取/设置并回读校验ACL；**仅存在AclFileAttributeView不表示权限已安全，写入ACL成功也必须回读检查。**

当前Windows可信身份已由TrustedOsIdentity从原生令牌获得SID。复用该来源；不要改为user.name、USERNAME或USERDOMAIN。将SID解析为Java UserPrincipal时，先验证本机JDK21实际支持的解析方式，不能假定任何字符串都会被lookupPrincipalByName正确识别。解析失败应受控失败，不能退回Everyone或继承权限。

新建文件的owner可能是某个管理组，不要单凭Files.getOwner就推断它等于当前登录用户。若必须读取owner，用它验证文件归属或明确的系统策略，而不是替代可信身份解析。

### 5.2 建议的组件接口

```text
readExistingPrivateCredentials(path)
    对既有文件先校验类型、归属与权限；需要且允许时收紧权限；再读取。

writePrivateCredentials(path, content)
    建立私有暂存位置 → 验证权限 → 写入 → 安全发布 → 验证目标。

createPrivateJson(value)
    建立私有临时目录/文件 → 验证权限 → 序列化 → 返回需清理的资源。

close/deleteOwnedTemporaryResources()
    仅删除本次创建且已核对路径的临时产物。
```

这只是职责示意，不是要求复制固定签名。为减少泄漏，别把content或完整对象放进异常、日志或toString。

### 5.3 严格按此顺序处理新输出

1. 规范化调用者路径，确认目标不是目录、符号链接或需拒绝的重解析目标；不要盲目跟随链接覆盖其他文件。对于无法可靠核验的特殊路径明确拒绝。
2. 只创建需要的目录。新建的任务私有临时目录在存入任何秘密之前建立权限；不要扩大或收紧用户已有父目录的全部ACL。
3. 在私有暂存位置创建空文件。若文件系统支持在创建时赋权限，优先使用；否则空文件建立正确ACL并回读确认后才能写入秘密。
4. Windows ACL必须处理继承结果。设置显式规则后回读，确认普通主体没有通过继承继续获得权限。若当前Java/provider操作无法去除继承或无法证明安全，拒绝写入并报告，不跳过。
5. 写入内容并关闭流。异常只报告阶段/错误类型，不附带秘密正文。
6. 发布到用户指定目标。选择同文件系统的受控暂存/替换策略，验证移动或替换后的ACL仍满足要求。
7. 不支持原子替换时，不要无条件退化为“复制到宽权限目标再补ACL”。可以采取经过证明的安全替代流程，或者明确失败并保留原目标；记录具体策略。
8. 只有最终目标校验成功才向调用方返回成功。失败时清理本次暂存文件；不要为了清理而删除用户原本存在的凭据。

不要在宽权限目标中写明文后才调用restrictToOwner。当前writePrivate正是“先写后限权”，两者都必须改。

### 5.4 处理既有文件和中间JSON

- 重复播种要继续复用原密码，不能因权限整改生成第二套口令。
- 既有文件权限过宽时，先限制/验证再读取或覆盖；无法满足策略就失败，原文件由用户掌控，不擅自删除。
- 把“过去已经泄漏的旧口令是否轮换”与本轮文件修复分开，不自动替用户轮换业务密码。
- 包含原始口令的用户导入JSON也要经过相同私有文件流程；不能只保护最后的credentials-file。
- finally清理只针对本次创建的临时文件/目录。避免先返回一个普通临时Path再忘记清理其私有父目录；可用小型AutoCloseable资源封装。
- 对CLI dry-run保持现有不产生最终凭据文件的行为；内部临时内容仍然按私密数据处理。

### 5.5 权限实现不需要做的事

不新增公开API、不修改CLI审核授权、不放宽TrustedOsIdentity、不调用系统命令向全机账号授权，不把生产凭据导出到文档。管理员能接管文件的系统能力不等于普通Users应当拥有读取权限。

## 6. 第三步：接入DemoSeedService并验收权限

1. `loadOrCreatePasswords/readPasswords`接入既有文件的受保护读取。
2. `writePrivate`只负责组装内容并调用新组件，不直接Files.writeString后再设置权限。
3. `writeJson`返回新的受保护临时资源，序列化发生在权限建立之后。
4. `seed`的finally关闭所有本次临时资源；异常时不吞掉会导致明文残留的关键诊断，但不要覆盖最初业务错误。
5. 删除或替换旧restrictToOwner，不留下另一个“非POSIX直接成功”的路径。
6. DemoSeedIT对Windows分支新增ACL断言；对Linux分支继续断言0600，不再只if(POSIX)就结束权限验证。

补齐测试矩阵：

| 场景 | 必须断言 |
|---|---|
| 新目标、宽权限父目录 | 写前受保护，最终ACL符合策略 |
| 既有宽权限目标 | 收紧成功或明确拒绝，不能静默忽略 |
| 重复播种 | 同账号口令不变，权限不退化 |
| 写入/发布/ACL失败 | 不残留新明文，原目标不被错误删除或截断 |
| 临时用户JSON | 具有私有权限，正常/异常退出均清理 |
| 链接或不支持的特殊路径 | 按已定义策略拒绝或可靠核验，不能跟随任意链接写秘密 |
| Windows不同显示语言 | 身份不依赖英文组名，规则判定使用稳定主体标识 |
| Linux | 实际可用环境下验证权限与原播种行为 |

Windows上不能因为测试失败就跳过整组；Linux无法实跑时如实记未验证，不影响先完成Windows可执行部分。

## 7. 第四步：给脚本增加可定位的阶段记录

先不要根据猜测直接大改。第三轮确认的是：pg_ctl日志已报告启动成功、PG可用，而脚本没有及时进入Maven；停止专用实例后脚本最终以就绪超时退出。输出管道/子进程句柄继承是调查方向，不是已经证明的唯一根因。

为以下阶段各增加“进入/退出/耗时/退出码”日志，不记录密码和令牌：

```text
PRECHECK → INITDB → START_SERVER → WAIT_READY → CREATE_DATABASE
→ RUN_MAVEN → STOP_SERVER → RESTORE_ENV → CLEANUP → EXIT
```

每个原生进程记录受控的工具名称、进程ID、工作目录和日志路径。数据库连接串不含口令时可记录。启动时间使用单调计时计算超时，墙上时间只用于人读日志。

基线先用未修改PostgreSQL发行版在可运行的非管理员账号下复现正常启动路径；环境不具备时保留限制，先完成不依赖PG的进程测试。不要为了复现再修改postgres.exe。

## 8. 第五步：实现有界的原生进程执行

### 8.1 短命令与常驻服务分开

| 类型 | 示例 | 生命周期 |
|---|---|---|
| 有界短命令 | --version、initdb、pg_ctl start/status/stop、pg_isready、createdb | 有显式超时，取得实际退出码，超时可安全收尾 |
| 常驻进程 | 回退直接启动的postgres.exe | 启动后保留句柄，不等它退出；通过就绪探测进入下一阶段 |
| 长测试命令 | Maven verify | 保留真实退出码与输出，不能误用PG启动的60秒限制 |

建议把有界短命令封装成一个helper，返回`ExitCode / TimedOut / Duration / StdoutPath / StderrPath`等结构。不要用输出文本中是否含“success”代替退出码。

### 8.2 进程启动与参数

- 不再把可能派生常驻子进程的启动命令直接接入`2>&1 | Tee-Object | Out-Null`并无限等待流结束。
- 选择可控制的进程API。目标若为PowerShell7，可评估.NET ProcessStartInfo.ArgumentList保持参数边界；若支持Windows PowerShell5.1，需要单独处理其运行时差异，不宣称同一API天然可用。
- 使用Start-Process时必须隐藏窗口；其ArgumentList不能仅因为是数组就假定路径空格已正确转义。对Windows原生命令行边界进行真实测试，禁止Invoke-Expression或拼接任意shell命令。
- 需要重定向输出时，分别写本次运行的日志文件或采取不会因后台子进程继承句柄无限等待的读取机制。**父进程退出不等于所有输出流立即EOF。**
- 如果使用异步读流，不要在后面无界等待ReadToEnd/事件完成；读取、退出和超时应有一致的收尾设计。
- 不照搬“Start-Process -Wait”作为万能修复；确认实际等待的是目标进程还是连同其常驻子孙，防止把原停滞换个写法。

### 8.3 超时必须真正可执行

外层deadline要约束等待中的进程本身。下面的形式不合格：

```text
while (now < deadline) {
    invoke-native-command-that-may-block-forever
}
```

推荐逻辑：

```text
启动短命令并保存本次进程对象
在剩余时限内等待该进程退出
若超时：核对归属并终止该短命令；收尾其本次可确认资源
读取已完成的有限日志并返回TimedOut
```

pg_isready内部可设置短连接等待，但仍需外层时限；单次探测最长时间不得超过剩余就绪期限。不能每次探测重新给完整60秒，导致总等待无限延长。

## 9. 第六步：重写启动、就绪和停止的编排

### 9.1 正常pg_ctl路径

1. 新建本次唯一运行目录，初始化实例，不复用别人数据目录。
2. 使用有界helper执行pg_ctl start；日志与进程退出状态明确。
3. 成功退出后立刻记录START_SERVER完成并进入WAIT_READY，而不是等待postgres结束。
4. pg_isready在总deadline内有界重试；确认自己启动的实例与目标数据目录一致，不能只因端口可连接就接管别人的服务。
5. createdb同样有超时；成功后再设置TEST_DB_*并进入Maven。

### 9.2 回退路径

只在已识别、可解释的启动失败下进入回退；失败类型不匹配就保留诊断退出。不要所有pg_ctl失败都静默直启。

进入回退前检查正常路径是否已经产生本次服务进程，避免同目录启动两次。直接启动postgres.exe时保存实际进程对象、PID、创建时间、可执行文件路径和规范数据目录；后台运行隐藏窗口。

真实仓库/数据路径含空格时，-D必须是一个参数。仅把调用者cwd切到含空格目录后仍启动无空格repo，不算覆盖。

如果决定取消自动回退，须提供可用的标准启动路径、清楚说明不支持的环境并同步文档；不能删掉失败分支后宣称它已验收。

### 9.3 停止与PID安全

优先对本次数据目录使用有界pg_ctl stop并确认停止。正常启动失败或超时也可能已经产生服务，不能只靠serverStarted布尔值决定是否清理。

强制结束的兜底不能仅信任postmaster.pid里的一串数字和路径文本：PID可能被重用。结合本次记录的进程句柄/创建时间、实际可执行路径、实际命令行与数据目录核对。无法证明归属时保留目录并报清理失败，不杀未知进程。

禁止按进程名、端口或全局服务列表批量停止。机器上有既有PostgreSQL服务，本轮不能接管它。

### 9.4 finally与退出码

- 环境快照在任何修改之前保存，覆盖JAVA_HOME、MAVEN_USER_HOME、MAVEN_OPTS、TEST_DB_*；所有预检/启动/测试异常都经过finally。
- 工作目录恢复只对应确实执行过的Push-Location，避免异常分支Pop过头。
- Maven失败保留Maven退出码。环境/起库失败可统一2；Maven成功但清理失败可用3。数值以最终文档为准，但不能打印“全部通过”掩盖清理失败。
- 清理前确认实例已停止，解析最终绝对路径并确认处于本次专用目录；拒绝链接/重解析路径绕出目录。
- KeepData保留数据与日志；失败默认至少保留必要诊断，不输出含秘密的内容。
