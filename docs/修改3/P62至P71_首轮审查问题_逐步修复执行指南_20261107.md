## 3. F1 手把手修 R2 游标期限

### 3.1 读懂当前调用

打开以下位置。

- `platform/application/PlatformReadService.java` 的 `page(...)`。
- `common/pagination/CursorService.java` 的两个 `create(...)` 重载、`resolve(...)` 和 `CursorData`。
- `platform/application/AdminCursorCodec.java` 的 `encode/decode`。
- `platform/PlatformReadPrivacyP66IT.java` 的已有列表分页、串游标和范围变化测试。

当前 `page` 续页获得 `resolved.ids()/position()`，却丢弃 `resolved.expiresAt()`。无期限参数的 `CursorService.create` 会重置为当前时间加 15 分钟。已有带 expiresAt 参数的重载可直接复用。

### 3.2 改动步骤

1. 在 `page` 的局部变量中增加 `Instant snapshotExpiresAt = null`。这里 null 仅表示当前请求正在建立首页快照。
2. 首页沿用当前 freshIds 与 position=0。保持原授权过滤和真实 total。
3. 续页在 resolve 成功后保存 `snapshotExpiresAt = resolved.expiresAt()`。真实数据库解析应必有期限；如发现实际调用可能返回 null，明确视作无效游标，返回 CURSOR_EXPIRED，避免给旧快照重新续命。
4. 保留 containsAll 范围/状态复核、页码边界、scope、queryHash、授权 epoch 和游标编码。
5. hasMore 为 true 时，首页调用原 create 重载，续页调用带 snapshotExpiresAt 的重载。hasMore 为 false 时 nextCursor 仍为空。
6. 该 helper 同时影响 A02、A06、A09、A13。逐项检查所有调用者，确保没有复制出独立分页实现。

核心修改形状如下，按现有方法组织整合。

```java
Instant snapshotExpiresAt = null;
// 首页分支保持现有逻辑。
// 续页分支 resolve 成功后执行。
snapshotExpiresAt = resolved.expiresAt();
if (snapshotExpiresAt == null) {
    throw new ApiException(ApiCode.CURSOR_EXPIRED);
}

// 保留原来的切页和 hasMore 计算。
if (hasMore) {
    String nextToken;
    if (snapshotExpiresAt == null) {
        nextToken = cursorService.create(access.actorId(), scope, queryHash,
                access.grant().revision(), ordered, to);
    } else {
        nextToken = cursorService.create(access.actorId(), scope, queryHash,
                access.grant().revision(), ordered, to, snapshotExpiresAt);
    }
    next = AdminCursorCodec.encode(nextToken);
}
```

此片段中的 resolved 只存在于原续页分支，不能把赋值和 null 检查挪到首页也会执行的位置。优先沿用 CursorService 的 TTL 定义，避免在读取服务复制另一个 15 分钟常量。

### 3.3 写真正的回归测试

推荐在已有平台集成测试中增加固定时钟用例，参考 `PlatformAdminTransactionIT.TestClockConfig` 的 `MutableClock`、`@Primary` 和每用例时钟重置方式。新建测试类时复用隔离导入与 `TestSchemaCleaner` 规则。

1. 隔离库至少准备 4 个可见用户，limit=1。将时钟设为 T0，读取首页游标 C1。
2. 通过 `AdminCursorCodec.decode(C1)`、`Hashing.sha256Hex` 查 `cursor_snapshot.expires_at`，记为 E，验证其为正常首页期限。
3. 推进时钟接近 E，使用 C1 读取第二页并取得 C2，查 C2 期限必须精确等于 E。
4. 再推进但仍早于 E，使用 C2 取得 C3，其期限仍等于 E。
5. 设时钟恰好为 E，分别提交 C1、C2、C3，全部返回 409 CURSOR_EXPIRED。选择 T0+15 分钟内不会使 accessToken 同时到期的配置，避免错误地验证到 SESSION_EXPIRED。
6. 新建一次首页请求可取得新的期限，这属于新快照。旧快照已经到期。
7. 重跑账号转校、范围收缩、筛选改变、epoch 改变、不同列表串游标及末页空 nextCursor 用例。

若沿用审查探针的数据库调整期限方式，修复后要断言所有新游标与被调整后的原到期时间精确相同。正式到期断言优先推进测试时钟，避免等待真实 15 分钟。

| 测试场景 | 期望 |
|---|---|
| 首页有多页 | total 为授权筛选后的快照大小，C1 有正常期限 |
| 临近到期时继续翻页 | 新游标与 C1 的绝对期限相同 |
| 恰好到期或超过期限 | 全部旧游标 CURSOR_EXPIRED |
| 数据新增 | 沿用已冻结的快照语义，期限无变化 |
| 数据离开授权/筛选范围 | 原有安全失效行为继续有效 |
| 已到末页 | hasMore=false，nextCursor="" |

## 4. F2 手把手修 R1 目录资格

### 4.1 先固定语义

现态目录已经每用户一条，优先 ACTIVE 授权，没有当前授权时取最近撤销记录。SQL 当前只带出授权状态和账号启用状态，所以缺角色/范围/能力的残缺记录也会被标 ACTIVE。

本轮推荐采用下表，对外继续使用现有 `items[].status` 枚举及标准错误外壳。

| 记录事实 | A14 输出 |
|---|---|
| 选中记录为 REVOKED | 原样 REVOKED，保留真实授权版本和历史元数据 |
| 选中授权 ACTIVE，目标确实 disabled 或 accountStatus=DISABLED | DISABLED，表达账号实际停用 |
| 选中授权 ACTIVE，账号可用且资格和授权结构完整 | ACTIVE |
| 选中授权 ACTIVE，但目标待审/驳回、身份/资格/凭据不可用、缺角色/能力/范围 | 整个 A14 返回 503 SERVICE_UNAVAILABLE，响应不输出一份看似完整的目录 |

只要出现上述不可投影记录就返回不可就绪。这会让一条异常记录阻断目录读取，是本方案明确选择的保守行为。回告记录异常目标和缺失事实的脱敏诊断，由受控运维核对；后续可协商新状态改善可用性。

ACTIVE 的本轮最低事实包括账号 ACTIVE 且 disabled=false、身份 VERIFIED、eligibility_source=VERIFIED_ACTIVE、存在非空凭据、SUPER_ADMIN 角色、ACTIVE 授权、至少一个有效平台能力及至少一条有效平台/学校范围。授权行、能力和范围以选中的同一 grantId 为准。

合法学校范围管理员满足上述事实时仍可显示 ACTIVE。全平台恢复管理员另需全平台 scope、ACCOUNT_MANAGE 与 SUPER_ADMIN_MANAGE 等现有条件。目录有效性不要直接套用 `isPlatformRecoveryAdmin`，否则合法学校范围或职责受限的管理员会被错误排除。

### 4.3 扩充查询事实

1. 保留原 DISTINCT ON 每用户选择一条授权的查询，保留 ACTIVE 优先、真实排序与目录规模检查。
2. 内层 SELECT 增加 `u.identity_status`、`u.eligibility_source`、凭据存在性以及角色/能力/范围的 EXISTS 结果。
3. EXISTS 的能力和范围必须用当前选中的 `g.id`，避免误把旧授权的残留能力借给新授权。
4. 使用 EXISTS 避免连接能力和范围表后倍增行数，导致 DISTINCT ON 选择不稳定或目录人数错误。无需返回密码哈希或原凭据。
5. 更新内部 `SuperAdminRow` 与 RowMapper，逐项核对列名、类型和参数顺序。

可供整合的 SELECT 表达式如下。

```sql
u.identity_status,
u.eligibility_source,
(u.password_hash IS NOT NULL AND length(u.password_hash) > 0) AS has_password,
EXISTS (
    SELECT 1 FROM user_role r
    WHERE r.user_id = g.user_id AND r.role = 'SUPER_ADMIN'
) AS role_held,
EXISTS (
    SELECT 1 FROM platform_admin_capability c
    WHERE c.grant_id = g.id
) AS has_capabilities,
EXISTS (
    SELECT 1 FROM platform_admin_scope s
    WHERE s.grant_id = g.id
      AND (
          s.scope_type = 'PLATFORM'
          OR (s.scope_type = 'SCHOOL' AND s.school_id IS NOT NULL)
      )
) AS has_scope
```

当前 V031 已约束平台能力的合法枚举和学校外键，故能力 EXISTS 可利用这些约束。执行时确认工作树仍有这些约束。若约束曾变更，按实际支持的能力值验证，不能把未知 capability 当作可用能力。

### 4.4 修改状态投影

将 `directoryStatus` 整理为清楚的三类处理。

1. 真实撤销直接返回 REVOKED。
2. 真实停用返回 DISABLED。避免将任何非 ACTIVE 都笼统写成停用，PENDING_REVIEW/REJECTED 属资格异常。
3. 其余记录只有满足完整事实才返回 ACTIVE，否则抛现有 `ApiException(ApiCode.SERVICE_UNAVAILABLE, "管理员目录存在待核对的授权，请联系平台维护人员")`。

资格条件可放在同一方法的可读布尔表达式中，或很小的私有判定方法中。按照现有 `PlatformSuperAdminService.assertEligible` 的账号条件核对一致性。保留对调用者的当前授权验证、仅全平台范围可读取目录、最大 200 条以及真实版本。

增加内部异常诊断时，只记录异常 grantId/userId 和缺失事实代码。接口 message 只给下一步指引。避免在一般日志记录密码哈希、凭据、完整用户 DTO、核验材料或其他目录成员数据。

### 4.5 修好原测试夹具

当前 `superAdminDirectoryRequiresPlatformScopeAndCollapsesGrantHistory` 的 TARGET 只插入 ACTIVE 授权头便断言 ACTIVE。把该正向夹具改成完整授权。

1. 优先调用隔离测试已有 `PlatformSuperAdminService.grantInitial(...)` 创建合资格的完整授权。
2. 若需指定 grantedAt 来测排序，在完整授权创建后只调整测试库中的时间字段，保留角色/能力/范围。
3. 仅插入授权头的残缺记录移入独立反例，期望 503。
4. 原有学校范围 LIMITED 夹具保留真实角色、范围及最小能力。它出现在有权全平台读取者的目录时可 ACTIVE；LIMITED 自己请求全局目录仍 403。
5. 撤销记录的历史显示不强行要求“当前还持角色”，因为合法撤销本来就可能移除角色。

至少覆盖下表。

| 用例 | 期望 |
|---|---|
| 完整全平台超管 | 一条 ACTIVE，真实版本 |
| 完整学校范围超管 | 全平台读取者看到 ACTIVE；学校读取者直调全局目录 403 |

## 5. F3 手把手修 R3 通知源版本

### 5.1 同时理解生产者、worker 和读取者

依次打开以下位置。

| 位置 | 当前职责 |
|---|---|
| `community/application/ChatService.sendOnce` | 保存消息后，从 saved.revision 生成 CHAT_MESSAGE_SENT 的 sourceVersion，并在源业务事务中写 outbox |
| `community/persistence/ChatRepository.outbox` | 持久化事件类型与 payload_json |
| `notice/application/NoticeOutboxWorker.drain` | FOR UPDATE SKIP LOCKED 取待处理事件，构造聊天提及通知，再写 processed_at |
| `notice/application/NoticeOutboxScheduler.poll` | 调用 worker；默认测试配置不注册调度器 |
| `notice/api/NoticeController` | 原有 `POST /me/notifications/read-actions` 在已读服务调用后顺带调用 drain |
| `notice/application/NoticeService` | 公告路径写内容版本；通知列表直接投影库里的 source_version |
| `notice/persistence/NoticeRepository` | 写入/读取通知，唯一约束用于避免相同来源事件重复投递 |
| V016、V017、V029 | chat_message revision 范围、outbox、notification 和可空 source_version 的历史结构 |

不要直接把 outbox 载荷的旧 sourceVersion 替换成消息当前 revision。消息发出时的版本和后来撤回或修订的当前版本可能不同，通知必须对应它所代表的真实源事件。

### 5.2 在接收人循环之前精确验证版本

1. 先 parse 完整载荷，验证其为期望对象，提取 messageId、sourceVersion 和 mentions。
2. sourceVersion 必须是 JSON 整数节点、可精确转 int，且在原消息版本的 `1～999999999` 范围。小数节点 `1.0` 也拒绝，保持整数线类型。
3. 只有检查全部通过后才调用 intValue。将结果存为局部 int，在接收人循环中复用。
4. 缺失、null、字符串、布尔、小数、超范围和非正值均走坏载荷路径。该事件零条通知新增，processed_at 保持 null。
5. 合法 mentions 为空数组意味着无接收人，通常可以正常完成该合法事件。缺失或类型错误的 mentions 与合法空数组分别校验，别用遍历空 MissingNode 把坏输入当作正常空事件。
6. messageId 必须是非空字符串并满足现有 ID 规则；每个接收人按当前生产者支持的 ID 规则验证。保留合法生产者的原有归一化行为，对整个列表预先完成验证再开始 INSERT。

核心校验顺序如下，可内联或提成一个很小且确实复用的函数。

```java
JsonNode versionNode = payload.get("sourceVersion");
if (versionNode == null
        || !versionNode.isIntegralNumber()
        || !versionNode.canConvertToInt()) {
    // 本事件进入可核对的坏载荷处理，尚未执行任何 INSERT。
}

int sourceVersion = versionNode.intValue();
if (sourceVersion < 1 || sourceVersion > 999_999_999) {
    // 同上，不能补默认版本。
}
```

以上片段中的注释位置必须实现成明确退出该事件的控制流，不能写完注释后仍执行 intValue 或 INSERT。可以用已定义的局部验证结果或明确的载荷校验异常来组织，保持解析/验证阶段与数据库写入阶段清晰。

### 5.3 处理失败的事务边界

当前 `catch (Exception ignored)` 同时包住解析和所有接收人的 SQL。其注释声称“没有部分通知写入”，代码边界无法保证这一点。执行本修复时一起收窄异常范围，避免只修 isNumber 后留下一条不一致路径。

推荐沿用当前单个 drain 事务，执行以下顺序。

1. FOR UPDATE SKIP LOCKED 取到当前批次，保持原锁和批次大小。
2. 每条聊天事件先完整解析并验证版本和所有接收人。解析失败或明确载荷校验失败，记录最小诊断并 continue，此时没有写任何通知。
3. 对合法事件依次插入通知，沿用现有唯一键及 ON CONFLICT DO NOTHING。
4. 只有所有接收人插入成功后，再 UPDATE 此 outbox 的 processed_at，并增加成功处理计数。
5. SQL 异常不被坏载荷 catch 吞掉，向外传播，交给 Spring 的 drain 事务整体回滚。这样之前已插入的接收人、之前处理过的本批事件以及 processed_at 一并回滚。
6. 若实现者选择每事件 savepoint 或独立事务，需要证明真实数据库可恢复到事件开始前且锁/调度正确。本轮优先使用现有批次事务的传播行为，减少额外边界。

解析可以只捕获具体的 Jackson 解析异常，以及代码自己抛出的专用载荷校验异常。数据库写入位于这个 catch 之外。不要用范围过大的 IllegalArgumentException/RuntimeException catch 包住业务与数据库调用。

日志记录 outboxId、eventType 和例如 INVALID_SOURCE_VERSION 的原因码即可，避免打印原 payload、聊天正文、接收人列表或凭据。本轮坏事件保留待处理，回告说明其人工核对方法。

连续坏事件可能占满最早 50 条并阻塞后续批次，这属于保留待处理策略的可用性边界。执行者要统计并回告，提供有权运维核对的 ID/原因清单。若实际隔离样本显示该问题，应按业务签收的隔离或修复流程处理，并单独验收。不能为让队列继续而把坏事件标成“投递成功”，也不能在本轮随意新增一套未约定的自动重试/隔离状态。

原非聊天 eventType 的处理行为先按现有调用者和测试保留。例如调度自检使用 P66_TEST_EVENT 来检查投递入口，改变全事件类型分派要另作有证据的修改。合法 CHAT_MESSAGE_SENT 才进入上述版本校验。

### 5.4 回归测试分为类型、持久化和事务三组

**类型组**可以用参数化单元测试验证实际 worker 的 JDBC 调用，也可以在集成测试中用 JSONB 事件逐项驱动。至少包含下表。

| sourceVersion 载荷值 | 期望 |
|---|---|
| 1、2、999999999 | 通知持久化对应的原值，事件完成 |
| 1.75、1.0 | 不截断，零新增，事件待处理 |
| 2147483648、4294967297、100000000000000000000 | 无溢出环绕，零新增，事件待处理 |
| 1000000000 | 超出源版本业务上限，零新增 |
| 0、-1 | 零新增 |
| "1"、true、null、字段缺失 | 零新增 |

Mockito 在这里可以验证转换分支，但事务及 PostgreSQL 行锁必须用真实集成测试。

**持久化组**建议新增 `notice/NoticeOutboxSourceVersionIT.java`。按现有 test profile 关闭后台轮询，并显式调用 Spring 注入的 worker Bean。

1. 用隔离用户和原项目/聊天流程发一条真实聊天提及，查源消息、outbox、notification，核对 ID 和源事件版本一致。重复 drain 不多写通知。
2. 同一个事件包含两个真实接收人，两个通知都写相同源事件版本，processed_at 有值，计数符合 worker 约定。
3. 一条坏版本事件后跟一条合法事件，本批次里坏事件零新增且待处理，合法事件正常完成。避免只测“抛过异常”而没查表。
4. 创建合法事件后模拟消息当前 revision 变化，投递仍保留冻结事件版本。需要同时遵守实际消息变更的测试夹具关系。
5. 经 GET /me/notifications 读取自己的通知，sourceVersion 为 JSON 整数正值。公告与聊天提及分别验证。
6. 在原 `POST /me/notifications/read-actions` 做一次调用，确认它顺带使用相同 worker 逻辑并遵守当前会话/访问权限。注意 `readNotifications` 服务事务和随后 `drain` 的事务是独立调用，后者失败时前面的已读动作可能已经提交。测试和错误说明要记录该事实，不能把外层 5xx 当成已读动作未发生的证明。

**事务组**要检查至少一个真实失败发生在前面已写通知之后。

1. 准备一条两个接收人的合法事件，两个接收人均真实存在。
2. 在专用测试 schema 中用临时触发器为第二个接收人注入数据库失败，或采用仓库已有的真实 SQL 失败注入方式。测试资源放在 try/finally 清理，避免影响其他 IT。
3. 从测试事务外调用 Spring worker Bean，断言数据库异常向外传播。
4. 在 worker 事务结束后另查连接/事务，确认该事件没有任何新通知，processed_at 仍 null。若前面还有另一条已处理事件，同批次的相关变更也应回滚。
5. 移除失败注入后重试，一次成功写齐接收人并标记完成。再次执行不新增。

PostgreSQL 在事务内出现 SQL 错误后会进入失败状态，不能仅在 Java catch 后继续执行下一条 SQL 并宣称投递独立成功。测试必须看真实事务结束后的数据。

### 5.5 历史数据只先盘点，再按证据修复

类型修复不会自动修复已经落库的空版本或伪版本。以下是只读盘点 SQL，可先在隔离副本使用。

```sql
SELECT source_type, count(*) AS invalid_count
FROM notification
WHERE source_version IS NULL
   OR source_version < 1
   OR source_version > 999999999
GROUP BY source_type
ORDER BY source_type;

SELECT id, event_type, created_at,
       jsonb_typeof(payload_json -> 'sourceVersion') AS version_json_type,
       payload_json ->> 'sourceVersion' AS version_text
FROM notification_outbox
WHERE processed_at IS NULL
  AND event_type = 'CHAT_MESSAGE_SENT'
ORDER BY created_at, id
LIMIT 100;
```

第二个查询供受控维护使用，保存结果时脱敏。不要强制把任意 version_text 直接 cast int，坏字符串和溢出可能让盘点本身失败。第一项只能发现明显无效版本，不能发现“1.75 被截断成合法 1”这种语义污染，后者要回查原事件和可证明的源历史。

回填候选应包含 notificationId、sourceType、sourceId、原值、建议值及证据来源。只使用能证明原通知对应事件版本的记录。存在旧 outbox、chat_change 或公告内容历史时逐项核对对应关系，别把消息当前 revision 或公告当前 contentVersion 填进全部历史。无法还原的记录列出数量、来源与客户端处理待确认项，保持真实缺失。

如确有可自动证明的历史修复，单独追加幂等迁移或受控修复脚本，并补 V031→新迁移的升级测试。本轮代码防截断和读侧投影可先完成，历史数据清点、修复和真实来源跳转验收分别回告。L01 只有新写入、历史策略和客户端来源验证都完成后才能整体关闭。

### 6.3 重写拒绝证明的说明与表头

把 S2 第 5 节表头“能否证明未提交”改为“当前处理分支能否证明本次尝试未执行，以及历史状态限制”。在表格前加入明确前提。

> 当前拒绝语义仍未冻结，客户端确认集合为空。仅在协议已冻结、具体路由/协议版本/HTTP+code/产生阶段已逐项登记、该逻辑操作为首次业务尝试且没有更早未知时，已确认规则才可作为本次未提交的证据。再次尝试的 4xx、缺操作头、缺令牌或令牌过期不能清除原操作的未知状态。旧 P70 的 notSubmitted 需重新核对来源，CONTRACT_ERROR 不属于通用证明。

| 场景 | 表格应表达的语义 |
|---|---|
| Jackson 未知字段拒绝 | 本次读入分支未调用业务；原编号可能已有历史提交，是否可进入确认集合另需冻结 |

| 缺令牌或查无令牌 | 当前拒绝分支没有新执行；旧提交与缓存过期、令牌清理可以同时存在 |
| 令牌过期 | 核销失败的当前事务应回滚；历史提交另查 |
| 已消费或上下文不符 | 已消费可来自先前成功，保留未知并读原回执 |
| 版本/状态冲突 | 本次事务的结果，可能已有原操作或其他操作改变目标 |
| 同键异文 | 当前请求冲突，原键绑定操作可能已经成功 |
| 请求与响应大小错误 | 必须区分请求前置 413 与事务提交后响应侧 413；HTTP+code 可重合 |
| 5xx、代理错误、断连、损坏回执 | 结果未知，按原编号/原键核对 |

至少在夹具说明中加入“首个回包丢失，后续再收到 4xx，客户端仍保持未知”的反例。登记产生阶段和数据库副作用证据，并在签收栏保留实际负责人与日期。只有实际签收后，Android 才能逐项登记确认集合。
