## R1 · P2 · A14 仍把不可用的超管授权投影成 ACTIVE

定位在 `platform/application/PlatformReadService.java:383` 和 `platform/persistence/PlatformRepository.java:765`，Java 路径相对 `src/main/java/cn/gulupai/server/`。

现态目录已经按用户去重，但 `superAdmins()` 的 SQL 只取授权状态及账号启用状态，`directoryStatus()` 在授权未撤销、账号未停用时直接返回 ACTIVE。缺失 SUPER_ADMIN 角色、授权范围/能力残缺、身份资格或凭据不再可用的记录仍能进入该分支。当前 `PlatformReadPrivacyP66IT.superAdminDirectoryRequiresPlatformScopeAndCollapsesGrantHistory` 甚至给 TARGET 只插入一条 ACTIVE 授权头，没有实际角色/能力/范围，就断言目录 ACTIVE，未覆盖残缺授权的真实有效性。

复现场景为在隔离库授予一个正常账号超管，随后构造“保留 ACTIVE grant 但缺 SUPER_ADMIN 角色”的已有异常状态。A14 返回该用户 ACTIVE，同账号能登录普通会话但访问管理账号列表是 403。现有初始化与最后恢复管理员判定已经将这种状态视为残缺，目录表达与真实治理资格脱节。前端按目录状态提示人数或支持操作时，会把不可用成员显示为有效成员。

修复步骤建议如下。

1. 共同确定目录 status 的有效资格语义，并在查询中读取所需真实角色、身份、凭据、授权能力及范围事实。保持“有效管理员”与“能恢复全平台的管理员”两个判定的区别，合法学校范围管理员可有效，但不能替代全平台恢复管理员。
2. 现有 ACTIVE/REVOKED/DISABLED 无法准确表示残缺状态时，与前端确认新投影或明确返回不可就绪。避免通过 ACTIVE、伪造撤销或静默隐藏异常来迁就 DTO。
3. 补缺角色、缺范围/能力、身份不可用、账号停用、重授等用例，并确认正常授权仍正确去重。保留写入端的最后有效管理员锁和判定。

## R2 · P2 · 续页重新获得 15 分钟，原快照到期时间未继承

定位在 `platform/application/PlatformReadService.java:275` 和 `:294`，以及 `common/pagination/CursorService.java:43`。

`CursorService.resolve()` 已返回 `expiresAt`，并提供继承该到期时点的 `create(..., expiresAt)` 重载。读取服务续页仅取原 ids 和 position，创建下一页仍调用无期限参数的重载，该重载重新使用 `clock.instant()+15min`。因此旧快照快到期时续页，新游标仍可把同一快照延长。新增当前范围检查有作用，但未修复期限继承。

隔离探针将第一张未过期游标的 expires_at 调到“当前时间加 60 秒”，立刻请求第二页。第三页游标的 expires_at 又回到约 15 分钟后，相比原到期点延长超过 10 分钟。

修复时在续页分支保存 `resolved.expiresAt()`，下一游标调用已有带绝对到期时间的重载。首页按原 TTL 创建，续页沿用首页到期点。补固定时钟用例，断言多次续页期限相同、原到期时所有续页均返回 CURSOR_EXPIRED，同时保留新加的范围/状态变化失效规则。

## R3 · P2 · L01 的 outbox 会截断小数，回告的整数校验描述不成立

定位在 `notice/application/NoticeOutboxWorker.java:47`。首轮回告第 47 行写“只接受 JSON 整数”，代码实际使用 `isNumber()` 后接 `intValue()`。Jackson 的 Number 包括小数，`1.75` 在这里转为 `1`。超 int 范围值也没有精确转换或正数范围校验，缺字段则存 null。新通知因此可能带一个与实际源版本不符、被截断的版本。

探针对真实 `NoticeOutboxWorker.drain()` 提供小数版本载荷，并捕获其对 JDBC 的通知插入调用，观察到 source_version=1。该探针验证实际 worker 的入库参数转换，未将 Mockito 当作真实通知投递或 PostgreSQL 存储的验收。

这属于指南中已经列明的 L01 待补项，首轮回告也保留了“待补”状态。无需把它重复认定为 S1 新引入回归，但应立即更正“已核实事实”，并将类型修复加入明确任务。

1. 用精确整数、可转 int、业务版本正数范围检查读取。合法来源还应从生产者及真实源事务核实，不能只让数值通过类型检查。
2. 对无法还原的旧载荷、缺失/非正值和超范围输入，采用已冻结的异常处理或可核对修复策略，避免补假 1。检查异常处理时 outbox 是否仍被错误标记完成。
3. 补整数、小数、溢出、0、负数和缺字段测试。分别验收公告与聊天提及的新写入、历史修复、通知列表和跳转。

## S2 草案还需修正的表述

- S2 第 9 行声称 A17 除密码外的字段均按动作白名单校验。当前 `AdminCommands.reauthentication()` 检查动作需要的字段，但不会逐项拒绝其他动作才适用的已知 DTO 字段。比如教师审核请求附带 status/reason/targetUserId 会被对应分支忽略。应写清“未知 JSON 字段会拒绝，部分已知但动作不适用字段当前会被忽略”，并把严格动作字段校验留作 S3 的明确任务。payloadDigest 提供空字符串或全空白也会跳过比对，草案中的“提供时必须一致”应补足这个现状。
- S2 第 5 节“能证明未提交”须明确只证明本次具体处理分支，不能证明原 operationId 从未提交。将 P71 的协议已冻结、逐项登记、首次尝试、无更早未知和旧 notSubmitted 重新核对条件写入该节。缺操作头、缺令牌、过期等 4xx 不得清除原先未知记录，不能因为表里写“能”就直接打开终拒白名单。
- S2 草案当前未签收，A17 六段线摘要、目标类型映射、缺令牌回放、A16 授权代次及持久 key 绑定属于下一批。首轮明确没有实现这些内容，审查按阶段区分，不作为本批“漏写代码”重复登记。后续依赖项须完整签收，包括操作编号、协议标记及 key 保留期策略。
