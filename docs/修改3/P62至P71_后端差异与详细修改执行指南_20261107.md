## 4. 批次一的管理读取修改

### 4.1 恢复资格与本人投影

1. 在 `PlatformViews.AccountUser` 增加真实 JSON boolean `restorationEligible`，由 `PlatformReadService.user` 投影到 `data.user`，先与 Android 确认字段嵌套。列表 A02 可维持原结构。现有 `ManagedUser` 已读出 accountStatus、disabled、identityStatus、eligibility、hasPassword 和 revision。
2. 提取一个可供详情和 `PlatformWriteService.changeStatusLocked` 复用的纯账号资格判定。当前写入要求 DISABLED、`disabled=true`、`eligibility_source=ADMIN_DISABLED`，该来源由已激活账号停用时写入。待审、驳回、IMPORT_DISABLED 和 LEGACY_DISABLED_* 全部 false。逐条核查导入、审核、改凭据等路径是否能让停用前的资格失效。若业务确认恢复还要求有效凭据或特定身份状态，同步写入同一判定，结合现有学生/教师合法状态验证，避免直接照搬“超管必须 VERIFIED”到所有用户。
3. `restorationEligible` 表示目标事实。A03 仍需 ACCOUNT_READ；A04 仍需 ACCOUNT_MANAGE、当前范围、正确版本、再认证及事务内复查。请求注入 `restorationEligible` 或身份/角色字段应拒绝。测试有资格/无资格、投影后资格变化、恢复后必须新登录及历史停用不被批量恢复。
4. 本人和登录/刷新共用 `UserProjectionService`，原业务字段继续保留；本人用 `capabilities`，管理账号用 `platformCapabilities`。验收有效超管显式 ACTIVE + VERIFIED。登录遇正确凭据且停用时按实际业务码处理，现有刷新及不少业务入口会因会话撤销或当前状态返回 401 `SESSION_EXPIRED`。回告实际分流，禁止为改文案混用 identityStatus。

### 4.2 范围、列表和审计

1. A02/A06/A09/A13 复用 `PlatformReadService.page` 与 `CursorService`。当前 total 取授权过滤后 ID 快照大小，超过 5000 明确 `COLLECTION_TOO_LARGE`，不是当页长度。冻结快照语义与并发变更处理，执行者优先采用续页时重新核对当前范围及筛选，必要时返回 `CURSOR_EXPIRED` 引导从首页重读。当前用户、申请、课程按 ID 批量装载没有统一重新过滤；验证账号转校、范围收缩、课程状态变化及申请状态变化。若发现旧快照仍返回越权行，用 SQL 批量范围约束或安全失效修复，连同 total/游标一致性一起测。A13 已有范围查询及游标版本，保留。
2. A03 除目标账号所属学校外，核对附带的 `grants/teachingCourses` 所指课程范围。当前按 userId 查询，若数据允许跨校关系，按课程真实 schoolId 过滤；摘要计数同样按有权范围，防止间接泄露。A10 确认 `claims` 只投影申请状态，`grants.active` 语义须与当前授权有效性一致，过期与撤销均不能放行。历史保留，管理详情只提供需要的元数据。
3. A14 当前只验能力，`PlatformRepository.superAdmins` 查询全库含历史授权，现有 ACTIVE 映射仅看授权和账号启用。建议首期完整全局目录只授全平台范围的操作者，并对学校范围明确 403；若业务确需学校目录，先冻结“有权子集”的语义和 Android 提示，再按授权记录实际范围过滤。当前目录条目只用 userId 标识，撤销后重授会有同一用户多条。建议现态目录每用户一条，优先真实当前授权、无当前授权时显示最近撤销；历史从审计读取。该规则和 ACTIVE 资格条件须共同确认。测试只有学校授权、重授、多条历史、超限、零 ACTIVE、缺角色/核验的残缺授权。零 ACTIVE 按真实不可就绪处理，最后有效管理员仍以事务内判定为准。
4. `AdminAuditMapping` 和 `ManagementAuditEvent` 负责审计名和可见范围。成功回执里的 action 是请求动作，A13 审计例为 TEACHER_APPLICATION_APPROVED/REJECTED，result 为 SUCCEEDED/REJECTED/FAILED。A15/A16 的审计内部关联真实 grantId，回执 resource.id 为 userId。可关联但两者不相等。保留 A13 有权可见才可读、按目标范围、敏感核验原文不进通用审计和历史 CLI 来源不伪造。每次验收记录原 X-Request-Id、operationId 和 auditId。

| 兼容与版本 | 旧调用和旧回执按当前 P66 协议。 | P71 写入、再认证及未知重试门禁关闭。 | 有兼容需要时由双方指定明确的协议标记及取值，在 A17/写入/回执核对中一致使用。核对现有调用者与部署兼容期，再定是否保留两套入口适配。 |

此表是实施提案。若双方同意开放版客户端直接改用现有完整规范 JSON 摘要，可省去双摘要适配，并在冻结表写明最终字段、摘要向量和兼容策略。两种方案择一执行。若要求保持 P71 最小 A17 正文，签发时只能登记线摘要与服务器已核实的上下文，写入时以完整业务正文重算并核对。那条方案需另定存储和绑定设计，并先补齐 A04 方向及 A16 授权代次，避免签发者只见一段无法绑定方向的摘要。不要用“第一次重试时拿最新版本”替代原操作。

### 5.2 推荐路径的具体改法

1. 在 `AuthController`、`PlatformAdminController` 读取双方选定的协议标记。对有意保留的旧协议继续接受现有字段和类型；新协议严格按动作白名单校验适用字段，拒绝未知标记、矛盾的 status/decision、额外业务上下文及模糊回退。同一代码路径归一化到现有 `AdminCommands.CanonicalCommand`。旧格式验证失败要明确拒绝，不能自动试第二种哈希。
2. 动作由 A17 解析并核对 targetType，写入则由实际方法、路径及 DTO 归一化。A04 用真实 `ACTIVE/DISABLED`，A08/A11 用 `APPROVE/REJECT`。必须拿 Android `AdminOperation.digest()` 和 A04 请求夹具验证第 5 段。推荐将 A04 的状态作为该段并在 A17 提供同一状态。若客户端当前该段为空，开放版需同步调整或使用完整后端摘要，验收用同目标同版本同理由的相反状态证明不能复用令牌。
3. A05/A15 无 expectedRevision，六段摘要中的第四段为字符 `0`。服务端推导 `TARGET_ACCOUNT` 或 `NO_ACTIVE_GRANT`，写入时重查真实前置条件。A15 由 targetId 推出唯一目标 userId，与实际正文 targetUserId 相同。A16 在 A17 保存当时实际的 grantId 或等效授权代次，在撤销事务对当前授权比对。V031 重授新行的 revision 可再从 1 开始，单用 userId 和 revision 无法区分两次授权。若需要列，新增迁移并说明旧未消费 A16 令牌在协议切换时如何拒绝或到期；保留旧已提交回执。
4. 线摘要使用六段严格串联。文本以双方约定的 trim 规则处理一次，同一规范值用于线摘要、业务写入和服务端完整指纹。现有 `AdminTexts` 用 Java `strip()`，Android 交接写 trim。确认 ASCII 空白、全角空白、CR/LF、代理对和 UTF-16 长度，禁止平台换行、Unicode 隐式正规化或空尾段丢失。ID 和枚举不允许嵌入换行，版本以十进制精确整数编码。维持 1～500 长度的实际写入理由/说明。
5. A17 校验密码非空且最多 128 个 UTF-16 code unit，保留原字符和首尾空格，不套注册的 8～64。校验实际已登录操作者及动作能力，沿用账号/IP 限流和安全密码编码器，外部错误不泄露凭据或核验材料。检查 `AdminReauthenticationService.reauthenticate` 当前仅显式判 null，按新协议补空值/上限测试。限流测试使用时钟与真实限制配置，保留 `Retry-After`。
6. 对新协议重算并核对必填 wire 摘要后，沿用服务端完整 canonical digest 绑定归一化后的动作、目标、版本或前置条件与业务内容。令牌只向调用者回传，库存安全指纹，绑定 actorId、真实 auth_session.id、operationId 和上下文。短时 TTL 当前 5 分钟，使用服务端 Clock。回包 `reauthToken/expiresAt` 即可沿用；若选择回显上下文，用当前线协议的 action/targetType/digest，字段逐项一致。绑定是否有效由错绑反例与库内证据验证。
7. 在写入事务中验证当前账号、会话、能力、目标及范围，核对正确上下文与未用令牌。取业务锁后到期也应整笔回滚，保留 `verifyUnused` 加锁及 `consume` 的期限条件。普通 accessToken 刷新沿用原 auth_session.id；新登录是新会话，不能凭旧令牌执行未提交业务。同一操作者新会话可否读原已提交回执按当前授权和冻结规则处理。

下面是提议的六段摘要核对向量。每个数组表示六个原样连接的字符串，JSON 的 `\n` 表示字段内单个 LF。前两种带非空正文，最后一种空理由用于摘要函数单测，写入仍会拒绝空理由。

## 6. 批次二的回执、幂等和原结果核对

### 6.1 七类回执与真实版本

| ID | 写入业务正文，另带 reauthToken | P71 回执 targetType / id | 业务完成状态和版本 |
|---|---|---|---|
| A04 | status、reason、expectedRevision | USER / 目标用户 ID | ACTIVE 或 DISABLED，与请求相同。用更新后的 app_user.revision。 |
| A05 | reason，无 expectedRevision | USER / 目标用户 ID | 当前保持关闭。受理语义、目标资源的 status 和 revision 来源在第 8 节冻结。 |
| A08 | decision、note、expectedRevision | TEACHER_APPLICATION / 申请 ID | APPROVED 或 REJECTED，申请版本；原库 ACTIVE 映射 APPROVED。 |
| A11 | decision、note、expectedRevision | COURSE_CLAIM / 认领 ID | APPROVED 或 REJECTED，认领版本，与任课关系的 ACTIVE 分开。 |
| A12 | reason、expectedRevision | ADMIN_GRANT / 班级授权 ID | REVOKED，原授权新版本，原课程历史保留。 |
| A15 | targetUserId、reason，无 expectedRevision | SUPER_ADMIN / 目标用户 ID | ACTIVE，真实平台授权初始 revision；旧授权历史保留。 |
| A16 | reason、expectedRevision | SUPER_ADMIN / 目标用户 ID | REVOKED，被撤授权的新版本，必须是原授权代次。 |

通用 `data.operation` 必含原 `id/action/targetType/targetId`、`status=COMMITTED`、`resultingRevision` 和真实 `auditId`。 `data.resource` 至少为 `id/status/revision`，与目标和结果版本相同。有 expectedRevision 时版本严格递增并且在约定范围，达到上限按既有异常/冻结规则处理并回滚。基于 `PlatformViews.AdminOperationReceipt` 和 `PlatformWriteService.Outcome` 复用现有构造。示例为首个 A08 联调正例。

```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "operation": {
      "id": "op_example",
      "action": "TEACHER_APPLICATION_DECIDE",
      "targetType": "TEACHER_APPLICATION",
      "targetId": "application_example",
      "status": "COMMITTED",
      "resultingRevision": 4,
      "auditId": "audit_example"
    },
    "resource": {"id": "application_example", "status": "APPROVED", "revision": 4}

```

已有回执和新回执共享同一逻辑操作。建议按当前模式持久化内部真实回执，Controller 在返回时将受影响的 targetType 映射成已协商的线类型，旧回执从同一内部对象映射，不批量改写历史或分裂操作主键。若必须新增回执字段，验证加密幂等快照及 `admin_operation.receipt_json` 的旧结构可读，按需要用历史 DTO 或明确版本适配，保留严格反序列化。HTTP 写出可能在事务提交后失败，回包丢失需走同编号核对。

### 6.2 执行顺序与原子性

1. 保留锁序。现有顺序为公共幂等锁（操作者、方法、路径、key）→ `platform_admin_lock` → actor + operationId 的事务锁 → 核验未使用再认证行 → 业务资源锁。审批/撤销内部保持广场先于认领/授权等现有顺序。核销实际发生在业务之后，仍在同一事务；审计、令牌消费、业务、`admin_operation` 与幂等快照任一失败整体回滚。CLI 路径直接共用管理约束锁。
2. `IdempotencyService.execute` 现有入口已把 token 排除在 `BusinessFingerprint` 外，缓存按 actor/method/path/key 去重，默认 7 天。 `admin_operation` 按 actor + operationId 保存已提交记录并比较完整摘要，不应随着短期缓存到期丢失原回执。现有 `execute` 在所有分支先要求非空 reauthToken，已有回执分支实际不校验令牌的消费或 TTL。建议共同确认已提交回放可省略 reauthToken 的行为，将令牌必需检查放入未提交分支，且先按当前权限和原范围检查回放。正向证明用已消费、已过期、已清理、缺失及重新签发的令牌分别测试；未提交一律要求当前可用令牌。
3. 同一操作已完成后，可能因目标已审批、版本递增或授权已撤销而无法再过 A17 的 prepare。原回执读取应在验证当前权限、目标范围和同正文后返回存档结果，绕开已完成业务的前置条件。对超管授撤沿用原操作的 auditId → grantId → 授权范围，防止取当前新授记录误判旧回执。核对短期缓存命中和 `admin_operation` 兜底两条路径的一致授权，补测与范围收缩并发，确保只取在该授权时点可读的数据。
4. 冻结 operationId/key 的关系和保留期。当前 `admin_operation` 不存幂等键，短期缓存过期或跨不同路径后不能靠它阻止“同 key + 新 operationId”执行。若开放协议要求管理动作的 key 在 actor 下跨路径、跨缓存 TTL 永久归属，新增管理专用的持久绑定，建议 actor+key 唯一且 actor+operationId 单一归属，存 key 安全指纹和完整命令摘要。放在现有管理锁后同事务比较/写入，冲突回 409 `IDEMPOTENCY_KEY_REUSED`。旧数据无可证明的 key 时保留旧 operationId 回执与兼容边界，不能凭空回填。另一可选协议是双方明确规定新操作的 key 等于 operationId，并在入口强制，旧协议仍按独立标识处理。择一并验证跨路径、跨动作、缓存到期和同键异文；公共幂等行为保持原样。
5. 客户端超时后的最小恢复契约可以用原 POST、同 operationId、同 key、同冻结正文读取回执。验证正向回放不改变任何业务行、不写第二条审计、不消耗新令牌。若需要专用只读查询，冻结其方法、路径、DTO、当前会话/动作权限、原作用域、存在性处理、并发与保留期，再实装。后台仅给有权操作员按 operationId + actor、auditId 和审计 requestId 核对，明确查询视角与可能延迟。未找到、暂不可见和正在提交均不单独证明未提交。登记实际使用的查询手段，别先发明路径让客户端接。

### 6.3 与角色及状态有关的验收

- A08 仅处理真实待审申请，禁止自审，两条独立操作竞争同一申请仅一条提交。通过原子激活账号并授基础 TEACHER，无自动任课、HELP_CONTENT_WRITE、SUPPORT_HANDLE。A11 保持学校核验、唯一当前任课及转交由本人接受。A12 撤销后课程原局部能力不再生效，项目、人员记录、成绩、旧公告均保留。
- A15 当前 `PlatformRepository.insertGrant` 写全套平台能力，范围按操作者为平台或目标学校。与前端和业务确认这是允许的委派策略，尤其“持 SUPER_ADMIN_MANAGE 但没有其他能力”的学校/平台操作者是否可授出自己没有的能力。若不允许，选择限制 A15 给足够授权的管理员或按确定的授予配置约束，禁止请求自选 roles/capabilities。
- A16 新执行当前校验目标用户学校并额外保护平台范围授权。验证目标用户转校、被撤的是其他学校原授权等场景，用原 grantId 查实际 scope 复核，保持与回放的范围边界一致。A16、A04、CLI 导入及新增的重置/改密路径都要复核最后有效恢复管理员不变量。
- 最后有效恢复管理员沿用实际判定和锁。可登录、有效 SUPER_ADMIN 角色/授权、全平台范围、所需管理能力及凭据条件缺一不可。用两名管理员并发停用/撤销相互竞争的测试，断言至少一人可实际登录和恢复管理。对停用/实际改密必须撤旧会话；撤销平台或局部资格后老 accessToken 及其 refresh 不能拿回旧权限，仍有其他业务资格时测试这些资格的原有行为。

## 7. 错误分层与未提交证明

下表用来回告产生阶段。上线前客户端的 `REJECTION_SEMANTICS_FROZEN=false`、确认集合为空仍按交接状态处理。回告按路由、协议版本、HTTP 状态、code 和明确产生阶段登记，当前表不给 Android 自动放行。

| 当前 HTTP / code | 已核对的产生阶段或实际例子 | 联调与证明边界 |
|---|---|---|
| 400 `MALFORMED_JSON` | MVC 请求读入/绑定失败，`GlobalExceptionHandler` 也将部分参数类型绑定错误映射到此码。 | 用真实请求证明该分支未进入管理事务。仅登记已固定的路由与触发条件。 |
| 400 `IDEMPOTENCY_KEY_REQUIRED` | `IdempotencyService` 在执行动作前检查缺键或非法长度/字符。 | 可证明当前校验分支未调用业务。历史同编号状态另查。 |
| 413 `PAYLOAD_TOO_LARGE` | 请求大小过滤可产生；响应序列化后的大小限制也可产生同码。 | 单凭 HTTP+code 无法区分两阶段。若要纳入候选，需先建立可区分且已冻结的请求侧契约，并验证真实代理回包。 |
| 422 `FIELD_NOT_ALLOWED` | Jackson 读入拒绝未知/只读字段。 | 针对 A17 和各写入夹具验证读入失败、无业务/审计/回执副作用，并确认实际代理原样转发。 |
| 422 `VALIDATION_FAILED` | 请求类型绑定、Bean Validation、命令字段/版本检查等多个位置。 | 按具体动作和来源分组。即使本次未写，也不能清除旧未知；只有双方确认的前置分支才可登记。错误可用最多 20 个 `fieldErrors`，不返回填入值。 |
| 403 `REAUTH_REQUIRED` | 缺 X-Operation-Id、缺令牌或指纹查无记录等。 | 回放前后顺序可能变化。缺令牌可与已有提交并存，需先读已有回执。不得将此码视为“该 operationId 从未成功”。 |
| 403 `REAUTH_EXPIRED` | 取令牌锁后检查，或执行事务中核销时发现超时并回滚。 | 两个阶段分别做无变更断言。旧成功回执与失效令牌可同时存在。 |
| 403 `REAUTH_CONTEXT_MISMATCH` | A17 上下文/摘要不符，或写入令牌绑定不符及已消费。 | 已消费可来自先前成功，尤其不能给通用未提交证明。分开登记 A17 与实际写入路由。 |
| 401 `INVALID_CREDENTIALS` / `SESSION_EXPIRED`；403 `FORBIDDEN` / `SELF_REVIEW_FORBIDDEN` / `ACCOUNT_DISABLED` | 本人密码验证、认证过滤、当前账号/角色/范围检查、动作回避。 | 对齐旧会话及权限丢失后的实际行为。失去读取权限不等于历史操作未提交。 |
| 404 `PATH_NOT_FOUND` / `RESOURCE_NOT_FOUND`；501 `ENDPOINT_NOT_IMPLEMENTED` | 未匹配管理路由、目标不存在、合法 A05 明确未开放。 | 分别给脱敏示例。旧结果可能因权限、资源或版本变化暂时不可查。 |
| 409 `REVISION_CONFLICT` / `INVALID_STATE_TRANSITION` / `LAST_ACTIVE_SUPER_ADMIN` / `IDEMPOTENCY_KEY_REUSED` / `OPERATION_IN_PROGRESS` | 业务条件、约束或同键正在处理/已有回执。 | 保留真实业务码。并发、重复或旧版本都可能说明已有别的操作结果，需要按原编号核对。 |
| 429 `RATE_LIMITED` | 限流层，例如 A17 账号/IP 密码失败窗口。 | 验证实际 Retry-After。限制当前请求，历史状态另查。 |
| 5xx、断连、网关错误、空/错回执、`CONTRACT_ERROR` | 可能发生在业务前、回滚后或提交后。 | 客户端保持结果未知。提交后断开/回包损坏的测试必须从原编号找回已提交回执。 |

证明矩阵至少包含四类反例。首次请求可证实的前置拒绝，已成功但回包丢失后再收到相同 4xx，响应侧大小限制与请求侧 413 重码，代理生成的未知来源错误。后端断言数据库的业务版本、审计、已提交操作、幂等结果和令牌消费。客户端只在已冻结、明确列入集合、首次尝试且没有更早未知时使用证明；P70 本地历史的 `notSubmitted=true` 逐条重新核对。 `schemaVersion/factsKnown/businessSent/outcomeUnknown/notSubmitted/attempts/origin/sessionId` 等本地字段不作服务端授权数据，真实会话绑定使用 `auth_session.id`。

## 8. A05 安全重置独立设计与开发边界

1. 维持现有合法请求的明确 501，A05 从开放范围单独排除。若其余六类先开放，Android 后续版须有 A05 单独禁用策略，并覆盖确认、再认证和恢复重试三个入口。在协议评审中决定 A17 对尚未支持动作如何响应，保证客户端不会把拿到再认证令牌当作重置可用。待确定可用交付渠道、接收人身份核验、一次性兑换界面/API、恢复账号规则、TTL 和作废策略后，再在现有路由实现受理。
2. 方案必须区分两次事务。管理受理写真实重置请求、截止、交付任务或交付证明、审计和幂等回执。安全渠道中的兑换事务用凭据指纹、状态/到期与并发 CAS 确保一次成功，写新密码哈希并撤销全部旧会话；账户若不再有资格，按冻结规则失败。交付由真实安全渠道承接，受理后的交付失败需要可核对状态和补偿机制。若实际只能异步入队，先冻结独立的交付/状态语义和 App 界面，不能让“入队”伪装成已交付或已改密。
3. 返回 `requestId/targetUserId/expiresAt/delivery` 加 `operation/resource`。requestId 是重置业务编号。resource.id 是目标用户，优先使用事务内读到的真实账号 revision 和当时状态，重置受理不必强增账号版本。当前通用校验如何表达“重置已受理”与目标状态需 Android 明确确认；若希望 resource 是重置请求对象，要改双方 DTO。确认 delivery 值域、真实 TTL、客户端时钟偏差和过期后读取原回执的行为。前端当前要求 delivery 长度 2～40，过期时间解析后晚于本机现在且严格早于未来 30 天。
4. App、一般审计、管理回执、日志和代码夹具不暴露临时口令/兑换 token。验证同编号重放不再次交付；同 key 异文冲突；过期、换账号、兑换并发、撤销重置、交付失败及实际改密后旧 access/refresh 失效。对最后可恢复超管测试交付失败或凭据作废不会使其失去恢复能力。需要加表时在 V031 后增量迁移，保留账号与授权历史。

## 9. 数据库、CLI 与非本批次事项

- 复用 V031 的 `platform_admin_grant/capability/scope`、`platform_admin_lock`、`admin_reauthentication` 和 `admin_operation`。只在确认授权代次、持久 key 绑定或重置表确有需要时追加迁移，当前候选号从 V032 起并以工作树最新编号为准。历史迁移不重写。升级测试涵盖 V030→当前及 V031→新版本，保留学生/教师账号、课程、项目、提交、成绩、授权历史、审计、旧回执和现有凭据哈希。检查回退/滚动部署时的旧版本兼容，并更新 `FlywayMigrationIT`、`P66LegacyUpgradeIT`、测试表清理清单和路由覆盖清单。
- 首位超管用 `AdminCliRunner` 的 `init-super-admin` 和 `PlatformSuperAdminService.grantInitial`。隔离库先确认现有独立账号、已激活/核验、有效凭据、受信 CLI 操作者，再 dry-run，执行后复查同一授权、七项能力、全平台范围、审计及真实登录投影。重复执行同目标应已激活且不新增；残缺角色、能力或范围显式报冲突。真正部署使用正式受控操作者与批准流程。 [现有命令、权限与回告](P66_接口差异与联合契约.md)
- 保留 `AdminImportService` 对已有超管的敏感变更保护和批次锁；复查新路径和旁路更新是否共享全局锁。历史 `LEGACY_DISABLED_UNCLEAR` 等来源不批量恢复，CLI 历史审计仍留真实来源。单测和集成测试用隔离账号及构造凭据。
- 保留 CLASS_ASSISTANT 作为公告发布身份，班级助理的七项能力仍为 TEAM_SUMMARY_READ、PERSONNEL_READ、PERSONNEL_HANDLE、ANNOUNCEMENT_WRITE、MATERIAL_REQUEST_HANDLE、COURSE_JOIN_CODE_MANAGE、COURSE_MEMBERSHIP_REVIEW，受课程范围、期限和回避限制。平台能力不混入局部授权。平台管理路由不得默认访问私人聊天、案情、互评、成绩正文或代做业务动作。
- 受理路由/单人员事项授权的管理 UI、助理候选选择与有效期选择、独立教师资格撤销、本人改密/激活、已加入课程专用投影均需各自冻结。后端分别复用 `OperatorGrantAdminService`、`PersonnelCaseGrantAdminService` 及原教学/课程规则，客户端有真实调用和流程后再验收。当前 P71 占位页面及本地 Recovery 机制单独登记。

### 10.2 隔离环境的真实四账号角色链

1. 超管登录，记录本人角色/能力及准确协议。学生和教师在实际部署做匿名注册，教师待审时用正确密码不能登录。超管从列表进入详情，经 A17 和 A08 审核，记录响应和可核对的 A13。
2. 教师用已核验账号登录，未获任课时对课程教学操作拒绝。走原认领与治理决定，再验证唯一真实任课、转交路径与有权课堂操作。
3. 教师给另一有效学生任命本课助理。助理只能操作授权项及本课。检查自审、跨课和无成绩权限。普通学生实际使用课程、项目或作业流程，验证平台角色未混入原规则。
4. 超管紧急撤销该助理授权，保留同一旧会话做权限请求与刷新。验证权限不能恢复、历史记录保持。另测管理账号停用/恢复、最后有效管理员保护、回包丢失后同编号回放及回执与审计关联。
5. 前端以交接 §13～14 的实际门禁为准。仅登记已经核对的准确 API 来源、部署版本/迁移号和冻结协议；发布明确开放的后续客户端版本。原 P71 的再认证/首笔写入/未知重试仍关闭，后端上线或 GET /health 200 不会改编译常量。先把根地址与 /api/v1 规范化、旧本地未知记录和 notSubmitted 来源核对、客户端拒绝组合与开放策略落实到真实候选包。
