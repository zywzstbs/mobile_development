## T01

编辑先锁定原条目，再用库里的 `audience` 和 `square_id` 核权，然后才比较版本。请求里的 `squareId` 不能改核权对象，也不能改归属。`scope` 或 `squareId` 与原记录不一致时拒绝，原标题、正文、`square_id`、`revision`、`content_version` 都不改。

通用条目只接受当前有效且 `scope_type=GLOBAL` 的 `HELP_CONTENT_WRITE`。广场范围的同一能力不能改通用帮助。课程条目只接受原课程当前教师，全局帮助能力不能代替教师资格。

`audience` 与 `scope` 不一致，或通用条目带着广场、课程条目没有广场时，接口直接拒绝，不用请求把归属改掉。V024 只在二者不矛盾时把 `scope` 对齐到 `audience`。

## T02

举报读取和处理走 `ContentReportAccess`，不使用求助工单的资源类型、回避或 `SUPPORT_HANDLE`。举报者读取本人记录。处理者必须同时满足：账号未停用、仍是 `assignee`、当前授权覆盖该举报广场。

第一轮写明 `CONTENT_REVIEW` 与 `CONTENT_REPORT_HANDLE` 都能处理。本轮保留这个映射，但两种能力都只按授权自己的范围生效：`GLOBAL` 覆盖全部，`SQUARE` 只覆盖同一广场。`CONTENT_REVIEW` 不会被自动当成全局授权。追溯不到广场的历史举报只接受 `GLOBAL`。

停用账号仍由 `CurrentUserPolicy` 返回 `SESSION_EXPIRED`，不会带着历史指派读到片段。

## T03

HELP-04 和 HELP-05 读取 `Idempotency-Key`，用现有幂等服务绑定用户、`PUT`、请求路径和正文。成功回放先重新做 T01 或反馈阅读资格检查，再返回原结果，不按旧 `expectedRevision` 再改一次。同键不同正文返回 `IDEMPOTENCY_KEY_REUSED`。

反馈仍按文章、用户、正文版本做业务 upsert。这不能代替请求幂等。正文后来更新后，旧键回放仍返回当次结果；新键若还带着旧正文版本则拒绝，不新增反馈。

这次上线前已经成功、但没有幂等回执的编辑和反馈，无法靠补造回执恢复。

## T04

通用包版本改存在 `help_content_pack`。已发布通用帮助的内容、适用版本或发布状态变化时，在同一事务里加一。课程条目不推进这个版本。幂等回放不调用推进。读取使用可重复读，版本和条目来自同一次快照。

不再使用 `max(content_version)`，也不用读取时的当前时间。`updatedAt` 是最近一次推进的时间；没有条目时也用行上记下的时间。

旧客户端可能缓存过 `max(content_version)`，空包时旧实现返回 1。V024 初始版本取已发布通用条目的最大 `content_version` 再加 1；没有条目时取 2。因此新版本大于旧缓存里可能出现的最大值。`appVersion` 只决定本次返回哪些条目，包版本是全局的。客户端更换筛选后应按契约重新取全量，不能拿另一个筛选的 `knownVersion` 来判断。

写入路径：HELP-05 编辑已发布通用条目，以及受控导入里新增、修改或撤下会改变通用包输出的条目。导入的 dry-run 不推进。课程导入不推进。仓库里没有帮助删除接口。
