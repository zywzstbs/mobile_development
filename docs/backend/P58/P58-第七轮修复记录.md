## 来源

## 份额接受

判定维度是目标约定、分项和这一份份额，不是整个任务一个用户集合。

1. 目标约定上有本人的 `agreement_ack` ACCEPT，覆盖该约定计划里本人的份额。
2. 目标约定由已生效提案生成，而且该分项在提案 `changes_json` 里：只有本人对这份提案的 CONFIRMATION ACCEPT 算数。上一版的接受不能沿用。同一份提案里列出的多个变更分项，由这一次确认覆盖；没被这份提案改到的分项，不因为这次确认变成 true。
3. 分项不在变更集合里，而且标题、点数、截止、标准和全部份额都与前序快照一致：沿提案的 `base_agreement_version` 找那一版，不取任务最新的 ACTIVE，也不用版本号减一。中间的待确认或被要求修改版本不会被当成已生效来源。
4. 待确认、被要求修改、人员变更续约、组长重建约定：只看这一版自己的 ACCEPT。不把上一版或以后版本的接受填进来。
5. 来源缺失、版本号重复、计划对不上或来源成环：停止继承，不发明接受。直接写在这一版上的 ACCEPT 仍然有效。
6. 旧快照一边没有截止时间时，不把这个缺口当成新的变更。两边都有而且不一致，则不能继承。

`maybeApply` 仍会复制未改分项并签署新版本份额。签署只表示责任记录还在，响应里的 `accepted` 不读 `signed`。接口测试先把份额改成已签署，确认前读取仍是 false；局部调整之后，未参与的人没有新的 `agreement_ack` 或提案确认，读取仍是 true，数据库里的签署标记也仍是 true。

同一人同时在两个分项时，改其中一个，另一个是否接受单独判断。把第二项的责任说明改掉并且完成确认后，新版本用这次确认；旧版本仍是原来的说明和原来的接受。确认还没齐、提案被撤回时，不产生新约定，当前版本不变。

组长重建出的待确认约定，三个人的 `accepted` 都是 false。再读已经生效的前一版，未改过的接受仍在。

## 验收继承

`reviewerAcceptanceInherited` 只在 `source_change_id` 能找到人员变更时返回。普通约定和提案产生的新约定继续省略，不填 false。

主契约 R_DELIVERY_01 把这个字段定义成交接投影上的一个布尔值，不是逐分项字段。第六轮已有用例在一个分项通过后续约时期望 true。本轮保持这个聚合：目标约定自己的分项里，只要有一条更早的通过验收，验收人和种类都等于这份约定计划里的 `reviewerPolicy`，就是 true。没有这样的记录就是 false。不因为任意旧分项在别的任务、别的人、别的种类或以后的版本上通过，就把整份约定标成 true。

匹配还要求：提交属于这个任务，提交的分项列表包含该分项，提交未撤回，`agreement_version` 小于目标约定版本。只比较版本数字不够，还要对上任务、分项、人员和种类。

接口路径：两人的自检约定先有真实通过验收，交接后续约得到第二版，计划和继承标记都按原验收人。再邀请一名没有份额的成员，由组长重建约定，把任务当前安排改成这名独立验收人。第二版的计划原文不变，再次读取仍是原验收人、原种类、继承为 true。新约定使用新的验收安排，并且因为它不是交接来源，继承字段省略。把那次提交的 `agreement_version` 暂时改到目标版本之后，旧约定变成 false；改回原来的版本后又是 true。当前安排在这两次读取里都已经是新验收人。读取不增加验收，也不改安排。随后用原键回放续约，仍是当时的 true；同键换一句说明返回冲突；组长离组后读取和回放都拒绝。
