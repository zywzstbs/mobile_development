# P50前端源码核查

日期：2026-10-31。来源：工程交接ZIP，Android目录声明版本P50 / 0.51.0-p50。C01～C05兼容方案已获用户确认，设计版本1.1已同步；以下问题描述保留初次发现时的对照语境。此次为定向静态核查，未运行Gradle、设备测试或真实后端联调；交接包中的历史测试结果不作为本次验证证据。未修改前端源码。

源码定位统一以压缩包内 `咕噜派_工程交接_P50_20261031/android-app/app/src/main/java/com/grupi/app/` 为根。检查真实UI请求构造与RemoteBackend；Preview*仅用于了解本机预览语义，不把它当服务器已实现。

## 一、阻塞兼容的差异

### C01 正式任务多发reviewerPolicy.kind

证据：ui/AssessmentScreen.java:146–188，plan.reviewerPolicy含userId及kind=INDEPENDENT/SELF_CHECK；新建ASSESSED同时发criteria=[]。原文和本设计只列userId，未知字段策略会导致422。

已确认方案：将kind列为显式允许的可选枚举；未传按已确认规则推导，传入时必须与服务器核定资格一致，不能凭SELF_CHECK绕过独立人选或本人贡献检查。ASSESSED兼容顶层criteria=[]作为空占位，不接受顶层标准覆盖分项标准。返回约定policy.kind供前端显示（AssessmentScreen.java:406–416）。不是取消未知字段校验。

### C02 岗位修改并非id/clientKey互斥

证据：ui/RoleScreen.java:240–254构造两字段并调用RoleRules.roles；data/RoleRules.java:27–54规范化后依然保留id及clientKey。已有行两者都有；新行id为空字符串，clientKey必有。因此01中D17的互斥要求会拒绝当前页面请求。

已确认方案：允许同传，将非空id作为现有行唯一身份、clientKey仅作本次关联键；空id+clientKey视为新增。跨项目/不存在id仍拒绝。可继续兼容之前仅id或仅clientKey的规范客户端。需要同步修订01/02校验例外及ROLE-21实现说明，不能只改解析层而漏数据库归属检查。

### C03 阶段新增不传clientKey，且包含order

证据：data/BoardRules.java:25–68；预设阶段{name,order}，规范化结果固定{id:"",name,order}，已有阶段id非空。阶段1～12项，名称1～40，order连续且无重复。ui/BoardScreen.java:334–345把规范化数组提交stages。

已确认方案：阶段单独兼容空/省略id的新增行，使用数组位置/order作此次关联；order允许但须0～n-1唯一连续并与最终排序一致，服务端生成ID。保持clientKey新增方式可用。不可套用岗位的clientKey必填规则。既有任务引用的阶段仍不能删。

### C04 组长接任已有LEADER交接项，不使用空itemIds

证据：ui/GovernanceScreen.java:518–545对kind=LEADER显示“接任组长”，通过同一接受按钮调用respondHandover；611–626发送itemIds=[item.id]。data/PreviewGovernance.java:568–586由nextLeaderId生成具有独立id的LEADER项。

修正此前判断：仅根据接口文档认为没有组长接任入口是不完整的；实际前端已有入口，只是返回模型描述未覆盖LEADER项。

已确认方案：后端handoverPlan.items返回独立LEADER项（kind/id/recipientId/recipientName/responsibility/accepted）；taskId对该类型不适用，不能强制要求任务外键。回应支持该item ID，仍限定指定接任人、planVersion。保留已确认的itemIds=[]作为同一组长确认语义的兼容别名，两个形式写同一条确认记录，不能重复计票。TASK确认仍不代表接受组长。

### C05 分项调整实际允许dueAt

证据：data/BulkChangeRules.java:221–240仅为变化字段组装title/dueAt/criteria；截止修改加入fields.dueAt。本设计D18却规定截止走完整约定，当前此操作会422。

已确认方案：允许未验收分项的dueAt通过现有提案修改，和标准一样绑定baseUnitRevision、相关本人确认、当前无待验收/通过贡献；旧提交dueSnapshot永不改变。还需把分项dueAt与任务整体dueAt的语义明确为分项截止独立，变更时不能改兄弟分项截止。D18已修订为支持分项dueAt，不要求前端移除此操作。

## 二、云文件流程尚未发现客户端实现

检索src/main/java全部源码未发现upload-intents、download-authorizations或uploadToken调用。AttachmentActivity.java:49明确展示“仅存本机”，调用本地AttachmentStore。ui/SupportScreen.java:72和156创建求助/回复时attachmentFileIds固定为空数组。

结论限定：当前源码的上述附件入口是本机功能，不能据其存在认定FILE-01～04已有Android云上传链路。后端四个接口仍全部开发，并用HTTP集成测试验收；若要现场在App上传材料/截图，需要前端新增选择文件→申请意图→PUT字节→completions→fileId引用，以及授权下载。不能把content://本机路径当成服务端文件。

## 三、可以关闭“源码未知”的核实项

- HTTP：data/RemoteBackend.java:16–33规范origin或已含/api/v1地址；65–97使用HttpURLConnection，15秒连接/25秒读取，禁重定向，2MiB限制，Bearer与Idempotency-Key；41–59在401时刷新一次后原键重试。该实现已核读，不等同多设备异常联调通过。
- 聊天：ui/ChatScreen.java:65传afterChangeCursor，68同时依据hasMore和hasMoreChanges继续拉取；不能再把“是否实现变更游标”列为完全未知。连续阅读范围及服务端实际撤回仍需联调。
- 帮助入口：data/HelpRules.java:10列NONE/CONNECTION/COURSE/PROJECTS/APPLICATIONS/GRADES/NOTIFICATIONS/SUPPORT；ui/HelpScreen.java:103–110实现跳转。HelpRules.java:29的客户端维护仅接受entry.id=null；后端初始帮助配置应遵守该可维护范围。
- 帮助维护权限：HelpRules.java:13读当前用户capabilities中的HELP_CONTENT_WRITE。后端只有内部operator_grant而不返回对应安全能力提示时，前端通用帮助维护入口不会出现。需要明确User/me投影补充capabilities，值由真实授权派生，不能接收客户端自授。
- 色板：data/BoardRules.java:7–11固定 `#236B56,#355F9B,#79518C,#9C4F2E,#466E39,#82565E,#6A5C37,#3F6C73`，校验会转大写。
- 待办type：data/TodoRules.java:16–31支持TASK/AGREEMENT/CHANGE_PROPOSAL/REVIEWER_INVITATION/APPLICATION/INVITATION/ROLE_PROPOSAL/ROLE_SWAP/ROLE_PLAN/REMOVAL_VOTE/MEMBER_CHANGE/MATERIAL_REQUEST/PERSONNEL_HANDOFF/SQUARE_MERGE/PEER_REVIEW/GRADE_APPEAL。其他类型不能假设已有页面跳转。
