# 数据库与事务设计

## 1. 统一存储约定

主键业务ID使用varchar(120)，服务端UUID生成；外键同类型，禁止凭前缀关联。所有业务主表有id、revision int（1～999999999）、created_at、updated_at timestamptz；不可变快照只有created_at和内容版本。本文表中省略这些公共列。状态varchar+CHECK，迁移显式更新允许集合。FK默认RESTRICT，禁止删除用户级联清空成绩。历史用户可脱敏显示，但不能破坏事实链。

点数numeric(14,2)，单项应用校验0～1000000；汇总可能超过单项上限，数据库容纳总量，DTO按原接口约束检查而不截断。权重numeric(3,2)且0～1；Q/B/G smallint 0～100，delta -100～100。缺少依据的投影为null，禁止默认0。时间用数据库/应用统一UTC时钟，不在索引谓词中写now()。

JSONB仅用于不可变快照、有限结构方案/附属字段；需要唯一性、关系核查、逐人授权或并发更新的对象单独建表。下面列的是物理设计，不要求一响应模型一表。有限JSON结构必须建立对应Java record和校验，不允许任意JSON直接落库。字段长度按原文§7，表外键和NOT NULL由具体可空定义决定。

## 6. 必须先实现的约束示例

```sql
CREATE UNIQUE INDEX uq_active_team_member
 ON membership(project_id,user_id) WHERE status='ACTIVE';
CREATE UNIQUE INDEX uq_assignment_team
 ON assignment_team_slot(assignment_id,user_id);
CREATE UNIQUE INDEX uq_pending_submission
 ON submission(task_id) WHERE status='PENDING';
CREATE UNIQUE INDEX uq_dice_active
 ON dice_session(task_id)
 WHERE status IN ('INVITING','ROLLING','TIE_ROUND','AWAITING_CLAIM');
```

正式任务单PENDING是原文“一个有效批次”的实现；普通任务同样一次待验收，避免同任务并行提交争夺完成状态。部分索引使用显式状态，不把expires_at>now()写进谓词；到期记录在相关写事务内先标EXPIRED再新增。原理参照[PostgreSQL部分索引](https://www.postgresql.org/docs/17/indexes-partial.html)。

## 7. 锁顺序与跨模块事务

演示规模优先可证明正确：课程业务写先锁相关square（ID排序），再assignment，再project，再task，再submission/子对象；同层按ID排序。人员事项子域统一为：预读关联 → `personnel_case` → 本case grant（需要时）→ 确定类型/ID的 handoff、member_change、removal_vote、material；case 永远先于其子记录，不能先锁 handoff 再补锁 case。grant/revoke 先锁 case 再取 scope advisory 和 grant 行锁。涉及双方转组/合并必须一次收集两侧再按序加锁。账户状态变化先user行，业务写需要保证账户状态时也先user；所有共享锁顺序在repository方法注释标注。不可在拿task锁后回头锁project。聊天序号独立锁chat_counter，但同样先授权scope行；不增加无关project revision。

PostgreSQL READ COMMITTED + 显式行锁 + 唯一约束；报表一次读取使用REPEATABLE READ或同一快照查询。锁等待设短上限，用户请求不得持锁做文件IO、外部HTTP或密码哈希。数据库锁能力依据[PostgreSQL显式锁](https://www.postgresql.org/docs/17/explicit-locking.html)。

|事务|锁定对象|同事务必须完成|
|---|---|---|
|创建项目/接受邀请|课程、作业、相关项目、本人资格、邀请/岗位|资格唯一、人数与岗位预留、Membership、关闭其他申请邀请、释放其他预留|
|岗位全量更新|项目、成员/预留、所有岗位|总和=capacity；引用保护；QUICK升级及组长岗位一起提交|
|依赖调整|项目、相关任务|无环与门槛校验，版本更新|
|正式约定生效|项目、任务、约定及确认|全员/验收安排、份额守恒、更新当前关系与版本|
|验收或撤回|项目、任务、提交|竞争同revision；验收固定标准/通过锁定；撤回恢复草稿且原快照不变|
|人员最终执行|课程、作业、源目标项目、成员、涉及任务|全部交接确认、目标席位、唯一资格移动、组长更换、历史记录、约定待重签、失效骰子和游标|
|人员事项受理/结案/收回|case → PENDING handoff|受理核当前任课教师；结案/收回在 case 锁内确定性取消仍未决交接；收回重查旧 assignee 完整能力|
|交接接受/取消|预读 caseId → case → handoff|锁后重查来源版本、指定关系、当前处理人与资格；取消检查 UPDATE 行数|
|关联人员决定|case → member_change/removal_vote|从数据库解析唯一 case；只允许当前 assignee；版本/终态在锁后重查|
|材料响应/审核/撤回|case → material → material_response/review|响应版本单调递增；审核固定 responseVersion 且当前行未撤回；撤回只标记对应版本占位；SQL 同时核 case 未结案及允许的状态转换|
|case 级教师授权/撤销|case → advisory scope → grant 行|撤权完成后新请求立即失权；历史 grant 与审计保留|
|成绩批量发布|课程、作业、涉及项目/任务按序、全部候选来源|全部basisDigest一致；整批快照、复核关联结案、通知一次提交|
|归档|项目及来源任务、交付/报告|状态前置、本轮sourceKey/release一致、关闭招募/码、记录archive_at|
|骰子投骰|项目、任务、session|唯一点数、收齐后筛候选/推进轮次；不能生成后才竞争唯一键|
|聊天发送/撤回|项目权限、chat_counter、message|消息/序号或变更序号、outbox；撤回不新增未读|
|上传引用|业务资源、stored_file|READY、当前用途权限、file_reference同业务对象一起写|

`V022` 把材料时间可信度拆开：`createdAtConfidence=EXACT` 对应真实非空 `created_at`，`UNKNOWN` 对应显式 null；`legacy_recorded_at` 只保存 V021 回填的最后修改时间供内部诊断，`time_source` 区分服务器提交、回执恢复和 legacy 未知。V021 已执行脚本不重写；新提交写入 `EXACT/SERVER_SUBMISSION`，只有受控 `material-time-recovery` 能在绑定真实 `operation_receipt` 后改为 `RECOVERED_EVIDENCE`。

## 8. 数据迁移原则

按05阶段拆Flyway版本。先新表和索引，再迁移数据，最后收紧NOT NULL；禁止生产自动ddl-update。每阶段测试从空库迁移和从上一阶段库升级两条路径。所有重要唯一约束有可识别名称，以便映射准确错误码。索引先覆盖FK、当前队列、分页排序，再用演示数据EXPLAIN检查，不盲目每列建索引。

## 9. 迁移和联查补充

广场合并需同事务更新assignment与project的当前square关联，保留origin_square_id或审计快照；旧业务ID不改。assignment_team_slot仅在合法离组最终执行时释放或转移，归档不释放；旧membership历史保持。方案/份额每次生效都保留不可变agreement快照，查询当前份额不可抹掉退出者原始责任证据。

为角色、阶段、任务、提交等跨对象引用建立复合唯一键/复合FK或事务内同属校验，不能仅凭单列FK存在就认为归属正确。file_reference等多态引用无法直接用普通FK证明业务对象存在，必须通过对应模块引用服务校验并在资源删除计划中检查，不能允许用户任意构造resourceType。
