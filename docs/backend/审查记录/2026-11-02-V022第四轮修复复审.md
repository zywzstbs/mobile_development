## W01 [P2] 时间恢复未绑定具体版本，且把回执时间直接标为精确提交时间

### 位置

- `src/main/java/cn/gulupai/server/governance/MaterialResponseTimeRecoveryService.java:39–49、63–74`。
- `src/main/java/cn/gulupai/server/governance/GovRepository.java:370–376`。
- `src/test/java/cn/gulupai/server/governance/GovU02MaterialTimeIT.java` 的恢复用例。

### 版本证据不足

recover(materialId, version, receiptId, ...)虽然接收version，但回执查询只返回id/user_id/method/path/business_code/created_at；校验只要求POST、同材料responses路径、同作者、OK和时间非空，没有读取或验证回执实际产生的responseVersion。

同一材料的v1、v2、v3都由同一学生发送到同一个路径。因此任意一次成功提交回执，都能被拿来给其他未知版本恢复时间。

具体反例：

1. 学生10:00提交材料m的v1，产生回执R1。
2. 学生11:00补交v2，后续审核/升级使v2保留为UNKNOWN。
3. 管理员运行恢复m/version=2/receiptId=R1。
4. 当前实现所有检查通过，将v1的回执时间写入v2，并标记EXACT/RECOVERED_EVIDENCE。

这会重新引入D02要避免的错误：把缺乏证据的时间包装成准确的历史事实。管理员受控执行不能代替服务端对版本证据的校验，选错回执就会污染历史。

### 回执创建时间不等于已证明的提交时间

即使receiptId确实对应目标版本，当前实现也直接使用operation_receipt.created_at。

材料新提交时间来自 `GovService.respondMaterialOnce` 的应用Clock；回执的created_at在V002中由数据库CURRENT_TIMESTAMP默认生成，IdempotencyStore.insert没有显式传入该次材料的提交时刻。两者是不同来源，代码没有保证它们完全等价。事务等待、应用Clock与数据库时钟差异等情况下，不能将回执行创建时间直接宣称为目标版本的精确提交时间。

正确恢复必须证明“这一个版本”和“这个版本实际记录的提交时间”，而不是仅证明“该用户曾成功调用过这个路径”。当前恢复用例断言结果等于receipt.created_at，恰好延续了未经证明的假设。

### 本轮方法级复现

临时程序 `/tmp/gulupai-v022-probes/RecoveryProbe.java` 使用实际MaterialResponseTimeRecoveryService，仓储用Mockito替代：目标是m的v2 UNKNOWN，提供同作者/同路径的“v1回执”投影。实际输出：

```text
requestedVersion=2 receiptFor=v1 result=RECOVERED recoveredAt=2026-11-02T10:00:00Z
```

程序还验证了服务调用 `recoverMaterialResponseTime("m", 2, v1ReceiptTime, ...)`。这证明Java恢复校验不会检查版本，**不是实际数据库已写入**；回执查询本身不包含版本字段的事实由源码确认。没有运行真实CLI进程或真实PG恢复。

### 修复方向

1. 不以相同method/path/user作为充分恢复依据。必须读取真实提交结果或专门提交证据，校验materialId、responseVersion、author及动作成功。
2. 如果使用加密幂等回执，按项目已有安全机制在服务内解密并验证原始结果；禁止将回执正文、密钥或材料敏感内容输出到日志/CLI。查询到的是历史成功结果，不能用当前GET结果代替历史证据。
3. 精确时间应来自可靠、明确绑定该版本的服务器提交字段/事件。旧回执没有足够字段或无法解密时，明确拒绝恢复并保留UNKNOWN，不能回退到receipt.created_at、updated_at或管理员手填时间。
4. dry-run执行同样的完整证据校验；只有可靠来源才可显示“可恢复”。重复恢复和已有EXACT保护继续保留。
5. 如已用当前错误逻辑恢复过历史行，先按time_source=RECOVERED_EVIDENCE与time_evidence生成只读影响清单，重新验证证据。无法证明的记录按受控纠错恢复UNKNOWN，保留原恢复审计；不要清空真正的新提交时间，也不要改V022校验和。
6. 此CLI是辅助恢复能力；不能可靠恢复并不妨碍D02成立。保持UNKNOWN是正确结果，无需强行恢复。

### 必补测试

- 同一作者同一材料v1/v2，两条真实成功回执；用v1回执恢复v2必须拒绝，dry-run也拒绝，数据库不变。
- 正确版本但缺少真实提交时间的旧回执必须保持UNKNOWN。
- 同一版本的可靠证据携带实际提交时间，且该时间故意不同于receipt.created_at；恢复必须取实际提交时间。
- 其他材料、其他作者、审核/撤回回执、失败回执、无法解析/解密的回执均拒绝。
- 可靠证据恢复成功、同证据重复无变更、不同证据不能覆盖既有EXACT；诊断旧值和恢复审计保留。
