## U01 [P2] 材料写接口未落实状态限制，能修改已验收材料和验收已撤回版本

位置：`governance/GovService.java:976–1046、1251–1257`。

当前响应明确给出以下限制：ACCEPTED材料canRespond=false/canWithdraw=false；只有RESPONDED材料canReview=true。然而对应写方法主要检查操作者与revision，并未校验同样的状态：

- respondMaterialOnce没有检查material.status或case.status，直接插入新response并改为RESPONDED。
- withdrawMaterialOnce仅增加“存在正文”的检查，没有拒绝ACCEPTED或已结案事项，直接置WITHDRAWN。
- reviewMaterialOnce仅确认responseVersion相同、版本行存在，没有确认材料处于RESPONDED，也没有检查该版本withdrawn=false；撤回后版本行仍存在，因而可被置ACCEPTED并写入审核记录。

### 具体反例

1. 学生提交→教师接受→学生取得最新revision，用新幂等键再次提交：已验收材料变回RESPONDED。
2. 学生提交→教师接受→学生用最新revision撤回：已验收材料变为WITHDRAWN。
3. case结案后，学生仍用正确材料revision提交：新增response版本并改变已结案事项中的材料。
4. 学生撤回当前版本→教师取最新revision并以该responseVersion审核ACCEPT：写入审核记录，材料ACCEPTED，但该版本仍withdrawn=true、正文投影为空，形成互相矛盾的状态。

这不是“同一版允许多条审核记录”的产品选择，而是业务写入绕过了已有can*限制和撤回状态。禁止操作不能只靠前端按钮隐藏。

### 本轮验证

在 `/tmp/gulupai-v021-probes/MaterialStateProbe.java` 中，以Mockito替代仓储和权限查询，执行实际私有应用方法并捕获传给updateMaterial的目标状态。学生与教师使用不同身份，审核使用合法处理人场景。输出：

```text
respondMaterialOnce case=IN_PROGRESS material=ACCEPTED -> persisted=RESPONDED
respondMaterialOnce case=CLOSED material=RESPONDED -> persisted=RESPONDED
withdrawMaterialOnce case=IN_PROGRESS material=ACCEPTED -> persisted=WITHDRAWN
reviewMaterialOnce case=IN_PROGRESS material=WITHDRAWN -> persisted=ACCEPTED
```

这里程序输出的persisted表示传给**模拟仓储**的写入状态，不是数据库已落库。本轮确认的是实际Java应用方法没有阻止写入；HTTP和PG场景仍需真实集成回归。外层现有回调只核材料本人/当前处理人，仓储UPDATE只核id/revision，未见其他层补上这些状态限制。

### 修复方向

1. 定义并复用材料的当前可回应/可撤回/可审核规则；同一规则用于响应can*和锁后的写入校验。
2. 新写操作锁case再锁material后，先核case可办理状态、材料状态、目标response版本及withdrawn标记，再插入历史版本或审核行。
3. 已验收材料、已结案事项不能因换幂等键重开；如业务有重新打开流程，应显式走原契约动作，不能通过普通响应/撤回暗中重开。
4. 审核必须针对当前尚可审核的未撤回真实版本，不以“版本行存在”作为充分条件；失败不新增material_review或改变revision。
5. 成功操作的同键回放仍按当前有权安全投影处理，不因加入新执行的状态检查而错误重复执行或恢复旧正文。

### 必补测试

- 上述4条反例通过真实HTTP操作建立数据，再分别断言错误码、材料状态、responseVersion/revision及两张历史表行数保持不变。
- 返回的canRespond/canReview/canWithdraw与同一状态下新写入口一致。
- 学生撤回与教师审核并发只能一个合法转换成功；另一方按版本/来源变化拒绝，不能出现ACCEPTED且当前响应withdrawn=true。
- case结案与学生回应/撤回竞争由case锁协调；结案先完成后，不得再修改材料。
- 原已成功请求同键回放不产生第二次效果，仍遵守当前读取权限。

## U02 [P2] V021把最后更新时间当成材料提交时间，误记旧版本历史

位置：`src/main/resources/db/migration/V021__material_response_versions_and_reviews.sql:38–48`；`governance/GovRepository.updateMaterial:305–310`。

迁移将 `material_request.updated_at` 写入 `material_response.created_at`，并注释为可证明的提交时间。但旧实现的材料回应、审核、撤回都调用updateMaterial，而该方法每次都会更新updated_at。因此updated_at只能证明材料最近一次修改时间，不能证明这版正文何时提交。

反例：旧库学生10:00提交v1，教师11:00接受；升级V021后responses[0].createdAt变成11:00。旧库学生10:00提交、12:00撤回，则升级后记成12:00。正文版本和作者仍可能正确，但时间语义已经错误。

影响：新版接口把审核/撤回时间显示为学生提交时间，可能误导过程记录和截止判断；“只回填可证明当前版本，不伪造时间”的迁移承诺未满足。本轮由迁移SQL和所有更新路径确认，未执行真实存量升级测试。

### 修复方向

- 仅当存在可靠提交事件/回执/快照能够证明时间时恢复真实createdAt；不能把其他字段名称看起来像时间就当作提交证据。
- 无法恢复时明确记录为legacy时间未知或时间语义不精确，按原契约允许的可空/兼容投影处理；若接口强制精确时间且无兼容表达，提出具体契约补充，不制造一个“看似精确”的值。
- V021若已经执行，不能修改原迁移校验和；新增迁移/受控修复处理此前生成的legacy行，保留诊断依据。不能把所有新版本时间一起清空。
- 新提交继续使用服务器实际提交时钟，不受legacy处理影响。

### 必补测试

从V020建立：只提交未审核、提交后审核、提交后撤回三类材料，各操作使用不同时间；升级后证明不会将后续修改时间当作提交时间。检查当前版本内容仍真实、缺失早期版本不被补造、新提交时间准确。已有新库表存在测试不能覆盖此问题。
