# 2026-11-02 后端实现审查

结论：当前实现不宜标为“281接口全部完成业务验收”。已有工程、迁移和测试基础，但定向审查发现以下可直接由代码确认的问题。此次未修改实现代码，也没有重写原接口覆盖状态。

范围：主要检查组队、成绩结算、聊天、幂等及既有验证方式；不是281个接口全量逐字段审计。下述业务问题依据源码控制流，不冒充已通过HTTP/数据库动态复现。

## R01 [P1] 幂等回放会重新暴露已撤回正文

位置：`src/main/java/cn/gulupai/server/common/idempotency/IdempotencyService.java:75`，`community/application/ChatService.java:97`。

触发：用户以键K发送聊天，随后撤回；在项目仍可写且仍为成员时，使用相同K与原正文重试发送。幂等服务直接反序列化第一次成功的完整Message，其中仍有原content、refs与withdrawn=false。回放回调仅检查账号有效，没有按消息当前状态重新投影。

影响：撤回占位可以被幂等缓存绕过，客户端可能将撤回消息恢复为原正文，违反所有读取和回放均遵守撤回规则。加密存储并不能解决回放时的业务权限/内容状态问题。

建议：保留一次业务效果及稳定ID，回放前按当前资源状态和授权重新投影可撤销内容。回归：发送→撤回→原键重试，仍返回同messageId但不能返回原正文或撤回前状态；正文历史/引用同样核查。

## R02 [P1] 到期但待验收的正式提交可被结算为0验收

位置：`src/main/java/cn/gulupai/server/grade/GradeService.java:584–603`，`grade/GradeRepository.java:50`。

账本projection只从份额、已通过验收、本人确认和更正构建；没有查询当前PENDING提交或未完成交接。份额已签、截止已过、尚无通过验收时，不添加gaps，accepted=0；settle仅检查gaps，因而允许结算。学生即使按时提交但教师尚未验收，也会被当作到期未交。

建议：区分“无待处理提交的到期未完成”与“提交待验收”，补PENDING/交接状态来源及摘要依赖。回归：截止前提交→推进到截止后→仍PENDING，结算必须阻止；明确无提交的到期份额才允许验收0。

## R03 [P1] 作品来源接口仍是固定空实现

位置：`src/main/java/cn/gulupai/server/team/application/TeamService.java:662–665`。

workSourceProjects核验账号后直接List.of()，注释仍写“证据属于P11”。P11已声明完成，但无论用户拥有多少已验收贡献，TEAM-06都返回空集，前端无法从此入口选择可引用成果。

建议：实现本人有效贡献及授权历史投影，不以空集合代替未实现查询。回归：有贡献/无贡献/历史离组贡献/无权来源四种场景。

## R04 [P2] 邀请候选静默截断且伪装完整列表

位置：`src/main/java/cn/gulupai/server/team/application/TeamService.java:658`，`team/api/TeamController.java:98–105`。

服务拼接申请和课程候选后limit(20)，Controller用ListEnvelope.full封装，返回hasMore=false、nextCursor=null、total=最多20。方法没有cursor参数，也未返回契约要求的projectRevision。超过20个候选无法继续查询；重复来源用户还可能占据名额。

建议：按userId去重、稳定排序，提供20条快照分页和完整total、projectRevision，续页绑定项目版本。回归：21个候选必须可取第21人；同用户申请/课程来源不重复；项目变更使旧游标失效。

## R05 [P2] 聊天变更流无限量，游标缺少绑定和有效期

位置：`src/main/java/cn/gulupai/server/community/persistence/ChatRepository.java:130`，`community/application/ChatService.java:74–85`及parseCursor。

changes SQL查询全部change_sequence大于游标的事件，没有LIMIT；响应始终hasMoreChanges=false并把nextChangeCursor设为全局最新。游标只是可自行填写的整数，无本人/项目绑定和7天期限，也没有按消息ID+revision去重。

影响：首次或长时间断线可能返回整个变更历史，触发2MiB限制而无法同步；不能按100项批量补齐，过期游标也不会要求重新加载。

建议：查询有限批次，游标前进到真实已下发边界，保存授权范围和到期时间。回归：101个变更、同消息多次变更、跨项目游标和超过7天。

## R06 [P2] 已读游标允许跨未下发缺口，写入口也未接幂等

位置：`src/main/java/cn/gulupai/server/community/application/ChatService.java:172–178`，`community/api/ChatController.java:77`。

只检查sequence≤latest，没有记录或检查本人连续下发区间；一个从未读取历史的成员可直接提交latest并清空之前未读。Controller没有Idempotency-Key处理，Service也未用幂等模板。

建议：维护授权下发区间，推进必须覆盖旧阅读位置到目标的连续区间，并接统一写协议。回归：只读取最新10条，不能越过之前90条；多设备合法max；缺幂等键返回约定错误。

## R07 [P2] clientMessageId只绑定content，忽略引用和提及

位置：`src/main/java/cn/gulupai/server/community/application/ChatService.java:106–110`。

对相同clientMessageId但不同Idempotency-Key，代码仅比较content；修改refs或mentions仍返回旧消息成功。正文不同则返回APPLICATION_EXISTS，也不符合CLIENT_MESSAGE_ID_REUSED协议。

建议：存储规范化完整消息请求摘要，涵盖content/refs/mentions；旧消息撤回后仍保留摘要作为稳定业务唯一键依据。回归：同ID文本相同但引用/提及不同必须409 CLIENT_MESSAGE_ID_REUSED；完全相同不重复发送。

## R08 [P2] 个人待办仍只涵盖邀请/申请

位置：`src/main/java/cn/gulupai/server/team/application/TeamService.java:757–788`。

todos只遍历pendingInvitations和applicationsForApplicant，dashboard复用此结果。正式约定待确认、待验收、任务、交接、材料、成绩复核等均不贡献待办，后续模块没有接入此聚合。

建议：按业务模块添加当前用户ACTION/WAITING查询，统一授权和稳定排序，计数与items同源。回归：创建一个待本人确认约定应出现待办，确认后消失；清消息提示不能完成待办。
