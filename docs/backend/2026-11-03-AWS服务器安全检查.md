检查日期：2026-11-03（Asia/Shanghai）。目标：`18.166.212.12`，服务目录 `/opt/gulupai`。检查方式：SSH 只读核验、低频公网协议探测、部署配置与相关鉴权代码核查、上游安全公告比对。

结论：已具备密钥登录、HTTPS、应用非 root 运行和数据库网络隔离等基础防护；**正式承载真实数据前，应优先处理数据库超级用户凭证、旧组件镜像及业务备份问题**。本次为安全检查，未升级镜像、修改 SSH/防火墙或重启业务服务。联调文档已更新并移除旧环境明文口令。

## 2. 按优先级处理的问题

P1 表示应在真实用户/数据接入前优先完成；P2 表示后续加固。此分级是部署整改优先级，不是漏洞 CVSS，也不代表已证明存在远程利用链。

### P1-01：应用使用数据库超级用户

证据：应用 `DB_USERNAME=gulupai`，同名数据库角色的 `rolsuper`、`rolcreatedb`、`rolcreaterole` 均为 true。当前 Compose 使用 PostgreSQL 初始化管理员同时作为业务账号。

影响：如果应用出现 SQL 注入或业务数据库凭证泄露，损害范围会扩大至数据库管理权限；内网隔离不能抵消应用自身持有过大权限的风险。

整改：为运行期建立独立最小权限账号；迁移使用单独的受控管理账号。将 Flyway 连接凭证与应用数据访问凭证分离，限制运行账号创建角色、数据库、扩展或访问无关对象的能力。需要结合现有 Flyway 和 schema 所有权验证，不能直接在现有唯一管理员上执行降权。

验收：应用运行账号 `rolsuper=false`、`rolcreatedb=false`、`rolcreaterole=false`；独立迁移及业务回归通过；运行账号无法越权管理数据库。

### P1-02：PostgreSQL / Caddy 镜像版本偏旧

实测 PostgreSQL 为 `17.6`，Caddy 为 `2.10.2`。镜像 digest 已固定，有助于复现，但固定 digest 不会自动获得安全补丁。

PostgreSQL 上游安全清单中存在修复于 17.7、17.8 及之后版本的安全问题；应使用 17 系列当前受支持的安全补丁版本。Caddy 仅支持最新 2.x 版本，上游公告 GHSA-8qx7-j2v2-x6q5 将 `<=2.11.4` 列为受影响、`2.11.5` 为修复版本，涉及协议升级响应头处理。当前应用未发现 WebSocket 接口，因此不能仅凭版本断言这条利用路径在本服务可达。[PostgreSQL 安全清单](https://www.postgresql.org/support/security/)、[Caddy 支持政策](https://github.com/caddyserver/caddy/security)、[Caddy 公告](https://github.com/caddyserver/caddy/security/advisories/GHSA-8qx7-j2v2-x6q5)。

整改：备份后在隔离环境验证 PostgreSQL 同主版本补丁升级及 Caddy 升级，重锁 digest。检查基础镜像、JRE 与 JAR 依赖的漏洞清单，并纳入定期升级。不能将宿主机 unattended-upgrades 当作容器或 Java 依赖的自动补丁机制。

验收：升级后健康检查、迁移校验、登录/刷新、文件传输、HTTPS 和证书续期通过；保留旧镜像及数据恢复方案。

### P1-03：未发现业务备份与恢复验证

已检查部署目录、常见备份目录文件名、systemd 定时器和 cron 文件清单，未发现 PostgreSQL、上传文件和业务加密密钥的配套备份任务。系统的 `dpkg-db-backup` 是软件包数据库备份，不是业务数据备份。未检查 AWS 控制台，不能排除云端已配置快照。

整改：建立数据库、上传文件与加密密钥的配套恢复流程；备份加密保存到独立位置，配置保留周期、失败告警，并在隔离环境执行恢复演练。上传文件卷持久化只保证容器重建时保留，不防服务器/磁盘丢失。业务加密密钥若丢失，即使数据库仍在，也可能无法解密幂等回执等数据。

验收：有自动执行证据及最近一次成功恢复记录，恢复后的数据库与文件引用一致；备份中不公开凭证。

### P2-01：root 密钥直登及 SSH 来源限制待核验

root 允许密钥登录；`X11Forwarding yes`、`AllowTcpForwarding yes`，认证宽限 120 秒、单连接最多认证尝试 6 次。密码已禁用，不能把这一状态描述为“开放 root 密码登录”。

整改：先验证普通运维账号的密钥登录与 sudo，再考虑关闭 root 远程登录；按实际需要关闭 X11/隧道转发、缩短认证宽限。AWS 22 入站建议限制为运维固定出口或受控管理通道；没有固定出口时需先设计不会锁死运维的访问方式。

验收：用新连接验证保留的登录方式，再收紧旧方式；云控制台恢复途径可用。本次没有修改 SSH，也没有删除任何密钥。

### P2-02：登录限流来源 IP 在反代后可能合并

代码 `AuthController.clientIp()` 使用 `request.getRemoteAddr()`；未配置受控代理的来源地址处理。Caddy 与 app 位于同一个 Docker 网络，推断应用通常看到代理容器地址，而不是每个真实客户端地址。

影响：现有限流按 `loginId + IP` 计算，相同账号的不同真实客户端可能共享计数和封锁；攻击者针对目标账号的失败登录可能影响该账号的其他使用者。这里只做配置/代码推断，未对真实账号执行封锁测试。

整改：由受控代理规范化转发来源，只信任明确代理范围；应用处理可信转发头，验证伪造的外部转发头不能绕过。另增加按真实来源和全局的请求预算，避免任意账号轮换绕过单账号限流。不要简单信任所有 `X-Forwarded-For`。

验收：两个客户端来源被正确区分，客户端伪造头无效，限流与用户提示符合预期。

### P2-03：主机防火墙与云入站规则缺少独立核验

UFW 未启用；当前依赖云侧规则、宿主监听和 Docker 发布端口。没有 AWS 管理凭证，本次未读取云防火墙/安全组的实际规则或 IPv6 策略。

整改：在云控制台核对 TCP 80/443 的公网访问、22 的运维来源限制以及 IPv6 对应规则，不开放 5432/8080/2019/2375/2376。若增加主机防火墙，先保留运维访问并验证重连。Docker 发布端口会经过其自身转发链，不能只看 UFW 状态就认定容器被保护。[Docker 官方防火墙说明](https://docs.docker.com/engine/network/packet-filtering-firewalls/)。

本次外部 TCP 建连曾在多个端口显示成功，但随后协议请求全部超时，与宿主无对应监听相符；未将单独 TCP 建连结果当作管理服务已暴露的证据。

### P2-04：容器与告警可进一步收紧

当前 Caddy 进程为容器 root；PostgreSQL 实际进程非 root，不能把其镜像入口配置用户为空直接认定为数据库以 root 运行。三个容器尚未显式设置 `no-new-privileges`、capability 最小集合、PID 限制或只读根文件系统。

整改：逐项验证 `no-new-privileges`、PID 上限、capability 限制；应用可结合临时目录与上传卷评估只读根文件系统。数据库初始化、文件卷权限和代理监听低端口有各自要求，不统一强行改成相同 UID 或删除所有权限。

未发现外部业务健康/磁盘/证书到期告警的部署证据；本次证书续期定时器 active，仍应监测续期失败和证书剩余有效期。80 端口需要持续可达才能 HTTP 校验续期。
