## 三、F01 / R01：幂等回放按当前资源投影

### 修改范围

`common/idempotency/IdempotencyService.java`；`community/application/ChatService.java`；留言主题、回复、历史和引用投影相关服务。全仓检索 `idempotency.execute`，生成一张“动作—返回资源—是否可撤回/失权—回放策略”核查表，随 F01 交付。

### 实现步骤

1. 保留现有键作用域、请求体摘要、锁、有效期和一次业务效果语义。新增显式的回放投影扩展点，例如 `ReplayProjector<T>`；旧接口可委托默认行为，不能强制所有不可变回执都重新执行动作。
2. 成功回执保留稳定资源 ID/类型及必要版本，回放从这些标识读取当前资源。不要把旧加密正文解密后直接作为最终 HTTP 响应；加密只解决存储，不解决撤回展示。
3. 回放流程：验证当前身份及资源读取资格 → 验证键/请求一致性（保持统一错误优先级）→ 按当前数据库状态投影 → 返回原资源ID。不得再次插入消息、增加 sequence、发 outbox、扣配额或重复执行业务。
4. 新执行与回放的前置条件分开：新发送要求项目可写；已成功命令在项目归档后，如仍有合法历史读取权，应按契约返回当前只读投影，不能在进入回放前统一 `requireWritable` 而误拒。失权用户始终不得回放正文。
5. 消息撤回后，正文、引用内容和预览均占位，withdrawn/revision 是当前值。主题/回复的历史和被引用内容使用同一投影规则，不能通过另一条读取路径恢复旧正文。
6. 当前状态读取与撤回事务建立明确顺序。可用资源锁或一致性事务实现；并发请求只保证可线性化，不承诺收回此前已发送到网络的数据。撤回提交后开始的回放必须看到撤回状态。
7. 旧回执兼容：可从旧返回值提取资源 ID，但不能信任其中正文与授权。无法定位资源时按现有资源不可用协议返回，不回退到原文、不再次执行命令。若现有 resource_refs 足够则不必新增表；需要补元数据时使用新增迁移/兼容读取。

### 验收用例

- R01-T01：键 K 发送→作者撤回→K+原请求重试：同 messageId/sequence，withdrawn=true，无旧正文/引用预览；消息及 outbox 数量不增加。
- R01-T02：先成功→离组/封禁→重试：拒绝；教师或管理员身份不能绕过成员权限。
- R01-T03：成功→归档且保留历史资格→重试：安全投影，不新增写入。
- R01-T04：主题/回复撤回后，原键、历史和引用读取均不暴露正文。
- R01-T05：相同键不同请求仍按统一幂等协议冲突；旧格式回执与缺失资源有确定行为。

## 四、F02 / R02：结算区分未交、待验收和未完成交接

### 修改范围

`grade/GradeService.java` 的 projection、sourceKey、settle、候选生成及发布校验；`grade/GradeRepository.java`；提交、验收、约定、交接及更正写路径的锁/失效处理；现有 `GradeP09IT` 及新增边界用例。

### 实现步骤

1. 扩展账本来源查询，以当前学生、交付项和有效份额为粒度取得：已签有效版本、到期时间、通过验收、本人确认、当前待处理提交、交接阻断/重签状态、最新有效教学更正。不要仅查询已经通过的验收。
2. `submission` 已有 status、unit_ids_json、agreement_version、提交快照；正式提交必须按实际覆盖 unit 匹配，不能把同任务其他项的待验收误算到本项，也不能只看 submitted_by 而漏掉共同贡献者。普通任务不得进入正式分值。
3. 对未签、待验收、未完成交接/待重签、通过未确认、截止前未完成分别产生稳定的内部 gap 原因，映射到已有响应结构和错误码。新增内部原因若会成为前端枚举值，先核查 P50 容错；不擅自发明公开错误码。
4. 先计算程序性阻断，再计算分值；教学更正分支不得因为提前返回而绕过本应存在的阻断。更正具有何种覆盖能力严格按已确认规则，不自行扩大为“强制结算”。
5. 仅当已签有效责任、已到截止、无待处理提交及交接阻断、无待确认验收且符合到期未完成条件时，允许 accepted=0。`now == dueAt` 使用一致边界；不要把“尚无通过验收”等价于“可以计0”。
6. sourceKey 纳入影响账本的来源 ID、revision、状态、版本及稳定排序后的覆盖项；包含会改变结果的时间边界状态，不能直接放每次都变的当前时间。PENDING→REVIEWED/撤回、交接状态改变、更正变化后，旧摘要必须失效。
7. 梳理所有来源写事务与结算事务的共同锁。当前仅 `lockTasks` 不足以自动证明没有竞态：提交/验收/交接必须也取得相同保护锁，或统一通过 assignment 级协调。按项目现有全局锁顺序实现，列出锁顺序表，避免一方 assignment→task、另一方 task→assignment。
8. 批量结算/候选生成/发布使用相同投影和来源校验；批量失败必须原子回滚。已发布成绩和历史结算保持不可变；来源改变使待发布旧候选不可用，后续走新结算、新发布，不覆盖历史。

## 五、F03 / R07：完整消息请求与 clientMessageId 绑定

### 修改范围与迁移

`ChatService.send/sendOnce`、`ChatRepository`、`ChatRequests`、`common/api/ApiCode`。建议新增迁移 `V019__chat_request_identity.sql`（编号以执行时为准），增加 `request_hash`、`request_hash_version` 或等价字段，保留 `(project_id, author_id, client_message_id)` 唯一约束。

### 实现步骤

1. 定义有版本的规范化输入：content、refs 的 type/id/version、mentions；路径和作者由唯一键作用域约束。统一省略/null/空数组规则及文本规范化，使用项目现有 CanonicalJson/摘要能力。不要自行 trim 正文、重排引用或将有序数组变集合，除非契约明确允许。
2. 新消息写入原始完整请求摘要，与消息、序号、变更事件、outbox 在一个事务提交。摘要不是从动态引用预览计算，也不能从撤回后的正文反算。
3. 相同 clientMessageId 且摘要相同：返回现有消息当前安全投影；不同：409 `CLIENT_MESSAGE_ID_REUSED`，不再返回 APPLICATION_EXISTS。同 Idempotency-Key 异请求优先遵循通用 IDEMPOTENCY_KEY_REUSED 规则。
4. 撤回清理展示正文与引用时保留不可逆摘要。新 Idempotency-Key 重试已经撤回的相同消息也只能返回撤回占位。
5. 并发发送靠数据库唯一约束和明确锁保护，不能仅“先查后插”。优先沿用项目计数器锁后再次检查唯一键；若捕获唯一冲突，注意 PostgreSQL 事务已失败，不能直接在同一失败事务继续查询。保证只有一次序号分配/消息/outbox效果。
6. 存量非撤回记录仅在原字段完整且规范化可确定时回填摘要；不要修改旧Flyway脚本。存量撤回记录无法还原原请求时标记 legacy/unverifiable，保留原唯一键。相同客户端ID的不可验证重试保守返回既有冲突码及说明，不猜测相同、不恢复正文、不创建新消息。记录此迁移兼容边界。
7. 如修复前曾发生“同ID异refs却成功”，数据库只保存最终存在的原记录，应以实际持久化记录为准，不能补造丢失历史。

## 六、F04 / R05：聊天变更流有界同步

### 修改范围与存储

`ChatController`、`ChatService.messages`、`ChatRepository.changes`、`ChatViews.Page`；新增专用同步游标存储或经认证的不透明令牌。不要直接复用15分钟列表游标作为7天聊天同步游标。

建议新增 `chat_sync_cursor`：token_hash、user_id、project_id、授权代次、last_change_sequence、expires_at、created_at；token_hash唯一，过期清理索引，必要外键。只保存摘要/边界，不缓存正文。若用签名令牌实现同等约束，须使用既有安全密钥机制并测试篡改；不能裸整数或仅Base64编码。

### 同步算法

1. 先验证当前项目读取权，再解析游标；绑定本人/项目/授权代次/期限，不得用另一个用户或项目游标查询。未知、篡改、过期或历史已经清理到无法连续恢复的游标按契约409 CHAT_SYNC_EXPIRED；失权按权限协议返回。
2. 首次未带 afterChangeCursor：在同一一致性快照取得历史消息页与当前变更高水位 H，返回 changes=[]、hasMoreChanges=false、指向H的新游标。**不得从0补发所有历史变更。** 客户端按协议继续补历史和增量。
3. 带有效游标 C：取一致性快照内高水位 H；查询 `C < change_sequence <= H ORDER BY change_sequence LIMIT 101`。前100条为本批扫描事件，第101条仅判定还有后续。不要把 next 游标跳到尚未扫描的 H。
4. 从本批事件生成消息的当前安全投影，同一消息保留最高revision，每批最多100个变更投影；游标位置依据最后扫描的原始事件，而不是去重后条目数。存在更新revision的投影可被后续页再次看到，客户端按id/revision合并，不丢事件是首要约束。
5. 没有事件时返回可继续使用的新游标，位置保持已确认边界。每个签发游标7天有效；清理事件时另查最早可恢复边界，不得靠重新签发游标让已丢失历史“重新有效”。
6. 变更读取、消息投影及高水位必须来自同一数据库一致性快照，或提供等价锁/边界证明；默认 READ COMMITTED 多次查询不能自动保证这一点。特别测试“历史页查完后发生撤回，再取高水位”不会漏撤回。
7. 历史 items 和 changes 是两条独立进度：hasMore 与 hasMoreChanges分别计算；nextAfterSequence 是实际连续下发边界，不直接取全局最大。顺带修正 beforeSequence、搜索、aroundSequence 页的 hasMore/边界计算，严格按原接口规则，不让稀疏搜索推进连续增量位置。
8. changes 不增加未读、不推进阅读游标；撤回投影不携带旧正文及引用。核对完整 CHAT-01 响应字段与 P50解析器，不因新增游标而删掉既有字段。
9. 验证实际序列化大小受公共2MiB响应限制约束；若需要按字节缩小批次，游标只能走到实际发出的扫描边界。不要先扫描全部历史再在Java中截断。

验收：R05-T01 首次已有大量历史仅建立H；T02 基线游标后101事件分两批完整补齐；T03 同消息多事件正确合并且进度不跳过；T04 他人/他项目/伪造/第7天到期边界；T05 补页过程中新增/撤回无遗漏；T06 before/after/search不同模式边界正确；T07 失权优先拒绝、重新加入不能继续旧授权代次游标；T08 变更不影响未读与已读；T09 大正文/引用在响应大小上限内可完成同步。

2. 普通历史页按实际连续序号合并区间；稀疏搜索只记录实际返回的点/连续片段，不用最小最大值包住中间未返回消息。撤回占位保留合法sequence，可以参与覆盖；不能通过物理删除制造不可解释缺口。
3. 每次 GET 只更新下发范围，不改变已读位置。记录写入不能放在 readOnly 事务中；与F04的一致性快照及并发策略一起设计，不通过去掉事务牺牲同步正确性。
4. PUT 接入统一 Idempotency-Key、规范化请求摘要、本人项目作用域及当前授权检查。缺键、同键异体沿用统一错误码。回放返回合法的当前最大位置，不把其他设备已推进的游标回退成旧缓存值。
5. 在同一事务锁定本人项目read_state（首次并发创建用UPSERT及后续锁）。设当前 L、请求 T：T<=L 为合法无回退；T>L 时验证最新序号和 `(L,T]` 的完整授权下发覆盖，出现任何缺口拒绝，不执行 GREATEST 直接跳过。
6. 合并相邻/重叠区间，删除已被L覆盖的范围以控制空间；授权失效后旧区间不可复用。重新加入按契约保留有权读取历史，但必须重新取得当前授权下发证据；保存的旧已读基线与新的下发代次分开处理。
7. 存量迁移保留已有 last_sequence 作为旧基线，明确无法追溯证明此前展示；不把0到最新批量标成“已下发”，不擅自清空用户已有阅读进度。
8. 两设备同时推进以锁后最新L校验，允许合法max；失败不得影响另一设备成功进度。下发记录丢失时保守要求重新拉取，不能放宽为只校验latest。
