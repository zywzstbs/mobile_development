## 3. G01 / S01：聊天变更游标改为不可变边界

### 3.1 修改范围

- `community/application/ChatService.messages/resolveSyncCursor`。
- `community/persistence/ChatRepository` 的游标创建、读取、更新与过期清理。
- V019中的chat_sync_cursor兼容策略；如需新字段或索引，新增V020或后续编号。
- `ChatFixP13IT` 中错误的同token消费预期；新增断线和并发回归。

保持CHAT-01路径、afterChangeCursor、changes、nextChangeCursor、hasMoreChanges字段不变。旧数值游标仍按既有协议过期处理。

### 3.2 必须成立的约束

- 一个token从签发到过期始终表示同一个 `(user, project, authorizationEpoch, position)`。
- GET不能修改输入token的位置。服务器事务提交不等于客户端收到响应。
- 一个旧token可以重复读取；投影使用当前安全状态，因此重复响应的正文/revision不必字节相同，但不能跳过未确认边界后的变更。
- nextChangeCursor只表示本次实际扫描边界，不能跳到尚未发出的最新序号。
- 保留首次无游标建立高水位、每批扫描最多100个事件、当前权限重查和撤回占位规则。

### 3.3 推荐算法

```text
读取当前身份/项目授权，进入既有一致性事务。
若无输入游标：
  在同一快照读取消息历史和变更高水位H；
  签发不可变token(H)，changes=[]，hasMoreChanges=false。
否则：
  解析输入token(C)，核本人/项目/代次/期限/可恢复边界；
  读取同一快照内C之后最多101个变更事件；
  本批取前100个，额外1个仅用于hasMoreChanges；
  扫描边界N=本批最后事件序号，无事件则N=C；
  按消息ID合并为当前安全投影；
  N>C时签发新token(N)，不更新token(C)；
  N=C时可直接返回仍有效的原token，避免每5秒无变化也插入一行；
  返回items、changes、nextChangeCursor和两个独立hasMore字段。
```

具体处理：

1. 删除或停止调用 `updateSyncCursorPosition`。不允许仅更换返回字符串，但仍把旧记录位置覆盖。
2. 新游标使用现有安全随机token并仅存hash；原token留在有效期内供重试。保留当前REPEATABLE_READ一致性，不改回多个READ_COMMITTED查询。
3. 新token按签发时间7天有效。事件保留边界独立检查，若数据已经无法连续恢复，即使token未到期也必须按CHAT_SYNC_EXPIRED处理，不能借续签“复活”缺失历史。
4. 重试旧C可再签发等价新token；不同字符串代表相同N不影响正确性。若需要复用token减少存储，不能依赖存储hash还原原token，且不能把不可变性改回消费状态。
5. 双请求同时使用C，不得因争抢更新同一游标而失败。下发区间记录仍可能竞争，检查现有记录代码；如发生序列化失败，采用已有可重试事务策略，不能返回不完整changes假成功。
6. 维护到期token清理。不能在首次下一页时立即删除上一页token；仅本项目在线用户清理会遗留长期不登录用户的数据，增加受控批量过期清理或明确现有调度入口，禁止每次全表无界删除。
7. 已读范围登记仍只来自items；changes不改变阅读游标或未读数。

### 3.4 V019存量token处理

旧实现已经原地推进的token无法证明客户端收到过哪些页，不能直接将其视为可靠的不可变起点。推荐部署修复时统一失效旧chat_sync_cursor，让客户端按既有CHAT_SYNC_EXPIRED规则重建历史基线。

实现可选择新增迁移删除该临时游标表里的旧行，或加格式版本并拒绝旧版本。两种均只处理可重建的同步token，不删除chat_message/chat_change/chat_read_state，也不清用户作品或幂等回执。执行记录说明这一兼容行为；不能修改V019原脚本。

## 4. G02 / S02：正式贡献固定到实际交付版本

### 4.1 修改范围与事实来源

`team/application/WorkSourceQueryService.sources/canReference`，`ProfileWorksService.requireSourceProject`调用链；核查DeliveryRepository和既有submission快照，但不随意改变提交/验收协议。

现有关系：

- `unit_acceptance`包含unit_id、submission_id、acceptance_id、passed。
- `submission`固定agreement_version、agreement_snapshot、unit_ids_json、due_snapshot和unit_due_snapshot_json。
- `unit_share`保留同交付项的不同agreement_version。
- passed unit存在唯一约束，不能把历次退回或未通过验收计为有效成果。

### 4.2 建立唯一的内部证据查询

建议在WorkSourceQueryService的仓储层建立共用CTE/查询构造，避免sources与canReference各复制一份独立SQL。内部证据可表示为：

```text
projectId, taskId, mode, evidenceKind,
evidenceId, unitId?, submissionId, acceptanceId,
userId, agreementVersion?, submittedAt, effectiveDueAt?, reviewerId?
```

这里只是内部结果，不新增HTTP字段。先产生“本人有权且归属正确的证据行”，再聚合来源项目和计数，最后据同一查询判断canReference。

### 4.3 正式证据SQL核心条件

```sql
FROM unit_acceptance ua
JOIN submission sub ON sub.id = ua.submission_id
JOIN acceptance ac
  ON ac.id = ua.acceptance_id AND ac.submission_id = sub.id
JOIN delivery_unit u ON u.id = ua.unit_id AND u.task_id = sub.task_id
JOIN task t ON t.id = sub.task_id AND t.mode = 'ASSESSED'
JOIN unit_share sh
  ON sh.unit_id = ua.unit_id
 AND sh.agreement_version = sub.agreement_version
 AND sh.user_id = :user_id
WHERE ua.passed = true
  AND sub.status = 'REVIEWED'
```

这是关键关联示意，不是可直接覆盖全部业务的完整SQL。还需按既有校验保证所选unit在submission.unit_ids_json中、份额是当次有效贡献、项目归属及权限一致。若历史已完成项在后续版本中以保留原版本方式存在，应以当次提交快照为准，不能强迫它改成当前版本。

逐步实施：

1. 核对agreement_snapshot结构和unit_share版本是否可靠保留，写清唯一事实来源。完整可用时以提交绑定版本关联；不能无条件取MAX(version)或当前ACTIVE约定。
2. 对快照/版本不完整的旧数据，列出可从既有记录确定恢复的条件。无法判定归属时不得回退为“任意历史份额都算”，应排除不可信证据并留下修复记录，不猜测用户贡献。
3. confirmedUnits需同时关联正确通过验收及本人的当次份额，不能仅发现一条confirmation就绕过证据归属。
4. 独立验收按ac.id计一次，判断自验时只看该submission覆盖项的当次贡献者。某人曾在v1有份额，不表示v2仍是贡献者；同样，当前已离组不意味着他当时没有有效独立验收记录。
5. 准时/迟交以submission的对应unit截止快照和submitted_at比较；优先unit_due_snapshot，其次可信due_snapshot。不能用后来修改的task.due_at改写历史。快照缺失且无法恢复时，不伪造准时/迟交结论。
6. 多个证据类型先分别去重聚合，再按project合并；禁止直接一对多大JOIN造成交付/确认/验收相乘。
7. 输出保持myEvidence.projectId等标准字段及已保留兼容别名。历史离组只允许证据安全摘要，不额外返回内部任务正文、聊天、文件链接或他人成绩。
8. 保存来源项目与列表共用谓词，保证“可选→可保存”和“无权→不能直接伪造sourceProjectId”都成立。

### 4.4 必须补的回归

- S02-T01：v1 A承担未完成U→合法交接→v2 B承担→B提交并通过。A不新增U证据；B有正确证据；A不能仅凭旧份额保存该来源作品。

## 5. G03 / S03：普通任务也进入作品证据

### 5.1 为什么不直接删除ASSESSED过滤

普通任务unitIds=[]，没有正式unit_share，贡献确认也不是同一套分项流程。删除mode条件仍然会被INNER JOIN delivery_unit/unit_share排除，需要独立的普通来源分支。

现有 `DeliveryService.checkedUnits` 明确普通提交必须由当时task.ownerId本人执行，因此合法普通submission.submitted_by可作为当次完成者的持久依据。之后负责人改变时，不能改用当前ownerId重算历史。若以后支持代交，必须另增明确贡献快照，不能继续使用这个推论。

### 5.2 查询与统计步骤

1. 普通有效交付从ORDINARY task→submission(status=REVIEWED)→acceptance(decision=PASSED)取得，归属合法提交人submitted_by。PARTIAL/RETURNED不能冒充整个普通任务有效完成。
2. 普通独立验收按acceptance.kind=INDEPENDENT及合法验收人归属，排除提交人自验；SELF_CHECK不能记独立验收。是否计退回的真实独立验收沿用正式分支的统一定义，不为普通任务另造一种口径。
3. 截止使用提交的due_snapshot，准时为submitted_at<=due_snapshot、迟交为>。缺快照按G02的数据缺口策略处理。
4. 将普通证据以明确类型前缀与正式证据UNION ALL，再按对应证据键去重。不能让普通submissionId与正式unitId字符串相同造成意外合并。
5. 延续现有对外统计单位：正式acceptedDeliveries按有效通过交付项去重，普通按整任务有效通过交付记录去重；ordinary confirmedUnits为0，不伪造正式确认项。若原契约/P50已有更明确的统计单位规定，必须按其统一，记录差异，不能未经说明把全部历史统计改成另一单位。
6. acceptedDeliveries和onTime/late使用同一证据集合。快照完整时，onTime+late应等于acceptedDeliveries；存在不可确定截止时可小于，必须在交付记录说明原因，不能用假时间补齐。
7. 只担任合法独立验收者也可按相应证据规则形成来源，acceptedDeliveries可为0、independentReviews>0，不能硬要求每个来源都必须有本人的交付。
8. sources和canReference都覆盖普通分支；作品保存仍要求真实有权来源。不要退回“只要当前成员就可随便引用”的粗放校验。

### 7.1 公共授权策略

建议提取小型 `PersonnelCaseAccessPolicy`，供GovService、候选查询、TodoQueryService复用，避免每个模块自行拼一套权限。至少区分：

- canReadCase：当前有必要读取资格，不等于可办理。
- canHandleCase：具备本case的当前处理资格、账号有效、无回避冲突。
- canInitiateHandoff：当前处理人且可以继续办理、case允许交接。
- canReceiveHandoff：本case有效候选、非发起人、无回避冲突。
- canRespondHandoff：指定接续人、交接仍PENDING、来源与授权仍有效。

### 7.2 已确认方案A的授权数据设计

先搜索是否已有真正case级授权表；有则复用。仅班级级capability或全局角色不等价。无可复用机制时，建议新建 `personnel_case_grant`：

|字段|用途|
|---|---|
|id、case_id、user_id|稳定授权ID与明确对象，外键|
|status、revision|有效/撤销状态和并发更新|
|granted_by、granted_at|管理员CLI授权审计|
|revoked_by、revoked_at、reason|撤销责任、时间和原因|
|expires_at（可空）|可选截止；为空表示持续到撤销或case结束，不默认授予跨case永久权限|

建立有效授权唯一约束和case/user/status查询索引。管理员经受控CLI明确授权指定教师处理指定case；授予授权不自动接手、不自动接受handoff、不授予其他case、课程成绩、聊天或全部项目读权。

默认继承已有“当前任课教师可按规则处理”能力，新case级授权补充其他接续教师资格。课程权属变化后的处理权限以实时策略为准，不从旧待办或缓存继承。撤销后原人失权，当前合法负责教师按已有收回/重派流程处理，不能无人负责却返回成功。

必须核查并调整所有仍直接requireTeacher的相关case操作，避免接续后只能看到待办却不能读取材料/办理事项。边界限定为该case及其必要子资源；与该case无关的教师专属动作继续保持原权限。

### 7.2.1 管理员CLI与授权生命周期

建议在现有管理员CLI中添加 `personnel-case-grant` 的grant/revoke/list子命令（最终命名遵循现有CLI风格），不新增App管理员页面。grant至少接收caseId、teacherUserId、reason，可选expiresAt；revoke接收grantId、expectedRevision、reason。支持现有dry-run机制，实际命令须记录操作者与审计结果，不记录材料正文。

grant事务验证：case存在且未结束、双方学校范围合法、目标是已核验且有效的教师、无本项目回避冲突；目标可以不是该广场的当前任课教师。重复授予同一有效资格返回已有记录或按既有幂等协议处理，不重复生成有效授权；变更截止或撤销使用revision保护。禁止仅凭任意userId或全局管理员身份绕过目标资格校验。

授权没有自动接任效果。授权后目标可以出现在本case候选中；收到指定handoff后可读必要的交接说明并回应。只有接受后，才以当前assignee身份办理case及其必要材料，不允许未被指派的授权候选浏览整案私密内容或执行处理动作。

授权到期、撤销、账号停用、教师资格失效或出现回避冲突后，立即停止凭该授权读取/操作；其他独立有效权限仍需单独评估。case结案后该授权不能用于继续办理；历史档案读取沿用已有档案规则，不由这个处理授权自动赋予永久访问权。撤销不删除历史handoff、材料或审计。

撤销当前assignee的有效资格后，不自动接受其他人的交接。由当前任课教师走受控收回/重新指派流程；若现有收回只检查isTeacher，须改为检查原处理者是否仍具有有效case资格，避免已授权接任教师被错误判为失权。无有效处理人时明确暴露受阻状态，不返回假成功。
