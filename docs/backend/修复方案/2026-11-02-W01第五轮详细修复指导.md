# W01 第五轮详细修复指导：历史材料提交时间的证据校验

日期：2026-11-02。状态：待执行，本文不是修复完成声明。

适用基线：已实施 V022 的后端。依据：[第四轮复审](../审查记录/2026-11-02-V022第四轮修复复审.md)。本轮只修复历史时间恢复入口及其已产生数据的核查，不重做 U01 状态机、D01 教师权限、281 个接口或前端。

## 1. 已确定的规则

1. D02 已获用户确认：无法证明真实提交时间的历史版本返回 `createdAt:null`、`createdAtConfidence:"UNKNOWN"`，前端显示“历史提交时间不详”。无需重新询问。
2. 新提交继续使用服务器实际提交时间和 `EXACT`。不改变现有 HTTP 路径、请求字段、响应结构。
3. 管理员有权执行恢复，不代表管理员指定的回执一定正确；服务必须校验证据。
4. 本轮保留 CLI 的可靠恢复能力，但仅支持满足本文件完整条件的回执。旧回执不支持、已清理、无法解密或字段缺失时，明确拒绝并保持 UNKNOWN。无需为恢复率增加外部日志平台、人工填写时间或第三方服务。
5. V001～V022 不得重写。新增迁移仅用于确有需要的纠错审计结构；不得为了方便把全部历史记录清空。

## 2. 缺陷与修复目标

当前 `MaterialResponseTimeRecoveryService.recover` 只检查回执的 method、path、businessCode、userId、createdAt。同一学生对同一材料的 v1/v2 使用同一路径，因此 v1 回执可以恢复 v2。当前又把数据库生成的 `operation_receipt.created_at` 当成材料提交时间，而实际提交时间取自 `GovService.respondMaterialOnce` 的应用 Clock，二者不保证相等。

修复后必须证明以下完整关系：

```text
成功的 POST 提交回执
  → 原始加密结果中的材料 ID
  → 该次动作生成的顶层 responseVersion
  → 对应 response 条目的 version、authorId、createdAt、EXACT
  → 要恢复的 material_response(material_id, version, author_id)
```

**特别注意：不能只在回执的 responses 历史数组中找到目标版本就接受。** v2 的结果可能包含 v1；该回执产生的版本由顶层 `responseVersion` 证明，必须等于请求恢复的版本。

## 5. K01：实现可信证据读取与验证

### 5.1 查询原始回执

扩展 `GovRepository.OperationReceiptEvidence` 及查询，至少携带：`id,user_id,method,path,http_status,business_code,result_ciphertext,key_id`。`created_at` 可用于诊断，但不能作为候选提交时间；`expires_at` 可用于诊断，不改变正常幂等过期策略。

按回执 ID 直接读取存量记录。不得调用普通幂等 execute 来读取证据：它可能执行 action 或删除过期回执。不得调用当前 GET 或 ReplayProjector，因为当前状态不是历史原始提交结果。

仍存在且可验证的过期回执可以作为历史证据；已删除的回执返回明确失败，不延长保存期限、不重建回执。

### 5.2 验证外层信息

依次要求：

- 目标材料版本存在，版本为正整数，目标作者明确。
- method 为 `POST`，path 精确等于 `/api/v1/material-requests/{materialId}/responses`。
- `http_status=200`、`business_code=OK`，符合当前保存成功提交结果的实际格式。
- 回执 userId 等于目标版本 authorId。
- ciphertext 非空，keyId 等于当前 `IdempotencyCipher.keyId()`。项目目前只有单个配置密钥；不支持的旧 keyId 明确拒绝，不尝试猜测或自动创建密钥轮换系统。

### 5.3 解密和结构验证

复用注入的 `IdempotencyCipher` 和项目 ObjectMapper。建议解析为 JsonNode 后逐项验证字段与类型，避免旧 JSON 缺字段被 record 默认值掩盖。当前密文保存的是 `GovViews.Material` 本身，不是 HTTP envelope；不要凭空解析 `data.material`。

必须同时满足：

1. 根节点 `id` 是目标 materialId。
2. 根节点 `responseVersion` 为整数，严格等于目标 version。
3. `responses` 中恰好一条 version 等于目标版本；缺失、重复均拒绝。
4. 此条目的 authorId 等于目标版本作者及回执 userId。
5. 此条目的 `createdAtConfidence` 明确为 `EXACT`；缺失或 UNKNOWN 均拒绝。
6. 此条目 `createdAt` 为非空合法时间，按 Instant 解析。
7. 此条目为该次新提交，`withdrawn` 明确为 false。
8. 如存在兼容对象 `response`，其版本、作者、时间、可信度与上述条目必须一致；出现冲突则拒绝。不能在数组验证失败后改用兼容对象“兜底”。

当前旧格式如果没有 responses 或可信度字段，拒绝恢复即可。不能把“字段缺失但看起来像时间”推断成 EXACT，也不能从 content、evidenceRefs、updatedAt、审核时间、回执创建时间中猜测。

### 5.4 时间精度与错误处理

项目 `JacksonConfig` 按 UTC 秒序列化 Instant，回执内时间可能只保留到秒。因此恢复的是**原始服务器提交结果所保留的秒级时间**；EXACT 表示来源可信，不代表恢复了原始纳秒。保留当前契约精度，不补造小数秒，不改全局序列化。测试分别断言存储的回执时间和对外秒级显示，不要求恢复原来已经丢失的小数部分。

验证结果至少包含 materialId、version、authorId、submittedAt、receiptId。不得让调用方传入未经验证的 submittedAt。

缺失回执/目标使用既有 NOT_FOUND；参数错误使用既有校验错误；证据不匹配、格式或密钥不支持使用既有 SOURCE_CHANGED，并配清楚的安全原因。不要新增 App 公共错误码。数据库连接失败等基础设施异常不得伪装成“证据不足”。

禁止日志或 CLI 输出解密正文、附件、密文、密钥。解析异常不要把完整 JSON 拼入异常消息；可以输出回执 ID、材料 ID、版本及失败原因类别。

## 6. K02：把验证接入恢复事务

处理顺序：

```text
校验参数 → 读取目标 → 读取并验证原始回执 → 得到 verifiedEvidence
→ 检查目标当前可信度与已有证据 → dry-run 或条件更新 → 返回结果
```

- UNKNOWN/null：dry-run 返回 DRY_RUN 和 verifiedEvidence.submittedAt，不产生业务写入；正式执行用这个时间写 EXACT/RECOVERED_EVIDENCE。
- EXACT：只有 `time_source=RECOVERED_EVIDENCE`、time_evidence 等于同一回执引用、created_at 等于已验证的提交时间时返回 ALREADY_RECOVERED；不更新恢复人或恢复时刻。
- EXACT 但证据不同、时间不同，或者来源为 SERVER_SUBMISSION：拒绝覆盖。旧错误恢复不允许在普通恢复路径中悄悄“修好”。
- UNKNOWN 却时间非空或其他不合法组合：拒绝，不能自动清洗异常数据。
- 正式更新继续使用 `WHERE material_id=? AND version=? AND created_at_confidence='UNKNOWN' AND created_at IS NULL`，校验影响行数为 1；不得先无条件覆盖再判断。
- 更新记录来源、回执引用、actorId、恢复操作时刻；操作时刻来自 Clock，但提交时间来自证据。保留 legacy_recorded_at。
- 行数为 0 时可以返回 SOURCE_CHANGED；若为实现并发幂等而重读，必须完整验证“同证据同时间”才可返回 ALREADY_RECOVERED。禁止以 UPDATE 失败推断成功。
- 若增加行锁，遵守 case → material → response 的既有顺序。不要持有 response 锁后再获取 case/material 锁。
- 不更改 case 状态、材料状态、作者、正文、版本号、审核记录或权限。恢复历史时间本身不应受当前材料是否已验收/事项是否结案限制。

修正服务类注释中“回执时间就是该次提交的真实服务器时刻”的错误描述。

## 7. K03：核查已经执行过的旧恢复

代码修好不会自动修复已污染的 EXACT 数据。只扫描 `time_source=RECOVERED_EVIDENCE`，逐条复用 K01 校验器验证其 time_evidence；禁止扫描后把所有 EXACT 一起置空。

输出三类结果：

|类别|判断|处理|
|---|---|---|
|VALID|完整证据匹配，当前时间等于证据时间|保持不变|
|CORRECTION_REQUIRED|证据可靠，但当前恢复时间与证据时间不同|受控纠错为证据时间，并保留修改前审计|
|UNVERIFIABLE|证据缺失、跨版本、无法解密或缺实际时间|受控纠错为 null/UNKNOWN/LEGACY_UNKNOWN，保留修改前审计|

只读核查不得产生纠错写入。如果候选为零，记录查询环境及数量即可，无需建立额外审计表。若无访问权限或环境不可用，记录待核查步骤，不推断零记录。

如确有待纠错行，执行模型须交付单独的受控纠错命令或脚本：

1. 先在副本验证并输出 dry-run 清单；实际环境先按既有备份流程留备份，不在测试命令中自动连接云端。
2. 修改前持久化审计：材料/版本、原 createdAt/confidence/source/evidence/recoveredBy/recoveredAt、原诊断值、本次原因、目标值、执行人、执行时间。不得只依赖终端输出保存原审计。
3. 优先复用适用的现有审计机制；若不适用，新增最小审计结构，使用下一个未占用 Flyway 版本（当前若仍到 V022，则为 V023），不修改旧脚本。审计插入与纠错 UPDATE 在同一事务。
4. UPDATE 按主键和读取时的原来源、时间、证据等状态做并发保护。重复执行不重复纠错，冲突中止并要求重新核查。
5. 纠错为 UNKNOWN 时，将当前恢复字段清空，原值完整存入纠错审计；legacy_recorded_at 保持原样，不能拿它保存本轮错误恢复时间。纠错为 EXACT 时保留可追溯回执引用并记本次操作审计。
6. 不碰 SERVER_SUBMISSION；不能在启动迁移时自动解密全库或不可逆清空数据。涉及真实环境的执行情况单独记录，未执行就明确说明。

这是有受影响数据时的条件任务，不要求为没有数据的课程演示建设通用数据修复平台。
