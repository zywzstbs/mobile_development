## 二、H00：先建立一套明确的权限词汇

### 2.1 将四种概念分开

1. **有效教师身份**：数据库当前账号有效、核验有效、具有TEACHER角色，并在该case允许的学校范围。不得仅信任登录时JWT里的角色或授予grant时的一次检查。
2. **本case处理资格**：有效教师身份且无回避冲突，并且是该广场当前任课教师或拥有本case未撤销、未到期的授权。
3. **本case当前处理人**：具备上述资格，且 `case.assigneeId == userId`。只有当前处理人可执行正常办理动作。
4. **本case读取资格**：分本人材料、指定交接必要摘要、当前处理人全案、当前任课教师契约允许的监督读取四类。读取不等于办理，更不等于自动接任。

`hasQualification`目前只返回“任课关系或grant存在”，不能继续用这个含混名字同时承担有效资格、读取、处理和收回判断。建议改为明确的方法并删除/限制旧方法调用，避免后续又绕过账号/角色/回避条件。

### 2.2 建议统一策略接口

可以保留PersonnelCaseAccessPolicy类，但将输入和含义明确化：

```text
isEligibleTeacher(case, user)
hasEffectiveCaseQualification(case, user)
isCurrentHandler(case, user)
canReadCase(case, user)
canReadMaterial(case, material, user)
canReadHandoff(case, handoff, user)
canRespondHandoff(case, handoff, user)
canMakePersonnelDecision(case, linkedResource, user)
canRecoverCase(case, currentTeacher)
```

允许再拆内部函数，但对外不能到处重复拼 `teacher || grant`。同一身份事实可用内部只读快照对象批量加载，避免每条待办多次SQL；快照只在当前请求/事务使用，不缓存到下次请求替代实时核权。

### 2.3 权限矩阵

|身份/状态|材料正文|交接必要说明|正常办理/人员决定|收回失权事项|
|---|---|---|---|---|
|材料指定学生|本人有权材料|不因学生身份获得|无教师办理权|否|
|只有有效case授权，未收到交接|不能读全案|无指定交接则无权|否|否|
|有效授权且被指定为PENDING接续人|不能借交接读全案|可读指定交接必要说明|只可按协议回应交接|否|
|有效资格且是当前assignee|本case必要材料|当前有权交接|是，且case处于可办理状态|不凭该身份抢回其他事项|
|当前任课教师但已经交出case|原契约允许的监督读取|依既有监督规则|不得绕过assignee代办|原处理人确已失权时可以|
|角色撤销/停用/核验失效/需回避|不能凭旧教师授权读取|不能凭历史from/to继续读取|否|不能以失效身份收回|
|管理员|CLI授权元数据和审计|无App案情读取权|无App代办权|通过现有合法管理流程，不绕过业务身份|

case结案后的读取遵守已有历史读取规则；不能因为处理权终止就无差别公开历史，也不能为了实现收回把CLOSED事项重新打开。

### 2.4 入口核查表

H00交付时逐项登记是否使用统一策略、是否有当前状态投影、是否落在事务中：

- personnelCase、squareCases、caseView及嵌套materials/history。
- material、myMaterials、requestMaterial、respondMaterial、reviewMaterial、withdrawMaterial。
- handoffCandidates、handoff、myHandoffs、create/respond/cancelHandoff。
- acceptCase、updateCase、closeCase、recover。
- member-change与removal-vote的personnel-decisions、相应幂等回放。
- TodoQueryService的PERSONNEL_HANDOFF及关联待办、dashboard计数。
- PersonnelCaseGrantAdminService授予/撤销、管理员用户导入的角色/停用/学校变更、核验状态改变。

不要仅新增策略类却让一半入口继续调用旧requireTeacher或裸grant查询。

## 三、H01 / T02：教师资格必须在使用时仍然有效

### 3.1 修改范围

PersonnelCaseAccessPolicy；GovRepository.accountEligible、handoffCandidates、activeGrant调用；TodoQueryService对应查询；所有case策略使用者；AdminImportService及角色/状态变更对并发权限的影响。

### 3.2 实施步骤

1. 将当前只查 `disabled=false AND identity_status='VERIFIED'` 的资格查询扩展为真实有效教师检查。增加 `EXISTS user_role(role='TEACHER')`，并核case对应学校。不要把它改成“必须有同广场active teacher_assignment”，否则D01接续教师会再次全部被排除。
2. `hasEffectiveCaseQualification = 有效教师 && 无回避冲突 && (当前任课关系 || 本case有效grant)`。grant到期严格使用项目Clock，`now == expiresAt`为失效。
3. 读取、候选、待办、回应、人员决定及收回使用同一逻辑。批量SQL应与策略语义一致，记录映射；不允许Java侧检查角色而待办SQL仍只检查账号。
4. grant授予时保留目标资格校验；使用时重查不能替代创建时校验。管理员重复导入去掉TEACHER角色后，即使grant仍ACTIVE，也不能继续授权。
5. 不必物理删除所有旧grant才能失权。保留grant/审计历史，并让运行期策略判定其当前无效；恢复身份后的资格是否恢复遵循grant仍有效这一既有语义，不能默默生成新授权。
6. JWT会话未过期也不能保留已失效的教师处理权。测试应覆盖旧token和重新登录后的token；若认证层先拒绝旧token，可以接受该拒绝，但不能仅测认证失败就声称新策略正确。
7. 数据库角色/状态变化与敏感写操作之间的竞争按第八节协调；不要只在Controller入口读一次身份然后在长事务后无条件写入。

### 3.3 必须验证

- T02-A：B获case授权并接任，管理员把B改为仅STUDENT，B不能读材料/事项、写记录、请求材料、发交接或作人员决定。
- T02-B：只保留普通有效账号、旧grant有效，候选与待办也必须消失。
- T02-C：未核验、停用、不同学校、回避冲突分别拒绝；合法授权教师虽然不是当前任课教师，仍可正常接任。
- T02-D：原成功动作的同键回放在角色失效后拒绝，不从幂等缓存返回私密内容。
- T02-E：当前任课教师A仍可依法收回失权B的事项；不能误删历史授权或内容。

## 四、H01 / T03：失权收回必须检查完整能力

### 4.1 根因和修改点

`GovService.recoverOnce`目前用hasQualification阻止收回，但canHandleCase还检查账号和回避。因此可能出现“不能办，但不准收回”。更改该判断，并核对canRecoverCase、当前任课教师校验和case终态条件。

### 4.2 建议处理流程

1. 校验发起收回者是该广场当前有效任课教师、无回避，读取权与版本合法。
2. 锁case并重查状态。CLOSED事项不走收回重开；无人受理的OPEN事项优先按既有acceptances流程，不将“收回”混成任意认领。
3. 取旧assignee的当前完整资格：有效教师、学校范围、无回避、任课关系或有效case授权。旧处理人仍合法时拒绝无理由抢回；旧处理人因任一条件失效时允许依法收回。
4. 使用既有expectedRevision并校验理由；在同事务取消仍PENDING的交接，更新assignee/revision，记录审计和必要通知。
5. 按统一锁顺序处理子资源，避免与接受交接反向锁。收回后旧处理人再尝试写入必须拒绝。
6. 保留旧材料、处理记录、grant和handoff历史；不能“恢复权限”来临时绕过收回失败。

### 4.3 回归矩阵

|旧处理人状态|收回预期|
|---|---|
|仍有效且无回避|拒绝无理由抢回|
|grant已撤销/正好到期|允许依法收回|
|grant有效但账号停用|允许依法收回|
|grant有效但核验/TEACHER角色失效|允许依法收回|
|grant有效但产生项目回避冲突|允许依法收回|
|case已结案|不通过收回隐式重新打开|

每种失权都测“旧人不能办、当前教师能收回、收回后新负责人可继续办理”三步，不能只测一个403。

## 五、H02 / T01：材料正文与版本的安全投影

### 5.1 修改范围

`GovService.material/caseView/materialView`；所有materialView调用者；GovViews.Material；必要的材料历史仓储；原API MaterialRequest字段与P50实际解析。

### 5.2 具体改法

1. 删除“是不是recipient”作为唯一showResponse条件。用策略决定当前读取投影，建议显式传授权上下文或投影类型，防止新的boolean参数再次混淆“提交人”和“正文可读”。
2. 材料详情与case内嵌材料调用同一投影函数；创建、回应、审核、撤回及幂等回放也核对，不能只修GET详情。
3. 本人有权材料、有权处理教师和契约允许监督读取者返回实际版本内容；未接任授权候选不能借case grant读取全案材料。对无读取权者按既有403/404协议拒绝，不通过返回{}暗示存在私人材料。
4. 内容已撤回时按现有撤回规则占位；不能因为是教师就恢复所有历史正文。若契约允许特定受理证据保留，必须沿用该专门资格，不能混入普通材料投影。
5. 核对原契约要求的 `responses[]`、version、content、evidenceRefs、createdAt等字段，以及P50使用的字段。当前只有response对象并不自动符合原契约；保留必要兼容别名，但标准字段不能缺失或伪造。
6. 如果现有表只保存最后response_json，而接口要求必要历史版本，应新增迁移保存真实材料版本；旧数据只迁移能够证明的当前版本，不编造前几版正文和时间。此项按实际契约差异实施，不无依据创建全量事件系统。
7. 审核必须核对指定responseVersion，避免教师读取v1后学生更新v2，审核却无意确认v2。投影修复不能破坏该版本冲突语义。
8. 材料引用/附件链接通过现有授权服务生成，不从旧JSON直接公开越权文件。不要把“有权读本材料”扩成有权读同项目全部文件。

### 5.3 测试流程

- T01-A：A要求学生材料→学生提交明确正文及证据→A读取详情与case内嵌结果，两处正文、版本一致。
- T01-B：B已授权但未接任时拒绝全案材料；B接受后能读必要材料并审核。
- T01-C：同学校无关教师、其他case授权者、管理员App身份不能读本材料正文。
- T01-D：B停用/撤权/角色失效后读取及原成功写请求回放拒绝。
- T01-E：读取v1→提交v2→审核v1产生来源冲突，不能误审新内容。
- T01-F：撤回后详情、内嵌、列表及回放都遵守占位；历史版本不假造。
- T01-G：断言HTTP JSON具体字段和content，不只断言状态码及responseVersion大于0。

之前临时方法验证已经确认原代码会输出 `responseVersion=1,response={}`。应把这一反例升级为真实业务链路测试，而不是仅测试private方法。

## 六、H03 / T04：关联人员决定由本case当前处理人办理

### 6.1 关联关系必须从数据库解析

目标路径：member-changes和removal-votes的personnel-decisions；修改GovService.decideOnce、decideVoteOnce及授权回调。保留现有请求字段，不新增让客户端任选caseId的绕权入口。

1. member_change根据 `personnel_case.member_change_id` 查关联case，并验证project/square/subject的既有关系。
2. removal_vote按现有vote→member_change→case关系解析；如某状态允许在case建立前处理，先核原状态机和真实创建流程，确定该动作所属case。不能使用“该项目任意一个case”替代，也不能查不到就回退为全局教师可办。
3. 如果发现同业务对象多个无明确有效性的case，按现有规则确定唯一当前事项；数据异常明确拒绝并记录，不随意LIMIT 1。
4. 只有本case当前合法assignee可作关联决定；账号/角色/回避/授权由H01策略核。B是合法接任教师就允许，A虽然仍是课程任课教师也不能代替当前负责人作同一个办理决定。
5. 当前任课教师的监督读取、失权收回仍保留；监督权限不能混成直接改结果。其他课程成绩、任课转交等动作不因case授权而开放。

### 6.2 事务与幂等

- 只读预查关联ID→按照第八节顺序锁case和change/vote→锁后重查关联、版本和可处理状态→核当前assignee→写决定与审计。
- ALLOW_HANDOVER/RETURN、placementPlan/reason、成员变更/表决状态转换保持原协议；本轮修授权，不重设计人员状态机。
- 不能先锁change再锁case而另一条路径先case后change；关联链路锁要列入统一清单。
- 幂等授权回调必须定位并核这个具体资源的当前读取资格，不能继续使用只检查账号有效的默认write重载。新执行另核当前办理资格。
- 同键回放不重复决定、不重复event；无权后不能通过旧成功回执读到人员事实。只读监督者是否可以回放旧办理结果与新执行要区分，按已有读取范围处理，不借回放代办。

### 6.3 用例

- T04-A：A受理→合法交给B→B对本case关联EXIT作决定成功→A对相同办理动作被拒。
- T04-B：B有case X资格，直接传case Y的change/vote ID拒绝；同项目不同case也拒绝。
- T04-C：B只是授权候选未接任，或者已再交给C，办理拒绝。
- T04-D：版本过期、终态、关联缺失、关系不一致都不能写半份决定。
- T04-E：同键重复只一次效果，同键异体冲突，失权后的回放拒绝；人员决定成功后继续原组内交接/执行链路。
- T04-F：removal-vote真实状态流程产生合法case，再验证B办理；不能手工塞不可能的PASSED/vote/case组合冒充端到端。

## 七、H04 / T05：交接读取、列表与待办统一授权

### 7.1 两个GET必须接入策略

`GET /personnel-handoffs/{handoffId}` 和 `GET /me/personnel-handoffs` 当前只按历史from/to，需修改GovService.handoff/myHandoffs及仓储查询。

- 详情：当前有效身份→定位handoff与case→按阶段核canReadHandoff→返回必要字段。不把“历史参与过”视为永久读取权。
- PENDING接续人：具备有效case资格且是指定toUser，可读这一份必要交接说明；仍不能读取完整case材料。
- 发起人：仍具备当前合法读取资格才可读；已失权不因fromUserId匹配而放行。
- 终态：按已有本case历史读取资格判断，不凭终态或历史身份自动公开。当前任课教师监督读取与普通参与人历史读取分别核定。
- 列表：从“本人参与”候选集中过滤当前无权项；一条无权不导致整个列表异常。total/分页若存在，必须以授权后的集合为准，不泄漏被过滤记录数量。

### 7.2 投影和回放

1. 核对PersonnelHandoff契约中的sourceCaseRevision、facts、unresolvedQuestions、decisionsNeeded等字段；当前仅六个元数据字段不足以让接续人了解交接。先修权限再补齐合法投影，不能先扩大字段暴露而保留旧from/to校验。
2. 最小必要交接说明不等于全案history或附件全集。当前被指定者可看交接快照用于决定是否接受，不授予任意case浏览权。
3. 创建、回应、取消响应及幂等回放使用同一权限边界；回放可保留稳定动作结果，但不得返回当前无权材料或早已失效的敏感投影。
4. TodoQueryService与GET使用同样的有效教师、双方资格和来源状态条件，避免点击待办必然403；若用户操作期间状态改变导致403/409，属于合法竞争，前端刷新。
5. 客户端不能把403或失权当空同步并继续展示旧缓存；沿用既有失权清缓存机制，不新增秘密读取接口帮助恢复旧内容。

### 7.3 用例

- T05-A：合法PENDING指定B能读必要交接摘要，仍不能读取全案材料。
- T05-B：撤销grant/到期/移除角色/停用/回避后，详情与本人列表一致失权或过滤，待办同步消失。
- T05-C：一个列表含有权和无权两条，只返回有权条；不因无权项让整个请求500，不泄漏被过滤total。
- T05-D：B接受后又合法交给C，B旧from/to身份不能获得超出当前资格的访问。
- T05-E：指定关系、来源版本、case/handoff终态变化时，读取与回应使用各自清楚的规则；既不能继续办理失效交接，也不能通过GET推进状态。
- T05-F：补齐JSON必填字段并实际断言facts内容，只对合法接续人返回必要说明。

## 八、H05 / T06：统一锁顺序和资格变更协调

### 8.1 最低要求：case永远先于其交接及其他子记录

对本轮人员事项事务，至少统一为：

```text
仅预读资源ID/关联（不据此写入或授权）
→ 按稳定ID锁case
→ 按稳定ID锁本case grant（确实需要协调资格时）
→ 按确定类型与ID顺序锁handoff / change / vote / material等实际涉及子资源
→ 重查资格、关联、版本与状态
→ 执行业务写入和审计
→ 一起提交
```

这是case子域的顺序，不允许据此忽略现有课程/项目/身份模块锁。H00必须列出真实父资源锁顺序；若操作还需square/project/user锁，应按已有全局约定先取得，然后进入case子域。跨case按ID排序，不能一条路径case→project、另一条project→case。

### 8.2 逐方法修改

|方法|现状/风险|修复要求|
|---|---|---|
|closeCaseOnce|case→UPDATE所有PENDING handoff|保留case先锁；子记录确定性处理|
|respondHandoffOnce|handoff→case，反向|预读caseId→锁case→锁handoff→重新核所有条件|
|cancelHandoffOnce|handoff→case|与respond同顺序；检查UPDATE返回行数及终态|
|recoverOnce|case→取消PENDING交接|与respond同顺序，重查旧负责人资格|
|createHandoffOnce|case后插handoff|锁后核来源、当前处理人、候选与唯一PENDING|
|reviewMaterialOnce|先material，case仅普通读|改为预读caseId→锁case→material→核当前处理人及responseVersion|
|关联人员决定|现有先change/vote|预查关联→按case和子资源统一顺序锁|
|grant/revoke|当前只锁授权scope/行|与case动作建立共同协调点，不能独立于办理事务修改资格|

不要在同事务先锁handoff，再“补锁case”，这仍保留反向顺序。预读拿到caseId之后，最终锁定记录仍需核caseId未变且确属目标case。

### 8.3 授权撤销与身份变更

1. 建议grant/revoke先锁case，再取得该case/user的advisory锁及grant行锁；所有使用该grant的敏感case事务也锁case。原advisory锁只串行grant/revoke，不能自动保护回应交接。
2. 重查用户角色/停用/核验与任课关系。对管理员导入、教师转交、成员加入等会改变处理资格的写路径，核查它们是否遵循可协调的锁/版本机制。
3. 若采用身份行锁或授权epoch，必须保证身份更新事务也触碰同一协调对象。只在读取方FOR SHARE而更新方仅修改user_role子表，不足以自动同步。
4. 不要求与完成前已在途请求实现不可能的“回收已发网络数据”；要求权限判断与业务提交有明确可解释的串行顺序，撤权完成后开始的请求一定失权，重叠操作不会留下互相矛盾的负责人状态。
5. 角色失效/授权撤销不自动完成交接或删除历史。需要由当前教师依法收回时，系统应能执行该流程。

### 8.4 必须新增的确定性并发用例

- T06-A：结案事务先拿case锁；接受事务尝试进入。修复后接受应在case处等待，不能先拿handoff反向阻塞结案；最终case/handoff状态一致，无死锁。
- T06-B：反向安排接受先拿case并完成，旧负责人结案重验后拒绝，不能结掉新负责人的事项。
- T06-C：收回失权事项与旧交接接受竞争，只有符合实时资格的一方可完成。
- T06-D：撤销grant与接受交接，明确顺序后断言合法结果，撤销完成后不能新接受。
- T06-E：接受与取消竞争继续回归；取消不得在UPDATE影响0行时返回虚假的CANCELLED成功。
- T06-F：材料审核与交接/撤权竞争，不能绕过当前负责人校验；学生响应v2与教师审核v1也保持版本冲突。

使用不同PG连接和事务内栅栏，在明确持有第一把锁后释放另一线程；设置有限测试超时并清理线程/事务。不要仅两个线程同时start就认为覆盖了死锁，也不要把所有500、死锁异常都当成预期冲突吞掉。固定锁顺序为主，有限可重试错误处理仅作为补充。
