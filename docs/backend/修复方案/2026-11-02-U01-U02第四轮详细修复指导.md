## 1. 已确认补充与执行顺序

### 1.1 D02：历史提交时间不可恢复时返回未知

用户已于2026-11-02明确接受：**仅对无法恢复真实提交时间的历史材料允许createdAt=null，增加时间可信度字段，前端显示“历史提交时间不详”；新提交仍返回准确时间。** 无需再问用户是否允许null。

本文件选用 `createdAtConfidence` 作为响应字段名，值为 `EXACT` 或 `UNKNOWN`：

- 新写入，或有可靠证据恢复的历史版本：`createdAt`为真实RFC3339 UTC时间，`createdAtConfidence="EXACT"`。
- 只有V021回填的最后修改时间、无提交证据的历史版本：`createdAt=null`，`createdAtConfidence="UNKNOWN"`。
- `UNKNOWN`不表示正文无效、不表示尚未提交、不表示新草稿。它只说明该版本提交时间未知。
- 不能用空字符串、1970年、当前时间或审核时间替代未知；前端不能对null强行解析或标为逾期。

字段名及枚举是落实已确认补充的具体设计。响应数组 `responses[]` 与兼容字段 `response` 使用一致结构；不改变材料请求、路径或业务ID。

### 2.2 名称差异要明确

当前实现和数据库使用 `RESPONDED` 表示待审核，原始通用状态表写 `SUBMITTED`。本文件状态矩阵中的RESPONDED指当前内部状态，不能因为修状态校验就全局替换枚举。

执行模型需核P50实际解析、已确认补充和具体接口约定：若需要将内部RESPONDED投影为契约SUBMITTED，在响应层明确映射并验证客户端；不得同时把新旧状态混入数据库让查询随机漏项。将核对结果记录到J00交付页，用户已确认的具体规则优先。

### 2.3 当前请求的判定顺序

1. 校验账号和资源当前读取/操作身份，不能向无权用户泄漏私密状态。
2. 区分幂等成功回放与新业务执行。回放按当前读取资格和安全投影返回，不重新转换状态。
3. 新执行进入既有幂等事务，预读只用于找到caseId。
4. 锁case，再锁material；必要时锁目标response行；重验关联和当前身份。
5. 先核expectedRevision，再核当前case/材料/目标版本是否允许动作；通过后才插入版本、审核或执行状态更新。
6. 版本不符用现有版本冲突码；状态不允许用现有资源/来源冲突协议，403只表示权限不足，不将所有冲突混成403。复用当前ApiCode及前端处理，不随意新增公共错误码。

## 3. J01 / U01：统一状态矩阵

### 3.1 材料层动作矩阵

以下矩阵以case尚未结案、操作者有对应身份、请求版本正确为前提；任一前提不成立均不能写入。

|材料状态|指定学生新提交/补交|指定学生撤回当前版|当前处理教师审核|
|---|---|---|---|
|OPEN|允许，产生首版|拒绝，无当前正文|拒绝|
|RESPONDED|允许，产生新版本，旧审核请求须失效|允许，撤回当前版|允许，必须核当前真实且未撤回版本|
|RETURNED|允许，产生新版本|按现有可撤回规则，当前版存在且未撤回才允许|拒绝；先等待学生重新提交|
|WITHDRAWN|允许，产生新版本|拒绝重复新撤回；旧成功同键可安全回放|拒绝|
|ACCEPTED|拒绝|拒绝|拒绝普通重复审核；原成功同键可回放|

这延续现有合法“审核前可补交v2”的用例。不能为了防止重复审核而禁止所有RESPONDED补交。也不能为实现状态修复偷偷增加“过截止一律不能补交”：材料截止是否阻止操作须遵循原契约，不能新增未经要求的处罚规则。

### 3.2 case层统一约束

- CLOSED：新提交、撤回、审核均拒绝；保留既有有权历史读取与同键回放，不通过普通材料接口重开case。
- OPEN/IN_PROGRESS：只有满足对应材料动作身份和已有业务条件才允许；教师审核仍要求当前合法assignee。
- case角色失效、学校不符、停用、回避等继续使用第三轮策略，不重新放宽。
- case与材料状态不同：材料已ACCEPTED不意味着case必须已CLOSED，case未CLOSED也不能让ACCEPTED材料随便重交。

### 3.3 推荐实现结构

新增小型纯规则组件或集中方法，例如 `MaterialActionPolicy`，输入锁后case、material、currentResponse及已有权限结果，输出三项动作许可及内部阻断原因。该名称是建议，可采用现有项目风格。

```text
canRespond = 有效指定学生
             && case允许写入
             && material处于允许回应状态

canWithdraw = 有效指定学生
              && case允许写入
              && material处于允许撤回状态
              && 当前response真实存在且未撤回

canReview = 当前有效处理人
            && case允许写入
            && material处于RESPONDED
            && 当前response真实存在且未撤回
```

`materialView`与三个写方法复用同一规则，不分别手写一份条件。字段can*只描述读取瞬间的资格，不能充当授权令牌；点击后状态被其他请求改变时，写入口仍锁后重查并拒绝。

规则组件不负责发SQL、不改变状态，身份判断仍由现有case策略承担，避免一个“通用权限工具”混合所有领域动作。

## 4. J01具体写路径修改

### 4.1 respondMaterialOnce

1. 从material预读caseId，锁case→material，重核归属、指定学生、账号与expectedRevision。
2. 应用状态矩阵：已结案或材料ACCEPTED立即拒绝，且在insertMaterialResponse之前拒绝。
3. 检查版本范围；当前responseVersion达到上限时明确按既有协议拒绝，不用整数溢出制造500。
4. version=旧responseVersion+1；用一次服务器Clock获取本次真实提交时间，保存正文、证据、author、时间可信度EXACT。
5. 更新material为RESPONDED和新responseVersion/revision；检查更新行数，失败回滚新版本行。
6. 保留旧版本及与其绑定的审核记录，不复制旧审核作为新版本已通过证明。
7. 返回当前有权投影；教师读到v1后学生提交v2，教师按v1审核必须冲突。

### 4.2 withdrawMaterialOnce

1. 锁顺序和身份/版本校验同上。
2. 拒绝case已CLOSED、材料ACCEPTED、OPEN、WITHDRAWN等不允许撤回状态。
3. 读取当前responseVersion对应行；不存在或已经withdrawn不能伪造成功。
4. `withdrawMaterialResponse`影响行数必须为1；再更新material状态和revision，全部同事务。
5. 保留该版本的编号、作者、原真实/未知时间及历史审核事实；正文和证据展示仍遵循原撤回安全投影，不借新时间字段恢复撤回内容。
6. 重复同键回放当前占位，换新键重撤回不能增加revision或伪造第二次业务效果。

### 4.3 reviewMaterialOnce

1. 锁case→material→所核当前response（如需要行锁），重查当前有效处理人和expectedRevision。
2. 必须是case可办理、material=RESPONDED、request.responseVersion=material.responseVersion。
3. 取实际response行并检查withdrawn=false。只检查Optional存在是不够的。
4. 校验决定与理由，沿用原接口规则；返回理由不得被清空绕过字段要求。
5. 仅通过所有校验后插入material_review并更新material为ACCEPTED或RETURNED；失败不新增审核行。
6. 普通同版再次审核只有在矩阵允许时才能发生；本轮不增加任意“改判”接口。要修改已接受结果应走已有明确业务流程，不能靠传最新revision重写。
7. 审核与撤回都由同一case/material锁串行：先撤回则后审核拒绝；先审核通过则后撤回拒绝。禁止出现“material=ACCEPTED但当前response.withdrawn=true”。

### 4.4 数据层最后一道保护

统一SQL条件应与锁后判断对应。例如更新时除了id/revision，可按动作加入允许的当前status，必要时使用独立仓储方法，避免万能updateMaterial掩盖非法转换。不要把复杂跨表业务强行写成不可维护的触发器。

response和review记录的外键、唯一键继续保持。若增加新约束，先检查历史是否存在错误组合；不能因约束失败删除历史数据或静默“修成成功”。输出异常ID并按审查后的存量策略处理。

## 5. J02 / U02：已确认的未知时间表达

### 5.1 对外数据约束

两条合法组合：

```json
{"createdAt":"2026-11-02T08:00:00Z","createdAtConfidence":"EXACT"}
```

```json
{"createdAt":null,"createdAtConfidence":"UNKNOWN"}
```

上述字段出现在每个responses[]条目及当前response兼容对象内。UNKNOWN时必须显式输出null，不能因全局NON_NULL策略省略createdAt；必要时在该DTO字段上局部覆盖序列化规则，不改变全系统空值策略。

新请求不增加客户端可写字段；客户端不能自报createdAt或EXACT，服务器仍按字段白名单拒绝伪造。

### 5.2 内部存储建议

新增迁移（当前V021，执行时确认最大编号，建议V022起）：

- material_response.created_at允许null。
- 新增created_at_confidence，枚举EXACT/UNKNOWN，不能为空。
- 新增legacy_recorded_at或等价内部列，保存旧回填的时间值，**仅诊断/审计使用，不作为真实提交时间向前端输出**。
- 可选内部time_source字段区分SERVER_SUBMISSION、RECOVERED_EVIDENCE、LEGACY_UNKNOWN；如采用，记录可靠恢复的证据ID/来源，不保存无必要敏感正文副本。
- 约束：EXACT必须created_at非空；UNKNOWN必须created_at为空。新应用写入必须显式填写EXACT，避免默认值把不可信回填误标成准确。

只修改响应时间的可信度，不把真实版本、作者、正文或撤回标记一起抹掉。

### 5.3 识别受影响的V021旧行

V021当前用 `substring('legacy-' || material_request.id,1,120)` 生成回填行ID。新提交使用服务端UUID。应利用明确的迁移来源识别旧行，同时核material_id、version及真实关联，不要仅对created_at“不像当前时间”的行猜测来源。

建议迁移步骤：

1. 读取迁移前样本与数量；确认legacy行生成规则没有被其他写路径复用。
2. 为既有正常UUID新提交行保留created_at，标记EXACT。
3. 对V021回填且没有可靠提交证据的行，将当前created_at复制到legacy_recorded_at，然后created_at置null、confidence置UNKNOWN。
4. 若已有可靠原提交事件/回执能确定真实时刻，可在受控恢复程序中绑定materialId/version/author后恢复EXACT，并登记依据；不能仅凭request.updated_at或“材料尚未审核”就假定时间准确。
5. 不改变material_request.updated_at，它仍代表材料最后修改时间；不同时间字段保留各自语义。
6. 迁移前后逐类核对行数、版本、作者、内容、withdrawn一致，只有明确的时间字段发生预期变化。

### 5.4 V021不能重写

V021可能已经执行。不能修改旧SQL、删除Flyway历史、repair校验和或清库重建来掩盖回填问题。

新库从V001跑到最新时会先经过V021，再由新迁移矫正legacy时间；已有V021实例直接跑新迁移。两条路线最终语义应一致。已有V020数据库升级也必须测，不只新建空库建表。

若发现V021回填本身因异常旧ID碰撞等无法执行，应单列精确升级阻断及数据库事实，不能擅自篡改已执行脚本；本轮不要预设存在此问题而重构全部迁移。

### 5.5 真实时间恢复的边界

“数据库里有一个非空时间”不等于“它是该版提交时间”。可靠依据至少要能绑定同一材料ID、同一responseVersion、提交动作及真实服务端时刻。

审核、撤回、最近更新时间、导入时间、迁移时间、浏览器本地时间都不能直接当作提交证据。确实无法恢复就UNKNOWN，这是已确认的允许结果，不需要为它造假数据让字段看起来完整。

## 6. J03：DTO、前端及幂等兼容

### 6.1 后端

1. 更新GovRepository.MaterialResponseRow与row mapper，null时间不得直接调用 `toInstant()` 导致NPE。
2. 更新GovViews.MaterialResponseItem及兼容response组装。数组和当前对象同一版本的createdAt/confidence必须一致。
3. 使用支持null值的Map构造（如LinkedHashMap），不能对UNKNOWN调用Map.of("createdAt", null)。优先用明确DTO避免重复序列化逻辑。

5. 旧幂等回执可能缺createdAtConfidence或保存错误时间：继续从缓存资源ID加载当前数据库投影；不能直接回放旧时间和旧正文。
6. 排序优先使用已有版本号而非createdAt，UNKNOWN不能打乱响应历史顺序。真实业务期限判断不得把null当0、当前时间或迟交；不基于不可信legacy时间作新的不利结论。
7. 保持用户权限：时间补充不改变谁可以看到材料正文/作者/历史；无权时不能借时间字段枚举私密记录。

### 6.2 Android

执行前定位真实P50材料模型、JSON解析和显示组件，记录修改路径。如果当前工作区只有后端和文档，应在交付中列出前端待修改项及契约样例，不能声称客户端已改好，也不能因为缺客户端就停止后端修复。

解析规则：

- EXACT且有合法createdAt：按现有时区格式显示。
- UNKNOWN且createdAt=null：显示“历史提交时间不详”。
- 兼容老服务器缺confidence但有时间时，按原逻辑显示；新服务器必须遵守两条合法组合。
- 不对null执行Instant.parse或字符串截取；不显示字面量null，不显示1970年。
- 不隐藏整条历史响应；正文、版本号、撤回占位按原规则展示。
- 不把客户端can*当授权，失败冲突后刷新材料和case；不要自动重发材料制造新版本。

### 7.2 并发用例

- U01-J：审核与撤回，两个真实PG连接；控制事务拿锁顺序，分别测试先审核成功和先撤回成功。最终状态与response.withdrawn一致，失败方没有审核记录或第二次撤回。
- U01-K：结案与学生补交/撤回：case锁给出明确串行顺序，结案先提交后材料写入必须失败。
- U01-L：审核与补交v2：若v2先成功，旧版本审核失败；若审核先ACCEPT，新补交被状态规则拒绝。

不要把所有异常都算预期竞争失败。禁止出现500/死锁被测试吞掉、material.status=ACCEPTED但当前版本withdrawn=true、失败请求仍增加历史行等情况。

### 7.3 时间与升级用例

|编号|迁移前数据/操作|迁移后预期|
|---|---|---|
|U02-A|V020仅提交v1，缺独立可信时间证据|不凭updated_at猜测，按策略标UNKNOWN|
|U02-B|V020 10:00提交，11:00审核|不能输出11:00为真实提交时间；旧值留作内部诊断|
|U02-C|V020 10:00提交，12:00撤回|UNKNOWN且仍撤回占位，不恢复正文|
|U02-D|V021已有legacy行和真实UUID新提交行|仅legacy不可信时间被矫正，真实新提交不受影响|
|U02-E|有可靠事件精确恢复旧版本时间|有恢复依据，EXACT和时间正确，重复恢复无变更|
|U02-F|升级后新提交/补交|createdAt为实际Clock时刻，confidence=EXACT|
|U02-G|新库全量、V020升级、V021升级、重复启动|结果一致，Flyway校验正确，无重复行|
|U02-H|未知时间序列化、GET/内嵌/列表/回放|显式null，confidence=UNKNOWN，无NPE或Map.of异常|
|U02-I|前端解析未知及精确时间|不崩溃，未知显示指定文案，旧数据兼容|

升级夹具必须将提交、审核、撤回时间分开。把三个时间设成同一常量会掩盖U02，不能证明迁移正确。
