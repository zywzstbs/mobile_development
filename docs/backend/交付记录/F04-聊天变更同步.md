## 2. 算法

1. 先 `requireMember`（失权优先 403），再解析游标。
2. 首次无 `afterChangeCursor`：同一快照取历史页与当前高水位 H，`changes=[]`、`hasMoreChanges=false`，签发指向 H 的新游标；**不从 0 补发历史**。
3. 带有效游标 C：同一快照取 H；`C < change_sequence <= H ORDER BY change_sequence LIMIT 101`。前 100 条为本批，第 101 条只判定 `hasMoreChanges`。
4. 游标位置取**最后一条实际扫描事件**，不跳到 H；同一消息多事件按 `messageId` 合并，保留当前 revision 最高的行；每批最多 100 个投影。
5. 无事件时位置保持 C，返回可继续使用的同一 token；token 从首次签发起 7 天有效，续页不延长到期。
6. 清理边界：若 `earliestChangeSequence > 0` 且 `C+1 < earliest`，无法连续恢复，409 `CHAT_SYNC_EXPIRED`。
7. 绑定本人、项目、`project.authorization_epoch`、期限；伪造/过期/跨用户/跨项目/授权代次变化均 409，不返回他人的变更。
8. changes 不增加未读、不写 read_state、不登记下发区间。
9. 历史页 `hasMore` 通过多取 1 条判断；`beforeSequence/search/around` 的 `nextAfterSequence` 不推进连续增量位置；`q` 与 after/before 仍互斥。

`messages()` 已不是 `readOnly` 事务：它需要写入异步游标位置和下发区间；一致性快照使用 `Isolation.REPEATABLE_READ`。

## 4. 兼容影响

- 旧实现接受的裸数字游标不再兼容，统一 409 `CHAT_SYNC_EXPIRED`，客户端需重建基线；这是方案要求的“不能裸整数游标”。
- `nextChangeCursor` 仍为非空 string；`changes` 结构未变。
- 每批最多 100，首次不返回历史变更；依赖客户端按 04/CHAT 协议先拉历史再增量。
