# P16 第三步：空库升级、恢复、重启、文件核对与清理预览

日期：2026-11-01  
状态：本步完成。没有做云部署，也没有用 pg_dump；本机 PostgreSQL 包里没有这个客户端。

## 代码

- `CleanupAdminService`：`cleanup-plan` 只允许 dry-run，列出 `WAITING` / `WOULD_DELETE` / `BLOCKED_BY_REFERENCE`，不改状态、不删文件。
- `cleanup-cancel` 把计划改为 `CANCELLED`，并写审计原因。
- CLI：`--app.cli.command=cleanup-plan --app.cli.dry-run=true`，以及 `cleanup-cancel --app.cli.plan-id --app.cli.reason`。

```
TEST_DB_URL='jdbc:postgresql://localhost:55432/postgres?currentSchema=gulupai_test' \
  ./mvnw -Dit.test=FileP05FIT,EmptyUpgradeIT verify
```

BUILD SUCCESS。`EmptyUpgradeIT` 1 通过，`FileP05FIT` 5 通过，同次单元测试 38 通过。

- 空 schema `gulupai_p16_empty` 从零执行 V001～V018，第二次迁移 0 条。
- 表数据复制到 `gulupai_p16_restore` 后删除源 schema。恢复侧 Flyway 版本仍是 018，`schema_baseline` 仍是 P00。
- 应用对恢复库启动两次，端口 18080。两次 `GET /health` 都是 `OK` / 数据库 `UP`。第二次启动日志：schema 已在 018，无需再迁移。随后查库，基线仍是 P00。
- 文件核对沿用 `FileP05FIT.reconcileRepairsMissingBytesAndCleansOrphans`：缺字节标失败，孤立文件先进入 7 天计划，到期后才删除。时间用测试时钟推进 25 小时和 8 天。
- 新增 `cleanupDryRunDoesNotDeleteAndCancelStopsExecution`：到期预览为 `WOULD_DELETE` 时文件还在；取消后核对不会执行这张已取消计划。文件仍无引用时，核对会另开一张新的 `WAITING` 计划，而不是立刻删除。
