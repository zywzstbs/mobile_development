## 2. 新的 gap 与允许条件

内部 gap code（映射到既有 `GapView`，不新增公开错误码）：

|code|含义|写入的位置|
|---|---|---|
|`UNSIGNED`|份额未本人确认|`GapView("LEDGER")`|
|`AGREEMENT_PENDING`|正式约定尚未生效/缺少生效约定|同上|
|`PENDING_SUBMISSION`|该交付项仍有 PENDING 提交|同上|
|`HANDOVER_PENDING`|任务仍在交接中，或已执行但尚未重签|同上|
|`BEFORE_DUE`|截止前尚未完成|同上|
|`UNCONFIRMED`|已验收但本人未确认贡献|同上|

允许 `accepted=0` 的条件：已签有效份额、已到截止、无待处理提交、无交接阻断、无待确认验收、约定已生效。`now == dueAt` 归入“已到期”（`!now.isBefore(dueAt)`），与旧实现一致并新增边界用例。

教学更正分支：先算 `signed/agreement/submission/handover/due/unconfirmed` 全部程序性 gap，再决定 `accepted` 取更正值还是 0；更正不能跳过阻断。

## 3. sourceKey 依赖

`grade-ledger-v2` 每行包含：

```
unitId | shareId | agreementVersion | points | signed | dueAt |
activeVersion | openAgreementVersion | openAgreementStatus |
acceptanceId | acceptanceKind | confirmed |
correctionId:correctionRevision |
pendingSubmissionId | handover(changeId:planVersion:status:blocked) |
responsibility | accepted
```

因此 PENDING→REVIEWED/撤回、约定生效/重签、交接状态改变、更正新增/替换都会使旧 `sourceKey` 失效。历史 `settlement`/`grade_snapshot` 保持不可变。

## 4. 锁顺序

|事务|加锁顺序|
|---|---|
|结算/更正/发布（GradeService）|`assignment` → 该 assignment 全部 `task`（`ORDER BY p.id,t.id`）→ 读来源|
|提交/验收/撤回/份额确认（DeliveryService）|`submission`（仅撤回/验收现存提交时）→ `project` → `task` → `delivery_unit`/`submission` 业务行|
|交接执行（GovService）|`member_change` → `project` → `task`（按 item）→ membership/role|
|约定确认（DeliveryService）|`project` → `task` → `agreement`|

共同保护锁是 `task` 行：结算持有全部 task 行锁；提交/验收/撤回/份额确认、约定确认、交接执行都必须先取得对应 task 行。没有反向 `task → project/assignment` 的路径，避免与结算的 `assignment → task` 形成环。`previewPublication`/`candidate` 只读不锁，发布时重新按 `basisDigest` 校验。
