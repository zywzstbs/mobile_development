## 2. 算法

1. GET 只登记**实际返回的历史 items** 的连续序号区间；稀疏搜索只登记实际命中的点/连续片段，不用 min/max 包住中间未返回的消息；changes 不登记。
2. 每个区间按“相邻/连续”切分；若已有区间完全覆盖则不重复插入；撤回占位保留合法 sequence，可参与覆盖。
3. GET 不改变 `chat_read_state`；不把未读清零。
4. PUT：
   - 要求 Idempotency-Key；同键异体 409 `IDEMPOTENCY_KEY_REUSED`；
   - `policy.requireActiveBusinessUser` + 当前项目成员；
   - `INSERT ... ON CONFLICT DO NOTHING` 建 read_state，再 `SELECT ... FOR UPDATE`；
   - `T <= L`：合法不回退，返回 L（其它设备已推进的值）；
   - `T > L`：校验 `T <= latestSequence`，再按当前 `authorization_epoch` 的区间检查 `L+1..T` 连续覆盖；任何缺口 422，不执行 GREATEST 跳过；
   - 通过后写 `last_sequence=T`，删除 `end <= T` 的旧区间；
   - 回放投影按当前 `chat_read_state` 返回最新合法位置，不回退成旧回执值。
5. 授权代次：`project.authorization_epoch`。本轮补齐真实递增点：邀请接受（`TeamService`）、转组/退出执行（`GovService`）、广场合并迁移项目（`MergeRepository`）；离组重入后旧的 `chat_delivery_range` 不再被当前代次引用。

## 4. 兼容与边界

- CHAT-06 新增 Idempotency-Key 要求：缺键由原“直接写入”变为 400 `IDEMPOTENCY_KEY_REQUIRED`。这是方案要求的统一写协议；P50 写接口本就带键。
- `Cursor` 响应字段未变，仅 `lastSequence` 可能因其它设备推进而大于请求值。
- 存量 `chat_read_state.last_sequence` 保留为旧基线；迁移不把 0～latest 批量标成“已下发”，也不清空现有进度。
- 若下发区间记录被清理/丢失，保守要求重新拉取，不放宽为只校验 latest。
