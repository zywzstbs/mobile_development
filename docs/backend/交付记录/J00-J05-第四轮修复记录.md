## J00：状态表、旧迁移与失败基线

### J00.1 当前材料状态与动作矩阵

以 case 未结案、操作者有对应身份、请求 revision 正确为前提；`RESPONDED` 是当前数据库/响应中的待审核值。

|材料状态|指定学生新提交/补交|指定学生撤回当前版|当前处理教师审核|
|---|---|---|---|
|OPEN|允许，首版|拒绝（无当前正文）|拒绝|
|RESPONDED|允许，新版本|允许|允许，必须核当前真实且未撤回版本|
|RETURNED|允许，新版本|允许（当前版存在且未撤回）|拒绝，先等重新提交|
|WITHDRAWN|允许，新版本|拒绝重复撤回；同键旧成功可回放|拒绝|
|ACCEPTED|拒绝|拒绝|拒绝普通重复审核；同键旧成功可回放|

case 层：`CLOSED` 拒绝新提交/撤回/审核；`OPEN/IN_PROGRESS` 仍需对应身份和当前 assignee；已 ACCEPTED 材料不因 case 未结案而可重交；case 未结案也不能审核已撤回版本。不新增“过截止一律不能补交”的规则。

### J00.2 名称差异结论（RESPONDED / SUBMITTED）

- 当前 `material_request` 的 CHECK 约束、`TodoQueryService` 和全部现有后端测试使用 `RESPONDED`；原 API 通用状态表写 `SUBMITTED`。
- 工作区没有 P50/Android 源码（`../final_project/frontend` 为空），`10-P50前端源码核查.md` 没有材料状态/`responses[]` 解析记录，无法验证客户端是否依赖 `SUBMITTED`。
- 本轮**不全局替换枚举、不做未经客户端验证的响应层映射**，避免数据库与响应出现两套状态或查询随机漏项。J00 记录该差异，作为后续 P50 联调核对项；若联调确认必须投影 `SUBMITTED`，应在响应层单点映射并补客户端契约测试，不能改库枚举。

## J01/U01：统一动作资格与锁后校验

### J01.1 代码

- 新增 `MaterialActionPolicy`（纯规则，不发 SQL、不改状态）：输入 case 状态、材料状态、`responseVersion`、当前 response 是否存在/已撤回、收件人和处理人结果，输出三个许可和内部阻断原因。
- `materialView` 的 `canRespond/canWithdraw/canReview` 与 `respondMaterialOnce`、`withdrawMaterialOnce`、`reviewMaterialOnce` 共用该规则；写入口在 `case → material → 当前 response` 锁后重新计算，不信任读取瞬间的 can*。
- `respondMaterialOnce`：锁后重核 case 关联/账号/指定学生/expectedRevision；ACCEPTED、CLOSED 在 `insertMaterialResponse` 前拒绝；`responseVersion >= 999999999` 按冲突拒绝；一次 `Clock` 写版本、正文、证据、作者、`EXACT/SERVER_SUBMISSION`；更新行数必须为 1。
- `withdrawMaterialOnce`：拒绝 CLOSED、ACCEPTED、OPEN、WITHDRAWN；`lockMaterialResponse` 取当前行；`withdrawMaterialResponse` 影响行数必须为 1；再更新材料状态，全部同事务。
- `reviewMaterialOnce`：锁 case→material→目标任务 response；必须 case 可办理、material=RESPONDED、request.responseVersion=material.responseVersion、当前行真实且 `withdrawn=false`；RETURN 理由 strip 后必须非空；失败不写 `material_review`。
- 错误码复用：身份/处理资格 403；revision 不符 `RESOURCE_CHANGED`；状态/来源变化 `SOURCE_CHANGED`。没有新增公共错误码。
- 数据层：删除万能 `updateMaterial`，改为 `markMaterialResponded`、`markMaterialWithdrawn`、`markMaterialReviewed`，分别带允许状态、旧 `response_version`、`revision` 和 `case.status <> 'CLOSED'`；审核 SQL 另要求当前 response 存在且未撤回。
- 合法路径保留：RESPONDED 补交 v2、RETURNED 重新提交/撤回、WITHDRAWN 重新提交、同键回放、审核与撤回由同一 case/material 锁串行。

## J02/U02：时间来源与纠错迁移

### J02.1 V022

新增 `V022__material_response_time_confidence.sql`，不修改 V021：

- `material_response.created_at` 允许 null。
- 新增非空 `created_at_confidence`（`EXACT`/`UNKNOWN`），无默认值，新应用必须显式写。
- 新增 `legacy_recorded_at`，保存 V021 回填值，仅诊断/审计，不向前端输出。
- 新增 `time_source`（`SERVER_SUBMISSION`/`RECOVERED_EVIDENCE`/`LEGACY_UNKNOWN`）及恢复依据 `time_evidence`、`time_recovered_by`、`time_recovered_at`。
- 约束：EXACT 必须 `created_at` 非空；UNKNOWN 必须为空；LEGACY_UNKNOWN 必须是 UNKNOWN；RECOVERED_EVIDENCE 必须登记依据和恢复时间。

### J02.2 legacy 识别

只按 V021 的确定性规则识别：`material_response.id = left('legacy-' || material_request.id, 120)`，并核 `material_id`、`id LIKE 'legacy-%'`、`author_id = material_request.recipient_id`。不按 `created_at` 是否“像当前时间”猜测，也不把 UUID 新提交当 legacy。

- legacy 行：`legacy_recorded_at = created_at`，`created_at = NULL`，`UNKNOWN/LEGACY_UNKNOWN`。
- 其他行：保留 `created_at`，`EXACT/SERVER_SUBMISSION`。
- 正文、版本、作者、`withdrawn` 不动；`material_request.updated_at` 仍表示最后修改时间，不迁移改写。

### J02.3 受控恢复（U02-E）

`MaterialResponseTimeRecoveryService` + CLI：

```bash
--app.cli.command=material-time-recovery \
--app.cli.material-id=<materialId> --app.cli.response-version=<version> \
--app.cli.receipt-id=<operation_receiptId> [--app.cli.dry-run=true]
```

只接受 `POST`、路径精确为 `/api/v1/material-requests/{materialId}/responses`、`business_code=OK`、`user_id=material_response.author_id` 的成功回执；回执 `created_at` 作为恢复时间，写入 `RECOVERED_EVIDENCE` 和 `time_evidence=operation_receipt:<id>`。重复恢复同回执返回 `ALREADY_RECOVERED` 且无变更；已有其他 EXACT 依据时拒绝覆盖。没有回执或路径/作者不匹配时保持 UNKNOWN，不把审核/撤回/最近更新时间当证据。

未做自动恢复迁移：Flyway SQL 不能解密/核验回执，旧回执也可能超过保留期；恢复必须显式受控执行，宁可 UNKNOWN 不造假。
