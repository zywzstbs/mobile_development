## 2. 规范请求摘要（version 1）

`CanonicalJson.hash` 的对象：

```json
{
  "requestHashVersion": 1,
  "content": <请求原始字符串，保留空白；可为 null>,
  "refs": [{"type": "...", "id": "...", "version": 1}, ...],   // 数组顺序敏感
  "mentions": ["..."]                                           // 去重后保留首次出现顺序
}
```

- 作者、项目、clientMessageId 由唯一键 `(project_id, author_id, client_message_id)` 绑定，不重复放进摘要。
- 不对正文 trim，不重排 refs；mentions 按业务“去重当前成员 ID”语义去重后保序。
- 摘要与消息、sequence、chat_change、outbox 同一事务写入。
- 撤回只清展示内容，不清 `request_hash`。

## 3. 行为

|场景|结果|
|---|---|
|同 clientMessageId + 同摘要，不同 Idempotency-Key|返回现有消息的**当前安全投影**，不新增消息/sequence/outbox|
|同 clientMessageId + 不同 content/refs/mentions/version|409 `CLIENT_MESSAGE_ID_REUSED`|
|同 Idempotency-Key 异请求|沿用统一 409 `IDEMPOTENCY_KEY_REUSED`|
|撤回后同请求、新 Key|返回 withdrawn 占位，无正文/引用|
|撤回后异请求|409 `CLIENT_MESSAGE_ID_REUSED`|
|存量 `request_hash IS NULL`|legacy/unverifiable：同 clientMessageId 重试保守 409，不恢复正文、不创建新消息|
|迁移前已发生“同 ID 异 refs 却成功”|只保住实际落库的原记录，不补造历史|

并发：发送前先取 `chat_counter` 项目行锁（`lockCounter`），再查 clientMessageId；同项目发送串行，唯一约束仍是最终防线。捕获唯一冲突时只返回冲突码，不在已失败事务中继续查询。

## 5. 兼容边界

- 存量非撤回记录也标记为 unverifiable。原因是旧实现保存的是 trim 后正文与去重后 mentions，无法无损还原原始请求；按方案“仅在规范化可确定时回填”的要求，本轮不猜测。
- 影响：升级前创建、且客户端仍用原 clientMessageId 重试的旧消息会得到 409，而不是旧成功回执。这是保守且不泄露正文的选择；客户端应改用新 clientMessageId。
- P50 请求字段未增删，未知字段仍 422。
