## 3. 实现要点

- ROLE-21：非空 id 只定位本项目已有岗位，可同时带 clientKey；空 id 加 clientKey 才新增，新 ID 由服务器生成。陌生或跨项目 id 不当作新增。clientKey 同次唯一，不能覆盖其他岗位身份。
- 岗位人数总和原子更新 capacity，且不能低于已在岗成员加有效预留，也不能删掉仍被成员、预留、申请或邀请引用的岗位。
- QUICK 转 DETAILED 必须一次提交 completeDetails 与 leaderRoleKey。组长占指定岗位，其他已有成员保持未选岗。已是 DETAILED 时禁止再传这两项。
- 提议、交换、多人计划冻结成员、岗位和当时的组长。只有当事人能回应。最后一名 ACCEPT 在锁内重验来源和容量后一次改岗；DECLINE 或组长 WITHDRAW 终止并保留历史。中间确认不抬协商版本，避免最后两票并发时第二票被版本挡住。
- 来源失效时方案保留但不能接受：组长变更、成员或岗位变化、容量冲突分别投影为 `LEADER_CHANGED`、`MEMBERSHIP_CHANGED`、`ROLE_CHANGED`、`ROLE_CAPACITY_CONFLICT`。接受时返回 `SOURCE_CHANGED` 或 `ROLE_FULL`。
- 计划只改列出的成员。之后新加入的成员不会被旧计划改写岗位。

## 6. 已知边界

1. 邀请接受沿用 P03：统计岗位占用时，受邀人自己那条尚未消耗的预留也算在内。因此岗位 total 需要大于“已在岗人数 + 含本人预留”，接受才会成功。岗位编辑和协商本身按“已在岗 + 有效预留”拒绝超占。
2. 组长变更通过 `project.owner_id` 判断。P04 不实现组长移交，移交属于后续人员治理。
3. 协商列表当前完整返回，不做游标快照。
4. 未做 Android 联调，未部署云服务器。
