## 仍需修复：R2 审核身份来源可伪造（P1）

位置：`src/main/java/cn/gulupai/server/identity/cli/CliOperatorDirectory.java:69`。

本轮新增操作系统用户名到审核主体的映射，但currentOsUser使用System.getProperty("user.name")。这是可由启动者通过`-Duser.name=...`覆盖的Java系统属性，不是可信的操作系统身份。具备启动CLI权限的人可声明已授权的用户名，命中另一审核主体，从而冒用审计身份或绕过按subjectId进行的自审检查。这仍是本地主机CLI信任边界的问题，不是匿名HTTP提权。

本轮已用无业务写入的命令验证：

```bash
.tools/jdk-21.0.13+9/bin/java -Duser.name=p62_forged_operator -XshowSettings:properties -version
```

实际输出包含`user.name = p62_forged_operator`。未执行真实审批。

同一问题的另一入口：operators通过@ConfigurationProperties(prefix="app.cli")普通配置绑定，Spring命令行属性可以覆盖部署映射。当前只拒绝app.cli.actor，并不拒绝app.cli.operators[0].os-user/subject-id/display-label等覆盖。注释所称“不在命令行临时指定”没有实现。

修复要求：从可信OS有效身份获取主体，并将审核映射放在操作者不能临时覆盖的受保护来源；或用固定受控启动器锁定JVM参数、配置文件、环境和命令参数，明确部署信任边界。不能仅把user.name换成同样可改的USER环境变量。增加启动级测试，证明-Duser.name伪造及operators命令行覆盖均不能改变审核人。现有测试只测自由actor参数，未覆盖这两个入口。
