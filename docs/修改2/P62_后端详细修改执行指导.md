# P62 后端详细修改执行指导（供执行模型使用）

编制日期：2026-11-04。

依据：[P62 前端接入契约](P62_注册与体验修复_后端接入说明.md)，包括其第8节续做补充。本文根据当前 Java 后端源码核对编写；不是部署完成证明，也不是线上问题的最终归因。

第11节里原先缺少枚举的通知偏好，已按仓库完整接口文档收成下面的实现约定，并据此改了后端：

- `courseNotices`、`mentions`、`supportReplies` 都是 `IN_APP` 或 `SYSTEM`。请求和响应示例都是字符串 `IN_APP`；索引里把 `mentions` 写成“最多20个成员 ID”与类型、示例矛盾，不采用。
- `projectChatModes` 是聊天偏好覆盖。元素为 `projectId` 加 `mode`，`mode` 取 `ALL`、`MENTIONS`、`MUTE`。索引里的 `QUICK/DETAILED` 属于项目模式，不是这条聊天覆盖。单用户最多 20 项，项目必须存在且当前用户是活跃成员，重复项目拒绝。
- 旧偏好行迁移时，三个渠道沿用原来的单一 `channel`，`quietHours.enabled` 记为 true，因为旧结构无法表达关闭。无记录的读取仍是 revision 0，不写库。
- 学生请求若带上 `teacherApplication`，返回 422，不静默丢掉。
- 编辑作业的截止时间不从创建规则继承“必须是未来”。已有任意项目使用该作业时，截止和人数只能保持原值。

## 1. 执行任务与边界

在本仓库实现 P62 所需后端能力，并修复契约差异，提交代码、增量迁移、自动化测试、接口文档和可复现验收记录。所有接口路径以下省略 `/api/v1` 前缀。客户端仍使用原服务器、包名及签名，本任务不修改 Android 键盘、弹窗、版本号或签名。

规则优先级：P62 明确覆盖的规则优先于旧 P58/名单开户限制；未覆盖部分沿用既有业务约束。学生和教师允许申请注册不意味着自动核验学校事实、获得课程资格、加入小组或获得后台能力。禁止用假账号、假成功、伪造版本及空字段默认值掩盖缺失实现。

先读取本目录原始契约以及涉及模块现有实现、测试和迁移，再修改。本文中“建议”是实现设计，不是新增前端契约；缺失的枚举、字段语义必须从仓库完整接口文档和前端补充材料核实。不要把待核实项擅自定成公开协议。

## 4. 注册及教师审核

### 4.1 匿名选项

新增 GET `/auth/registration-options`。仅该路径及 POST `/auth/registrations` 精确加入匿名白名单；不要开放整个 `/auth/**` 或 `/schools`。检查访问令牌过滤器是否会在到达控制器前阻断匿名路径。

HTTP200，data 为 enabled、teacherApplicationEnabled、schools。schools 只包含允许注册学校的 id/name，ID唯一，完整返回且最多1000项。注册关闭仍返回200及false；无学校返回[]。建议配置全局开关和学校注册许可，复用真实学校主数据，不把所有学校隐含设为开放。超1000须显式报错并协商分页，不能截断。开关及学校资格须在提交时重新核验。

### 4.2 注册请求与响应

POST `/auth/registrations` 匿名，必需幂等键；成功HTTP200，data严格为 `{id, requestedRole, status}`。学生为ACTIVE，教师为PENDING_REVIEW，不返回token，不建会话，不返回核验原文。

|字段|实施要求|
|---|---|
|loginId|trim后4～32，正则 `[A-Za-z][A-Za-z0-9_]{3,31}`；规范化和登录、导入一致|
|password|8～64 UTF-16 code unit，不trim，不截断，不记录原文|
|displayName|trim后1～24 UTF-16 code unit|
|schoolId|提交时仍在允许注册学校集合内|
|requestedRole|仅STUDENT/TEACHER，不直接绑定权限集合|
|teacherApplication|TEACHER必填，trim后5～500；STUDENT省略。学生附带该字段的处理需明确记录，建议拒绝而非静默使用|

拒绝 roles/capabilities/identityStatus/reviewedBy 和所有未知字段，422 FIELD_NOT_ALLOWED。不要关闭全局未知字段拒绝。DTO 自动生成的 toString 也可能泄露密码，禁止记录请求对象。

当前账号查找区分大小写。优先保持当前语义、共享规范化函数并覆盖导入账号；不能未经数据碰撞检查突然全库转小写。数据库唯一约束才是并发判重依据；精确将账号唯一冲突映射409 ACCOUNT_EXISTS，不能将所有完整性异常一概映射为重名。

### 4.3 存储与事务设计（建议）

使用独立注册记录存申请类型、审核状态、用户关联、学校、核验材料、revision及审核元数据；账号表存密码哈希及登录唯一标识。教师可以预留账号标识和密码哈希，但审核前不激活登录、不授TEACHER。若将待审凭据放独立表，必须解决与已导入app_user之间的跨表唯一性，不能各建一个唯一索引就宣称全局唯一。

学生ACTIVE仅表示可登录；学校身份仍按已有未核验状态处理。教师审批状态也不能直接复用学校 identity_status 造成“审核通过就自动认领课程”。分别解释账号状态、申请状态、学校事实状态，核查所有使用这些状态的策略。

申请创建、凭据占位、基础角色写入、幂等回执在同一事务提交。审核更新、基础TEACHER授予和审计也同一事务提交，任何失败整体回滚。

### 4.4 匿名幂等及限流

不要创建虚假登录principal，也不要使现有幂等服务任意接受null。建议为注册建立独立命名空间及存储：以端点+幂等键为唯一范围，安全指纹、固定初始回执、过期时间、指纹密钥版本为主要字段。正文规范化需保留密码原始空格，并覆盖所有有效字段；不能仅哈希loginId。建议用服务端密钥HMAC指纹，密钥从受控配置读取；保存回执不保存完整请求JSON。

同键同正文仅产生一份账号/申请，返回首次回执；同键不同正文409 IDEMPOTENCY_KEY_REUSED。并发同键应等待首事务结果或按明确的可重试策略处理，不能重复落库。不同键同账号由唯一约束裁决，只成功一个。审核后同键重放仍返回最初PENDING_REVIEW，不能将回执当当前状态查询。规定过期清理、密钥轮换、关闭注册后的重放策略并写测试；唯一账号约束始终保留。

沿用成熟PasswordEncoder，检查其对最大长度及非ASCII密码的支持，验证64 UTF-16单元的多字节密码不被静默截断。限流至少分别覆盖账号与可信来源IP，不能只使用账号+IP组合让换账号绕过IP限制。429 RATE_LIMITED，可提供真实Retry-After。注册关闭403 REGISTRATION_DISABLED。不要信任任意客户端X-Forwarded-For。

### 4.5 审核工具与登录

按现有受控CLI/运维机制新增待审读取及批准/驳回命令；本轮不做公开App审核API。审核输入包含申请ID、expectedRevision、决定、理由；审核人来自可信运行身份，不能任意填写后视为已授权。拒绝自审，核验说明只是线索，不能自动据此授予身份。

状态机：PENDING_REVIEW → ACTIVE或REJECTED；并发审核仅一个成功，记录审核人、时间、理由、前后版本。未约定的撤销或重新申请不要暗中实现。

登录先完成密码校验，错误密码统一现有INVALID_CREDENTIALS；正确密码待审403 ACCOUNT_PENDING_REVIEW、驳回403 ACCOUNT_REJECTED；批准后沿用会话机制。事务内再次确认状态，防止状态竞争。检查刷新、令牌过滤、CurrentUserPolicy，确保待审账户无可用旧会话。基础TEACHER不附带HELP_CONTENT_WRITE、SUPPORT_HANDLE或任课关系。

## 5. 学生代建作业编辑

### 5.1 创建者及投影

新增可信created_by存储，创建时取principal.userId。旧记录只能在唯一可信证据可验证时回填；否则null。不能从课程老师、首个成员或学校名单猜测创建者。

AssignmentRow、SQL映射、AssignmentView、CourseProjectionService及所有调用处同步更新。投影需要当前请求人上下文：可读取当前课程、本人创建、origin=STUDENT、confirmationStatus=PENDING_CONFIRMATION、资源未处于禁止编辑的历史状态，才canEdit=true；无法确认一律false。

至少覆盖广场作业列表、作业详情、创建、编辑响应；确认响应及其他复用投影也核查。不要将一位用户计算出的canEdit缓存并返回另一位用户。创建和确认的旧幂等回执缺新字段时，采用兼容回放投影，避免反序列化失败或回放过时编辑权。

### 5.2 PATCH契约

新增 PATCH `/assignments/{id}`，登录、Idempotency-Key必需。正文为expectedRevision及全部五类可编辑值：name、requirements、hardDueAt、minMembers、maxMembers。拒绝只读字段及缺失值，不能将PATCH擅自实现为可省略字段的局部更新。

name trim后1～100，requirements trim后1～10000，人数必须整数且1≤min≤max≤20，时间为有效RFC3339瞬间。现创建规则是名称120/要求5000且截止必须未来；不要直接复用该校验导致编辑契约错误。编辑契约未要求截止必须未来，尤其已有项目的过期作业应允许原截止不变的文字修正。若统一创建规则，先记录旧数据与兼容影响。

鉴权先核验当前课程读取资格，再核验本人、状态及版本。非本人403；已确认409 ASSIGNMENT_LOCKED或RESOURCE_CHANGED；版本冲突409 RESOURCE_CHANGED。成功返回同一完整对象、revision+1。

### 5.3 并发与使用中的约束

在同一事务锁作业行或使用等价严格CAS。确认和编辑必须竞争同一revision，更新条件包含预期版本及待确认状态，受影响行数必须为1。

任何小组/项目已使用作业时，截止和人数只能保持原值，变化409 ASSIGNMENT_IN_USE；名称/要求可改。比较时间用Instant，不用字符串，等价时区写法不算修改。查找实际作业关联关系，不能只查活跃小组绕过“任意小组”规则。

特别补齐“编辑检查没有小组→另一事务创建小组→编辑修改约束”的竞态：建组入口和约束编辑按统一顺序锁同一作业行，或使用等价数据库隔离方案。只给PATCH加锁、建组不参与，仍存在漏洞。

不得改id、squareId、createdBy、origin、confirmationStatus、gradingEnabled、sourceReferences；不重建作业、不迁移任务、不改成员和成绩。记录前后版本及动作审计。

### 5.4 幂等回放

复用IdempotencyService的ReplayProjector或历史回放接口，回放前重新核验当前身份、课程资格、创建者、确认状态，并比较当前revision与缓存成功结果revision。不能用原请求expectedRevision比较成功后的版本，否则正常重试也必然失败。

资源仍是本次保存后的同一版本且可编辑，才允许回放；已确认、又被编辑或资格已失效时返回当前冲突/权限错误。回放不再执行更新、审计或递增revision。旧结构回执适配不能绕过这些检查。

## 6. 本人协作偏好与字段错误

保留现有用户行锁、expectedRevision=0首次创建和revision=1的实现；不要新增重复版本机制。P62报告的请求编号仅是线上定位线索，没有线上日志时不能写“已定位线上根因”。

先补真实GET `/me/profile`→原样PUT测试：默认collaborationGoal为空，现DTO @NotBlank和normalize非空要求均会拒绝；两层都需要处理。P62未要求协作期待非空，建议允许空文本，并明确null与空串的规范化策略。不要擅自改变READY等历史availability值的含义。

统一DTO与服务：昵称1～24 UTF-16单元，技能≤8项且每项≤20，weeklyHours整数0～60，availability/collaborationGoal各≤180，intro≤300。列表null、空项、缺字段、空白文本分别测试。已存超新限额资料不能在GET偷偷截断，记录兼容处理与引导修正方案。

校验失败保留现包络、HTTP422及VALIDATION_FAILED，可在data加入fieldErrors，每项仅field/code/message，最多20项。公共处理覆盖Bean Validation、服务层跨字段校验及安全可定位的解析类型错误。码可为REQUIRED、INVALID_FORMAT、TOO_LONG、OUT_OF_RANGE、DUPLICATE。未知字段仍FIELD_NOT_ALLOWED。

禁止使用FieldError.rejectedValue、异常原始输入值或完整DTO构造消息；不要回显密码、核验材料。顶层message中文简洁。保留X-Request-Id，认证过滤器等非Controller错误也要有统一包络。增加敏感字符串不出现在响应和日志的测试。

## 7. 通知偏好新结构

GET返回完整结构：

```json
{"revision":0,"timezone":"Asia/Shanghai","quietHours":{"enabled":true,"start":"22:00","end":"08:00"},"courseNotices":"IN_APP","mentions":"IN_APP","supportReplies":"IN_APP","chatDefault":"MENTIONS","projectChatModes":[]}
```

PUT使用expectedRevision及对应可写偏好。原文未完整定义三类渠道允许枚举、projectChatModes元素结构与规模限制：先查询既有完整API契约；仍找不到必须列为协议缺口，不能只接受空数组、随意设计字段或无条件丢弃非空设置。

改NoticeRequests.Preferences、NoticeViews.Preferences、NoticeService和NoticeRepository；配套增量迁移。三种渠道独立存储，quietHours含enabled，timezone校验真实时区，时间严格HH:mm，允许跨午夜。按已确认契约验证项目ID、模式及用户权限，拒绝重复项目。

旧记录channel映射三个渠道、quietStart/End映射quietHours需写明确转换规则。建议保留既有渠道而不是默认为静音；旧结构无法表达enabled时明确记录默认依据。无记录GET revision0且不写库；首次expectedRevision0原子插入revision1；后续按真实版本CAS。并发首次插入必须一个成功、另一个409而非500；所有偏好字段同事务保存。

检查真正消费这些偏好的通知/聊天路径，不能只扩展响应DTO而发送行为仍依赖旧channel。若要兼容旧客户端，明确旧PUT与新PUT的识别和冲突规则，混合矛盾字段拒绝；没有兼容依据时不要留下两套不一致值。

## 8. 合并资料与投票

MergeViews.SideView补当前用户canVote。计算依据必须与PUT投票授权使用同一规则：冻结选民集合、当前提案状态、真实可访问资格及其他既有限制，不能只看STUDENT角色。

两侧squareId不同且分别对应sourceSquareId/targetSquareId；冻结eligibleCount合法非负整数，requiredCount=floor(eligibleCount/2)+1，agreeCount等计数来自真实选票；passed不能在零选民时无条件通过。已有disagree/abstain/unvoted应核对总和与冻结人数一致。

返回标准agreeCount/requiredCount；若保留旧别名则两套严格相等。首次myBallot空对象或revision0，已投返回实际choice和正整数revision，不从他人票数推断本人票。为有资格、无资格、历史提案分别测试。

客户端按ID读取GET `/squares/{id}`课程资料，后端保证相关合法查看者能按既有权限读取；不得为修复空白资料开放所有课程。查看详情必须无投票和合并副作用。不要在真实课程执行测试投票或合并。
