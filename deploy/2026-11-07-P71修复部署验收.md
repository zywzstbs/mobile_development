## 2. 升级演练

在旧版继续提供服务时执行以下演练。

1. 导出线上一致性数据库快照，恢复到独立 preflight 数据库。
2. 将业务文件卷复制到独立演练文件卷，启动仅监听服务器 127.0.0.1:18081 的新版容器。
3. 新版启动自动完成 V031，核对 129 张原有业务表的数据指纹。app_user 的 eligibility_source 属新增字段，account_status 的预期归一化另外校验。
4. 在演练副本中通过受控 CLI 给原运营账号初始化超管，验证新管理读取。该授权只存在于演练数据库。
5. 完成 178 项 JSON HTTP 检查，覆盖 21 个既有测试账号的登录、本人资料、通知偏好、通知、刷新、授权拒绝及登出，另验证管理总览、账号、教师申请、课程、审计和超管目录。
6. 验证原有文件的授权下载，字节大小和 SHA-256 一致。下载授权 URL 和登录 token 仅在进程内使用。

演练通过后，才进入正式维护窗口。正式切换前重新导出最新数据库与文件备份，避免使用演练开始时的旧快照作为最终恢复点。

## 3. 正式切换及数据保留

维护代理完成校验和重载后，停止旧应用，备份数据库、文件、旧 JAR、旧环境与 Compose/Caddy 配置，再切换新版应用镜像。

新版启动后、向普通客户端重新开放前，再次核对原有表指纹，并逐账号比较 account_status/disabled 的迁移结果。原有两条 disabled=true 且 account_status=ACTIVE 的记录按 V031 归一化为 DISABLED，其余账号状态按原事实保留。

数据库密码、幂等加密密钥及其 key-id、注册指纹密钥及其 key-id 均在服务器内按原实际配置比对，结果一致。备份归档可由 pg_restore 读取，旧数据库快照及业务文件受限保存。
